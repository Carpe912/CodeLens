错因是**用错了 grep 语法**：当时跑的是
`grep -rn "loadOrderDetails\|batchProcessOrders" src/` ——
在 BSD grep（macOS）下 `\|` 是**字面量**而不是「或」，所以那条命令找的是字符串

→ 教训：验证「符号是否存在」一律 `grep -rnE "a|b"`；**无输出时先换一种搜法复核**
（`rg` / `grep -F` / 直接读文件）再下结论。
**代价不是多花几分钟，而是把两个真实缺口从 backlog 里删掉了 —— 差点放弃 100%。**

`classes`（类名），而「XX 功能是怎么实现的」全库只有 `code_chunks` 存实现正文。

**被推翻的两条**：
1. 「根因是 `ask.ts` 写死 `limit: 10`」——**错**。线上 `RERANK_ENABLED=true`、
   `RERANK_CANDIDATES=50` ⇒ `retrievalLimit = max(10,50) = 50`，**候选池是 50 条宽**，
   在 50 条里仍只有 5/19 ⇒ 预算解释不了。
2. 「换语料后噪声变多把结果挤掉了」——**错**。拿 `code_chunks` 已知 chunk 的向量直接做 KNN，
   top1 相似度 1.0，没有任何噪声能挤掉它。

**症状特征（值得记住的诊断信号）**：答案的「引用期望位置」接近满分、覆盖却是 0 ——
**「LLM 的答案引用了证据里不存在的东西」** ⇒ 它是从签名/常量里认出符号名的。

**三步定位法（可复用，10 秒级，不需要 embedding 服务/不需要 LLM）**：
① 按 `symbol_name + 文件base` 查 `code_chunks` → 19/19 全在且有向量 ⇒ 非 A 类；
② 用已知 chunk 自己的向量当 `$2`，跑新旧两种谓词对比 → 旧 0 行 / 新 3242 行 ⇒ 锁定 SQL 谓词；
③ grep 全仓 `code_chunks` + `repo_id` 组合 → 检索/分析层**仅此一处**违反约定。

**约定已被写了四遍**（`db/index.ts:552-562` 整段警告、`repos.ts:82-83`、`fuzzySearch` 注释、

### 实现了什么

`retrieval/multi-strategy-search.ts` 的 `expandWithDependencies(repoId, results, limit)`（原为空函数）。
语义：命中文件 F 里 `import { X } from './T'` ⇒ 把 **T 里定义 X 的块**补进结果。

三条不变式（都写进了代码注释）：

1. **不改原排名**：每个命中文件取分数最高的一条当「锚点」，补入项插在锚点正后方，

2. **上限挂钩证据预算**：`clamp(ceil(limit * 0.4), 2, 6)` —— `limit=10` → 4 条。因为下游最后是

3. **补不上必须出声**：0 条时区分「没有内部导入边」（warn + 提示 `rebuild-graph`）与「全部重复」（log）。

定位靠**符号级 JOIN**（这是它区别于「再加一次模糊检索」的地方）：
`import_relations ir JOIN files tf ON tf.id=ir.imported_file_id
 JOIN code_chunks c ON c.file_id=tf.id AND c.symbol_name=ir.imported_symbol`，只认内部边。

## 第 10 轮：把「要不要重建」收成**一条判据**（用户说"我到现在都没搞清楚"）

**教训（我的表述问题）**：前面给了两张情景表（"两层粒度" + "三个情景"），
它们其实是**同一条判据的两种投影**，但我一直没把那条判据本身说出来 ⇒ 用户越看越乱。
**给判断标准时，先给判据，再给投影；不要用情景表代替判据。**

**唯一判据**：**这次改动有没有移动「已有符号的行号」，或改变「符号名 / 文件清单」？**

两问落地：
1. **文件总行数变了吗？**（增删一行就算变）→ 是 ⇒ **必须完整重建**（后面所有符号行号被平移）。
2. 没变则：**改动是否只在已有符号内部**（函数体语句 / `.vue` 模板文案），名字没改？
   → 是 ⇒ **不用重建，但也别跑增量**；否 ⇒ **必须完整重建**。

**为什么是它**：索引里的东西按刷新机制分三类 —— ① 文件清单（增量可修）② chunk 文本+向量（增量可修）
③ 结构化事实（符号名/行号/签名/URL/导入/调用边）**只有整仓重建一条路**。
判据的本质 = 「这次改动动到第 ③ 类了吗」。行号或名字一变，③ 立刻失效；两者都没变则 ③ 仍有效，
只是 ② 的文本旧了 —— 而那一档又因增量会删调用边而**不能用增量**。

**实操口径**：完整重建 ≈ 6 分钟，半增量 ≈ 12 分钟 ⇒ **重建既更安全也更快，没有纠结余地。**

顺手试过一个"机器判据"（跨层行号一致性）：
`functions` 的 (name, line_start) 与 `code_chunks` 对不上的条数 —— 健康库 baseline 是 **11/1034**（≈1% 噪声），
`classes` 是 **0/203**。噪声来自同名/嵌套/变量箭头函数的口径差 ⇒ **不能当布尔判据**，未采纳。
另：`files` 表**没有 `updated_at`**，`updateFile()` 只改 content ⇒ **没有时间戳可用于判断新鲜度**。

## 第 12 轮：回答「和行号有什么关系，是给证据展示用的吗」

用户这一问点到了**判据的锚点本身**。答案是：**行号是索引唯一的坐标系，不是展示装饰。**

**索引不是源码副本，是「关于源码的地图」** —— 每个条目（函数/类/URL/调用边/代码块）都靠
`(文件, 行号)` 定位回源码。查到四个真实消费点（都已核对行号）：

| 消费点 | 位置 |
|---|---|

| VS Code 列表/问答 | `views/searchView.ts:37,47`、`views/qaWebview.ts:727` |
| 调用图节点 | `views/callGraphWebview.ts:288` → `openFile(path, line_start)` |
| Web | `apps/web/src/pages/RepoPage.tsx:1196,1221` |

**关键区分（这才是判据盯行号的原因）**：evidence 是 `code_text` + `line_start/line_end`
**同一时刻一起快照**的（`evidence-mapper.ts` **不回读磁盘**）⇒ 两种失效：
- **内容旧**（探针 B）：区间仍对，跳转落点正确，只是文本是改前的 ⇒ **信息过时，可容忍**
- **位置错**（探针 C）：区间指到别处，**跳过去是别的代码，而系统把它当证据给你** ⇒ **错误信息，不可容忍**

**坐标无法局部修**（插入点之后所有条目都受影响，实体层没有 offset 平移路径）
⇒「行号有没有动」≡「地图还能不能用」≡「要不要重建」。

已写入 skill `codelens-deploy` §12.0.1 与 `TECHNICAL-NOTES.md` §18.1。

## 第 13 轮：「如果我不需要行号，能不能实现增量索引」——**能，而且积木已经全在**

**先纠正前提**：行号**不是**增量的代价。正确增量会重新解析改动文件 ⇒ **行号天然正确**。
现在行号错是因为实现**根本没重新解析那个文件**（只删重插 chunk，实体层不动）——
是「没更新」，不是「增量必然错」。⇒ **"不要行号"只消掉 5 项失效里的 1 项**：

| 现在的增量会坏什么 | 依赖行号吗 |
|---|---|
| 跳转落到错误行 | ✅ 只有这一项 |
| 新增的函数/类**根本不在索引里** | ❌ 缺条目 |
| 调用边被 CASCADE 删且不重建 | ❌ |
| `import_relations` / `file_dependencies` 过期 | ❌ |
| 实体层向量不更新 | ❌ |

**关键核实（本轮最有价值的发现）**：`EnhancedIndexer.indexFileWith(parser, repoId, fileId, path, content)`
**本身就是逐文件的**，四步全做：`analyzeEntities` → `storeEntities` → `buildRelationships` →
`generateEmbeddings`。它是 `private`，**只被 `indexFiles` 的批次循环调用，增量路径从未调用它**。
⇒ **做真增量的积木已齐，只差接一根线。**

**三条真实约束**（都是「顺序 / 全仓视野」，不是「不可能」）：
1. import 边写入时就要解析 `imported_file_id` ⇒ 新增/改动文件必须**先全部写完第一遍**再跑实体；
2. 跨文件符号表（`beginRepo`）必须在任何 `analyzeEntities` 前建立，吃的是**全仓文件内容**（只读取不解析）；
3. `file_dependencies` 是整仓 GROUP BY，只能最后一次性物化。

⇒ 正确形态 = ①写改动文件 → ②读全仓建符号表 → ③逐改动文件 `indexFileWith` → ④整仓物化依赖。
**工作量 ∝ 改动文件数**。详见 `TECHNICAL-NOTES.md` §19、skill §12.7。

### 关键判断（都是「想错会安静地出错」的那种）

- **`--name-status` 的重命名行多一列**（`R100\t旧\t新`）。读反**不抛错**，只会静默删错文件、
  在库里留幽灵。必须靠真实 rename 的探针兜住 —— 而目标仓库最近 29 个提交里一个 rename 都没有，
  所以探针里**自造了一个 origin** 把 A/M/D/R/改名改类型/复制/T 全摆上。
- **快照必须在删除之前抓**：`functions`/`classes`/`string_constants` 都有 `chunk_id CASCADE`，
  删完再抓只剩空快照 ⇒ 删除被漏报成「什么都没发生」。
- **`before`/`after` 两侧文件集必须严格同源**，否则报告会把某个文件的**全部**实体谎报成「新增」。
- **zip 源返回 `200 + supported:false` 而不是 4xx**：这不是错误，是能力边界，界面要展示的是

### ⚠️ `moved` 的语义（差点记错）

## 24. 一个 `.vue` 让 1308 个文件的实体层全部归零（2026-09-19 晚，已修）

### 现场（用户报「构建失败了」）

repo 33 状态 `failed`。**判据 = 「哪一层有数、哪一层是 0」**：
`files` 1051 / `code_chunks` 14084 都正常，但 `functions`、`url_patterns`、`url_usages`、
`call_graph` **全是 0** ⇒ 第一层好、第二层全空 ⇒ 增强索引在**一开始**就死了。
日志 `Indexing 1051 files...` 之后**仅 3 秒**就 failed ⇒ 1308 个文件不可能 3 秒跑完
⇒ 死在**一次性全仓扫描**（`beginRepo`），不是逐文件循环。

### 根因（两个，缺一不可）

1. **`URLResolver.registerFiles` 没有逐文件 try/catch** ⇒ 异常穿过
   `registerRepoFiles` → `RepoScope.begin`，到 `EnhancedIndexer.indexFiles` 才被捕获，
   此时实体表还是空的 ⇒ **一个文件的格式问题 = 整仓检索能力归零（连坐）**。
2. **`.vue` 原文被喂给了 TS 解析器**：`<template>` 的 `@import="onImport"`（模板事件绑定）
   与 `<style>` 的 `.apiwire-...-import {`（CSS 类选择器）被 TS 错误恢复**合成 `ImportDeclaration`**，
   `getModuleSpecifierValue()` 遇到非字符串字面量的合成节点抛
   `InvalidOperationError: Expected the module specifier to be a string literal.`
   4 个元凶全是 `.vue`（行号 32 / 12 / 60 / 69）。
   ⚠️ `sfc-host.ts` 注释写了「**两遍**索引都必须走 `parseVueScriptBlocks`」——
   **漏了第三处**：跨文件符号表这一遍。

### 定位手法（可复用）

写**离线探针重放线上那次调用**逐文件 catch，钉到「文件 + 行号」，而不是读代码猜。
探针自身的坑：`imp.getModuleSpecifier().getKindName()` **也会抛**（同一判据），
在 catch 块里二次抛出会让探针整个崩掉，看起来像「问题是全局的」。
**探针里每一个可能抛的调用都要单独兜。** 现成脚本 `src/scripts/probe-resolver-sfc.ts`。

### 修法

- `url-resolver.ts` `registerFiles`：两遍循环各自逐文件 try/catch，坏文件从 `sources` 摘掉、
  记进 `failed`，末尾汇总 `[URLResolver] 4/1310 个文件未能进入跨文件符号表` + 逐条明细。
  **降级局部化 + 记账**（只 catch 不记账 = 从「连坐」退化成「静默漏掉」，更差）。
- `languages/typescript/index.ts` 新增并导出 `toResolverSource()`：`.vue` 解包 script 块后
  **用空行占位**。⚠️ **不许直接拼接 script 块** —— provider / 间接落点都带行号，
  拼接会让第二块行号整体前移；空行占位让行号与 `.vue` 严格对齐。

### 验证（不做完不能算修好）

- repo 33 A/B：provider 46 → 46（**明细完全一致**）；落点 95 → 96，逐条核对：
  −1 条在 `AutomatedTesting/.../Main.vue:177`（该文件 script 是 48–118 行，177 行**在 `<style>` 里**，
  旧行为凭空编造）；+2 条是真实 `const {...} = context;`（之前整份文件被丢）⇒ **新行为严格更优**。
- **对既有语料逐条中性** ⇒ 不必重建：repo 29（166 个 `.vue`）174→174 / 36→36；
  repo 30 868→868 / 25→25。**省掉两次 20 分钟级重建。**

### 一句话

**一条「按单个文件成立」的假设，被写进「处理整仓」的循环里，而且失败是静默的。**
与第 23 节（压缩产物被 AST 分块放大 160×）是同一个形状。
