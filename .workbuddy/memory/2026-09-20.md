## 28. 「列出全部 386 个接口」为什么答不出来（排查 + 口径失真）

用户提问背景：仓里显示 386 个接口，但问「列出来」时得到「证据中不包含这 386 个接口的清单数据」。

### 定位（全部落在代码上）

- `/ask` 四个分支**全都**只产出 `evidence = top-K`（`ask.ts:49-54`，limit 10）。
- `llm/qa.ts:251` 明写「如果证据不足，明确指出」⇒ 拒答是**按设计工作**。
- `classifyQuery`（`qa.ts:76-120`）8 类里**没有集合/枚举档**，正则不含「列出/全部/所有/一共」，
  所以「列出所有接口」落到 `general`。

- `url_patterns` 全仓只被读一次：`/repos/:id/stats` 的 **COUNT**（`repos.ts:106`）——
  386 这个数就是从这来的，**没有任何路由返回这些行**；前端 `RepoPage.tsx:639` 只渲染数字。

### 结论

**集合类问题（列全部 N）对检索式问答是结构性无解**：top-K 回答「最相似」，不保证「完备」。
调 K、加 rerank、换嵌入模型都不解决。要完备性只能走 SQL/结构化查询。

### 附带发现（更值钱）：386 是虚高的

- `ALL ${promise}` ← `Promise.all(promise)`；`DELETE ${name}` ← `this._map.delete(name)`。
- 还有 MIME 类型（`text/csv`）、静态路径（`testwire/static/pw/api.json`）混入。
- 根因：`entities.ts:962` `extractHTTPMethod` 用 **子串匹配**（`text.includes('DELETE')`）。
- 粗筛含 HTTP 客户端调用的行：**246 / 386**（约 36% 不像真实接口）。

> **教训**：这个数错很久没人发现，因为 **UI 只显示数字、没有明细**。
> 与「计数 == 0 必须显式失败」是同一枚硬币的两面 —— 只暴露汇总值 = 把错误永久隐藏。
> **正确顺序：先修抽取口径，再谈「完整展示」。**

## 35. 推送被 GitHub 阻断 —— 定位与解法（HTTP 443 走不通，SSH over 443 可行）

用户报错：`致命错误：无法访问 'https://github.com/Carpe912/CodeLens.git/'：Recv failure: Connection reset by peer`。

### 35.1 定位过程（关键是区分「代理策略」还是「链路干扰」）

| 探测 | 结果 | 含义 |
|---|---|---|
| `curl --noproxy '*' https://www.baidu.com` | 200 | 本机**有**直连外网能力，不是沙箱断网 |
| `curl --noproxy '*' https://github.com` | **Recv failure: Connection reset by peer** | **与用户报错逐字一致** ⇒ 是他本机链路问题，不是沙箱策略 |
| 走代理 `curl -v https://github.com` | TLS ClientHello 发出后即 `SSL_ERROR_SYSCALL` | **SNI 阻断**的典型特征（重置发生在 ClientHello 之后） |
| `api.github.com` / `codeload.github.com` / `raw.githubusercontent.com` | 200 / 301 / 301 | 只有 `github.com` 这个 SNI 被打，其它子域正常 |
| `nc -z github.com 22` | TCP 成功 | ⚠️ **TCP 连通 ≠ 可用**，别据此下结论 |
| `ssh -T git@github.com`（实际握手） | `kex_exchange_identification: Connection closed by remote host` | 22 端口 TCP 能连、**SSH 协议被切断** ⇒ 22 也不可用 |

**教训：判断「某个端口/域名能不能用」，必须做到协议层（TLS/SSH 握手），`nc -z` 只验证 TCP 三次握手，会给出假阳性。**

### 35.2 根因之一：`~/.ssh/config` 里的 ProxyCommand 指向了一个没在监听的端口

```
Host github.com
    HostName ssh.github.com
    User git
    Port 443
    ProxyCommand nc -X connect -x 127.0.0.1:7890 %h %p   # ← 7890 无监听
```
`lsof` 查过：**127.0.0.1:7890 没有任何进程在听**（大概率是 Clash 没开）。
于是所有走 `git@github.com` 的操作都在 ProxyCommand 一步卡死。
**「配置已经写好了」不等于「能跑」——必须实际验证一次。**

### 35.3 解法（不改个人 SSH 配置，最小侵入）

把 remote 显式指向 443，**绕开**上面那个 Host 块
（`Host github.com` 不会匹配 `ssh.github.com`，所以 ProxyCommand 不生效）：

```bash
git remote set-url origin "ssh://git@ssh.github.com:443/Carpe912/CodeLens.git"
git ls-remote origin        # 验证：拿到 8b1edef refs/heads/main
```

实测 `Hi Carpe912! You've successfully authenticated` —— 本机 `id_rsa` 已在 GitHub 注册。
原地址备份在 `/tmp/origin-url-before.txt`（`https://github.com/Carpe912/CodeLens.git`）。

**另一条路（未采用，供参考）**：启动本地代理（7890）+ 给 git 配 `http.proxy`，
但那样依赖代理进程常驻，不如 SSH/443 稳。

### 35.4 状态（已完成）

- ✅ **已推送**：`git push --force-with-lease origin main` → `+ 8b1edef...1876d8c main -> main (forced update)`
- 远程复核（独立于本地追踪）：`git ls-remote origin` 的 `HEAD` 与 `refs/heads/main` 均为新历史；
  27 条提交、208 文件、**`sk-*` 命中 0**。旧历史 `8b1edef` 在远程已不可达（对象会随时间回收）
- 随后又补了一条 `docs(dev)` 记录提交并**快进推送**（无需 force），本地与远程同步、工作区干净

## 37. 决策记录：agent 那 6 项能力该不该做（**结论：只做 1 项 + 2 个切片**）

用户问「这些功能全实现了会不会提高项目能力」。结论：**会提高，但不是在能力真正短缺的那一层。**
这是一条**否决式**决策记录，面试/立项可以直接用。

### 37.1 判断的支点：瓶颈在数据层，不在编排层（有数据）

| 证据 | 数值 |
|---|---|
| API 代码量分布 | `indexing/` 29.9% + `retrieval/` 22.0% = **51.9%**；`agent/` 仅 **6.0%**（1,640 行 / 27,450 行） |
| URL 检索评测基线 | **37/37 = 100%** |
| 源码侧独立交叉验证召回（§27.3） | 源码 252 处调用点 vs DB 241 行；归一后仅 **9 / 13** 条差异，**逐条看全是基底前缀归属差异，不是真漏** |
| 你自己下的结论（§27.3） | **「召回本来就够，坏在粒度与呈现」** |

⇒ 那 6 项**全在编排层**；而项目剩下没解决的问题是「**粒度不对齐"接口"这个概念**」和
「**除了 COUNT 没有出口**」。**7 项能力一项都修不了这两个问题** —— 反证是：你把出口补上
（`/repos/:id/url-patterns` + MCP），用户的问题就解决了，**没加任何一轮推理**。

### 37.2 逐项判定（✅ 3 / ❌ 4）

- ✅ **跨轮会话记忆 —— 最该做**：它是**产品能力**不是优化，没有它用户问"那它呢/再往下看一层"
  根本无法解析。而且 v2 图的 `PostgresSaver` 已经拿 `sessionId` 当 `thread_id`
  ⇒ **基础设施已在，只差接线 + 开关**。单位成本最低、用户可感知最强。
- ✅ **工具调用的超时/重试/降级 —— 只做这一半**：文档把它塞在 `ToolRegistry` 里；
  注册/发现机制对 5 个工具是过度设计，但"超时取消、失败降级"是**真实的可靠性缺口**。
- ✅ **答案↔证据一致性自检 —— 做最小切片**：代码问答最致命的失败是"证据没覆盖却答得很确定"。
  一条自检有真价值；文档描述的 4 项监控/指标/重规划是过度设计。
- ❌ **多轮推理循环**：v2 图的 `grade→retrieve` 回边就是它，且 `min(maxReasoningRounds, 策略计划长度)` 已封顶
  ⇒ **再加轮次边际递减**，且每轮都乘上延迟与 token 成本。
- ❌ **任务分解与重规划**：现在 `classifyTaskType` 正则分派已覆盖大部分；需先证明存在真"多跳问题"。
- ❌ **完整反思引擎 / 动态工具注册**：过度设计。
- ❌ **学习机制（`agent_lessons`）**：**学不了** —— 需要"答案对不对"的反馈信号，而你没有标注集
  （`interview-prep/10` 自己写了"没有 golden set ⇒ 无法算准确率/召回率/MRR/nDCG"）。规模也不够。
  做出来就是一张 **0 行的表** —— 恰好是本文档警告的「看起来像能力」那种东西。

### 37.3 三个反直觉的判断（"全实现"可能反而变差）

1. **未测量的功能不算能力提高。** 没有 golden set ⇒ 「实现后能力有没有提高」**在当前仪器下不可证**。
   先补测量能力再加功能，否则就是你反复警惕的「数字是自己编的」那一类。
2. **正确性风险单调上升。** 多轮 + 反思 + 重规划 = 更多 LLM 调用 = 更多"证据没支撑但很像真的"答案。
   对开发者工具，**信任 > 聪明**：一次自信的错误答案比三次"我不确定"更伤。
3. **「别让那 7 张表白建」是沉没成本理由，不是用户价值理由。** 而且已落地的 v2 图**绕开了那张 schema**
   （状态落进自己的 `checkpoint*` 表）——按这个逻辑还得先把图改成写 `agent_executions`，纯属为了让表不空。

### 37.4 真正会提高能力的是这 4 件（都不在这份文档里）

1. **粒度**：chunk 对齐「接口/函数」这个概念（已诊断清楚，是真问题）
2. **测量能力**：有标注、能自动重跑的质量闸门（37/37 是**用例集**，不等于线上质量）
3. **索引可信度**：`计数 == 0 必须显式失败`（铁律 2）—— 一次静默整仓归零，破坏力大于任何编排优化
4. **出口**：结构化问题走 SQL（已做）；把"未命中"归因做成例行检查

### 37.5 面试/立项口径（比"我全实现了"强得多）

> 「我有 6 项待实现能力，我判断**只做 1 项**。依据是三组数：编排层只占 6% 代码量而索引+检索占 52%；
> URL 检索用例 37/37 已满分；源码侧交叉验证显示**召回本来就够，坏在粒度与呈现**。
> 所以我否决了多轮推理、反思引擎、学习机制 —— 不是做不出来，是它们修的不是那个问题。
> 而且学习机制需要标注信号，我没有 golden set，做出来只会是一张空表。」
>
> **"我否决了什么、为什么"——这才是 AI 替不了的那部分。**
