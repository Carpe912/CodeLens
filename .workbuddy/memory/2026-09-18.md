# 2026-09-18

## 评估：CodeLens 是否可用 LangChain / LangGraph 改造

对项目做了通读式评估（未改动任何代码），结论：**可以，且 LangGraph 高度适配，但必须增量改造而非重写。**

### 关键事实（已核实）
- 技术栈：pnpm monorepo，apps/api（Fastify 5 + TS，约 18k 行）、apps/web（React）、apps/vscode-extension
- LLM：直接使用 `@anthropic-ai/sdk`，模型 `claude-sonnet-4-6`；Embedding 走 DashScope text-embedding-v4，1536 维，pgvector HNSW
- 检索层是真实资产，务必保留：multi-strategy-search.ts(1160) + url-search.ts(912) + url-derivation.ts(1571) + url-template-matcher.ts(338)，合计约 4000 行手写混合检索
- `src/agent/` 约 1600 行，其中 5 个类是空壳：`TaskPlanner` / `ReasoningEngine` / `ConversationMemory` / `ReflectionEngine` / `ToolRegistry` 全部为 `export class X {}`，体积由 JSDoc 设计文档撑起
- `agent-core.ts` 实际是线性 3 步：`classifyTaskType`(正则) → `gatherEvidence`(1 次搜索 slice 5) → `generateAnswer`(1 次 LLM)
- `agent-core.ts` 硬编码失真字段：`confidence: 0.85`、`reasoning: []`、`stepsExecuted: 1`、`toolsCalled: ['vector_search']`、`reflections: 0`
- `agent/config.ts` 的 `maxReasoningRounds: 5`、`enableReflection`、`enableLearning` 从未被任何代码读取
- 文档 `AGENTRAG_UPGRADE.md` 宣称"多轮推理引擎（最多 5 轮）+ 自我反思"，与代码行为（1 轮、0 反思）不符

### 4 套并存的意图分类器（术语互不兼容）
| 位置 | 分类数 | 机制 |
|---|---|---|
| `llm/qa.ts:79 classifyQuery` | 8 类 QueryType | 正则 |
| `agent/agent-core.ts:192 classifyTaskType` | 4 类 TaskType | 正则 |
| `llm/query-intent-parser.ts:70` | 5 种 action | 正则 |
| `llm/multi-strategy-search.ts analyzeQueryIntent` | 5 类 intent | 正则 |

agent 层完全无视 qa 层的分类结果。

### 数据库现状
- 基础表在 `src/db/index.ts` 内联创建；增强表在 `migrations/001-003`
- `src/db/migrations/add_agent_tables.sql` 已定义 6 表 + 1 视图 + 2 函数：`agent_conversations`、`agent_executions(plan,steps,result,confidence)`、`agent_lessons`、`conversation_memory`、`tool_calls`、`agent_reflections(round,on_track,needs_replan)`
- **这 5 张表零代码引用**，只有 `agent_conversations` 被 agent-core 写入。该 schema 的语义几乎就是 LangGraph 状态机，属"已设计未实现"
- `/agent/query` 接收 sessionId 并写库，但 `run()` 从不读回历史 → 会话实际是"只写不读"的无状态单轮

### 其他问题
- `/ask` 路由 `index.ts:1254-1322` 有 4 路 strategy 分支，含 4 段近乎重复的 result→evidence 映射
- 同一"检索→回答"有 3 个入口（`/ask`、`/root-cause`、`/agent/query`）共 5 条代码路径
- 全仓无流式：`qa.ts` 用阻塞式 `messages.create`，无 `text/event-stream`

### 版本核实（2026-09 实测）
- `@langchain/langgraph` 1.4.x；`@langchain/langgraph-checkpoint-postgres` 1.0.5（2026-08-19），Node>=18，peer `@langchain/core ^1.1.44`
- `PostgresSaver` 可直接复用现有 `pg.Pool` → 持久化零迁移成本
- `setEntryPoint`/`setFinishPoint` 已废弃，须用 `addEdge(START, ...)` / `addEdge(..., END)`
- zod 当前不是依赖，若用 `withStructuredOutput` 需新增

### 建议结论
- **LangGraph**：用于填实 `src/agent/` 空壳，承载状态机、多轮循环、反思、工具调用、状态持久化、SSE
- **LangChain**：仅取模型封装（结构化输出 + streaming）与 tracing；**禁止**替换 MultiStrategySearch / AST 分块 / 索引器，那会让项目失去真实壁垒
- 落地顺序：Phase 0 先修文档与硬编码失真 → Phase 1 单节点图等价替换 → Phase 2 加循环与反思 → Phase 3 流式与多轮会话

## 拓展方向调研：代码图的「半成品」现状（重要发现）

用户问「项目功能单一，怎么拓展」。核对代码后发现：**不是功能单一，是索引能力远超产品化程度**——已建了半张知识图谱，却只暴露了 `/search` + `/ask` 两个出口。

### 真实数据（源码出现次数）
`code_chunks` 110 · `string_constants` 48 · `call_graph` 30 · `url_patterns` 29 · `import_relations` 21 · `constant_references` 14 · `question_feedback` 9 · `url_usages` 7 · **`file_dependencies` 4** · **`search_logs` 3**

### 三个确凿的「坏账」
1. **`file_dependencies` 从未被写入**：全仓库只有 2 处 `DELETE`、1 处注释、1 行 migrate 日志——**没有任何 INSERT/SELECT**。schema 承诺的「file-level dependency graph」**根本不存在**，所以跨文件影响分析无从谈起。
2. **`search_logs` 从未被写入**：同样只被 DELETE，无 INSERT/SELECT。所谓「search analytics」不采集任何数据。
3. **`findCallChain`（`db/index.ts:847-893`）是死代码 + 坏查询**：查询用了 `caller_chunk_id / callee_chunk_id / caller_name / callee_name` 四个**不存在的列**（真实列是 `from_chunk_id / to_symbol`，migration 001 只额外加了 `call_type / arguments / call_line`）。而且**零调用点**——一旦有人调用就会 `column does not exist`。它本来是想做递归深度遍历的。

### call_graph 的真实形态（既是现状也是瓶颈）
真实列：`from_chunk_id`(调用者 chunk, 有外键) + `to_symbol`(被调用者**符号名字符串**, 无外键) + `call_type/arguments/call_line`。
- 正向：`WHERE cg.from_chunk_id = $1` → `to_symbol`
- 反向：`WHERE cg.to_symbol = $1`（**只 1 跳**，无传递闭包）
- **`to_symbol` 是名字不是实体** → 同名符号跨文件歧义；`LEFT JOIN code_chunks c2 ON c2.symbol_name = cg.to_symbol` 在同名多 chunk 时会**笛卡尔放大**
- 所以：**符号消解（name → chunk/entity）是所有图分析（影响面/死代码/架构体检）的前提**

### 答复给用户的拓展思路（已给出优先级矩阵）
- 立即做（数据已在库）：MCP server、死代码/未用导出检测、影响面分析（1 跳）
- 规划做：符号消解、PR 审查/变更影响、评测体系（golden set）

## 定位评估：这个项目到底为谁而建（用户提问 + 我的核查）

### 证据一：索引构成（线上 codelens 库实测，repoId=29）

| string_constants | 760 |
| url_patterns | 65 |

### 证据二：模块自述
`retrieval/url-search.ts`（912 行）头部注释直接写着：
「1. 意图识别：自动识别用户是要查找**定义**还是**使用位置**」「5. 使用位置搜索：查找 URL 在代码中的调用位置」。

  它把提问里的 URL **只当成「符号名提示」**：取路径末段去 `code_chunks.symbol_name` 查定义。
  → 这就是今天那个 URL 例子降级成 level:'file' 的根因：URL 被当成函数名查，自然查不到。
- `searchURLUsages` 的实现是 `code_text ILIKE '%段%'` 的文本匹配 + 打分（整串命中 0.95），

- 用户直觉成立：项目的重心就是 API 溯源。

## 跨边界「接口 → 调用点」断链根因（test-repo 实测，2026-09-18 深夜）

用户选择「先入库真实仓库 + 接通 URL 链路」，随后指示用 `remote-project/test-repo` 当例子（省 token）。
本地 test-repo 与线上 repoId=29 的 14 个文件路径完全一致，可直接当样本。

### 关键发现 1：跨边界的边表早就设计好了，而且有数据
`url_usages` 存在且 repo 29 有 **445 行**，`usage_context` 已区分两侧：
`route_definition 322 / api_call 105 / router 4 / unknown 14`。
字段：id, repo_id, url_pattern_id, usage_file_id, usage_chunk_id, usage_line, usage_code, usage_context, http_method, call_stack, created_at。
→ 设计意图：`url_patterns` = URL 本身（一 URL 一行），`url_usages` = 它出现的所有位置（调用点 / 路由定义）。
   即「接口 → 调用点」这条跨边界边的存储层**已经存在**，不需要新建表。

### 关键发现 2：配对是断的，65 个 URL 里只有 4 个两侧齐全
| 情况 | 个数 |
|---|---|
| 调用点 + 路由定义 都有 | **4** |
| 只有调用点 | 16 |
| 只有路由定义 | 41 |
| 都没有 | 4 |
| 合计 | 65 |
→ 今天只有 **6%（4/65）** 的接口能回答「它在哪里被调用了」。

### 关键发现 3：根因是唯一索引漏了 method + 定义位置（已用 rollback 事务实证）
```sql
CREATE UNIQUE INDEX idx_url_patterns_unique ON url_patterns (repo_id, pattern);
```
- 只有 `(repo_id, 原始 pattern)`，**没有 method、没有 definition_file_id/line**。
- `relationship-builder.ts` 的 `buildURLUsages()`（约 468-560 行）先按
  `(repo_id, normalized_pattern, method)` SELECT，命中就复用 patternId；未命中才 INSERT，
  而该 INSERT **没有 ON CONFLICT**，且整个循环体包在 `try {} catch {}` 里 → 唯一冲突被**静默吞掉**。
- 实证：在事务里插 `GET /api/users/:id`（userRoutes.js L15 真实存在的路由）→
  `duplicate key ... Key (repo_id, pattern)=(29, /api/users/:id) already exists`
  （已存在的那行是 L27 的 **PUT**，因为 PUT 与 GET 共用同一原始路径字符串）。
- 后果：`GET /api/users/:id` 既不在 url_patterns 也不在 url_usages → 该接口的「谁调用了它」永远查不出来。
  同批被吞掉的还有 `POST /api/users`（与 GET 撞）、`DELETE /api/users/:id`（与 PUT 撞）等。

### 关键发现 4：string_constants 只收「声明的常量」，不收内联实参
`this.client.get('/api/users')` 这种内联参数字符串**没有**进 string_constants（该表只索引 `const X = '...'`）。
所以 `url_patterns` / `url_usages` 才是调用点的唯一来源，不能指望 string_constants 兜底。

2. 代码：`relationship-builder.ts:498` 的 INSERT 加 `ON CONFLICT ... DO UPDATE`，

3. 重建：`node apps/api/dist/scripts/reindex.js 29 <repoPath>`（需先把源码传到服务器，
   约定路径 `/tmp/codelens-repos/<id>`；服务器上目前**没有** test-repo 源码）。
   ⚠️ reindex 会先 DELETE url_patterns / url_usages / functions / classes / string_constants / call_graph / import_relations / file_dependencies，
