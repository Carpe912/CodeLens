# 14 - 索引质量排查：五处「静默丢数据」与它们的判定口径

> 承接 `13-索引崩溃排查`。13 讲的是**炸掉的**索引（整仓归零 / 撑爆数据库）。
> 这一篇讲更阴的一类：**索引看起来完全正常，但库里少了东西，而且没有任何报错。**
>
> 全部实测于 repo 33（`testwire-frontend`，真实 GitLab 前端工程）：
> 守卫后语料 1308 个文件、14395 个代码块、4468 个函数实体。
> 文中每个数字都有可复现的取数命令，见 §六。

---

## 零、一句话结论

> 一个「当前提失效时它只是安静地少做一点事」的分支，比一个「直接崩掉」的分支危险得多 ——
> 因为崩溃会把人叫过来，而安静地少做只会把排查引到错误的方向。

这次排查的五个问题**全是这一类**，而且它们叠加在一起，制造了一个极具误导性的现象：
仓库页显示 1051 个文件，实际扫到 1308 个 —— 差 257。

---

## 一、入口：一个「文件数对不上」的观察

### 1.1 现象

repo 33 重建完成后，各层统计看起来健康：

| 层 | 数量 |
|---|---|
| `files` | 1051 |
| `code_chunks` | 14084 |
| `functions` | 4468 |
| `url_patterns` | 383 |
| `url_usages` | 629 |
| NULL 向量 | 0 |

但把「扫描器认为该索引的文件」和「`files` 表里真实存在的文件」两个清单做 `comm`：

```bash
node -e "import('/root/CodeLens/apps/api/dist/indexing/file-scanner.js').then(async m=>{
  const {files}=await m.scanRepoFiles('/tmp/codelens-repos/33');
  console.log(files.join('\n'))})" | sort > /tmp/scan_paths.txt

psql -tAc "SELECT path FROM files WHERE repo_id=33" | sort > /tmp/db_paths.txt

comm -23 /tmp/scan_paths.txt /tmp/db_paths.txt | wc -l   # → 257
```

**257 个文件凭空消失**，而且日志里一行报错都没有。

### 1.2 第一步不是修，是**分类**

257 个缺口按扩展名和路径形态拆开：

| 形态 | 数量 | 例子 |
|---|---|---|
| barrel 文件（`index.ts` 只做转出） | 218 | `src/.../index.ts` → `import Main from './Main.vue'; export default Main;` |
| `*.d.ts` | 7 | `auto-imports.d.ts` |
| 纯枚举文件 | 25 | `src/enum/HttpMethod.ts` |
| i18n 字典 | 4 | `vcrontab/language/{cn,en,pt_br}.js` |
| **真源码（必须单独看）** | 3+ | `utils/MessageBox.ts`、5 个 `.vue` 组件、`eumn.ts`（**216 行**） |

分类这一步决定了后面所有事情的对错。如果只看「barrel 文件不产代码块是合理的」就收工，
就会漏掉第三行那两个真正的缺陷（§二、§三）。

### 1.3 用探针把「猜测」变成「数字」

我写了一个只读探针，把「某个文件到底解析出几个代码块」直接打出来：

```js
// /tmp/probe-zero-chunk.mjs（只读，不连数据库）
import { readFile } from 'node:fs/promises';
import { languageRegistry } from '.../dist/indexing/languages/registry.js';

const parser = languageRegistry.forFile(abs);
const n = parser.parseChunks(abs, content).chunks.length;
console.log(`${n} chunks | ${content.split('\n').length} 行 | ${parser.id} | ${rel}`);
```

结果立刻分成两堆，**这是整个排查的转折点**：

```
    0 chunks |   27 行 | typescript | src/enum/HttpMethod.ts
    0 chunks |   17 行 | typescript | src/enum/TreeSelectionSelectedState.ts
    0 chunks |  216 行 | typescript | src/components/.../eumn.ts      ← 216 行，0 chunk
    0 chunks |    4 行 | typescript | src/utils/MessageBox.ts
    0 chunks |   42 行 | vue        | .../Auth/Main.vue              ← 真组件，0 chunk
    0 chunks |   39 行 | vue        | .../MenuWrapper/Aside/Header.vue
    0 chunks |   11 行 | vue        | .../PublicSetting/ExportData/Main.vue
```

**「216 行的文件产出 0 个代码块」不可能是正常行为。** 那不是「这个文件没有可索引的东西」，
那是「解析器不认识这个文件里的东西」。

## 二、缺陷一：`enum` 声明没有任何 visitor

### 2.1 根因

分块器（`languages/typescript/chunker.ts`，基于 `@babel/parser` + `@babel/traverse`）
的 visitor 表里有 `FunctionDeclaration` / `ClassDeclaration` / `VariableDeclaration` /
`TSInterfaceDeclaration` / `TSTypeAliasDeclaration` / `ObjectMethod` / `ClassMethod` ——
**唯独没有 `TSEnumDeclaration`**。

而 `enum Foo { A = 'a' }` 在 AST 里既不是变量声明也不是类声明，
**三种 visitor 一个都不匹配** ⇒ `chunks` 为空。

### 2.2 为什么这个缺陷在这里特别致命

`enum` 恰好是这个工程里**最该被搜到的东西**：

```ts
// src/enum/HttpMethod.ts（全文 27 行，就这一件事）
export enum HttpMethod { GET = 'GET', POST = 'POST', ... }
```

读一个不熟悉的工程时，「这个值域的合法取值有哪些」「这个字段的枚举定义在哪」
是第一落点，也正是代码问答系统最该答对的问题。而它在索引里**整份不存在**。

连带还有一个更细的缺陷：`ExportNamedDeclaration` 的 visitor 只把
函数 / 类 / 变量收进 `exports`，**interface / type / enum 三种 TS 声明从不出现在导出列表里** ——
于是「这个符号被哪个文件导出」这条信息对类型层符号全部缺失。

### 2.3 修复

```ts
// languages/typescript/chunker.ts —— 与 interface / type 同粒度：一个声明产一条块
TSEnumDeclaration(path: NodePath<t.TSEnumDeclaration>) {
  const node = path.node;
  if (!node.id || !node.loc) return;
  chunks.push({
    symbolName: node.id.name,
    symbolType: 'enum',
    lineStart: node.loc.start.line,
    lineEnd: node.loc.end.line,
    code: code.split('\n').slice(node.loc.start.line - 1, node.loc.end.line).join('\n'),
    filePath, imports: [], exports: [], calls: [],
  });
},
```

`symbolType` 新增 `'enum'`。**这个值能不能加，是被核查过的，不是随手写的**：

- 数据库侧 `code_chunks.symbol_type` 是 `TEXT` 且**无 CHECK 约束** ⇒ 加值不需要迁移；
- 代码侧只有一处**枚举式**消费（前端 `SYMBOL_TYPE_STYLE` 徽章配色），它有 `unknown` 兜底
  ⇒ 加值最多是「徽章变灰」，不会报错。

实测：**本语料 +54 个 enum 块，其中 20 个文件由此从「完全不可见」变成有内容，
33 个文件在原有块之上补上了枚举块。**

## 三、缺陷二：`chunks.length === 0` 就静默跳过

### 3.1 根因

```ts
// indexing/indexer.ts（修前）
const parseResult = parser.parseChunks(filePath, content);

// 如果解析不出代码块，跳过该文件
if (parseResult.chunks.length === 0) {
  processedCount++;
  continue;              // ← 不落 files 表、不打日志、不计数
}

const fileId = await insertFile(repoId, relativePath, parser.id, content);
```

**「解析不出代码块」被当成了「这个文件不需要入库」。** 这两件事完全不同：
前者是**能力的边界**，后者是**结论** —— 而能力边界不该由被能力限制的那个组件自己下结论。

后果有三层，一层比一层难查（这是这一节真正的价值）：

1. **仓库页的文件数偏小**（1051 vs 1308）。这个现象最容易被误判成
   「扫描器或守卫有问题」，而真正的原因在入库侧。
2. **依赖图在这些节点上断链。** 这些文件在 `files` 表里没有行 ⇒ 指向它们的
   `import` 边没有落点。而 218 个 barrel 文件恰恰是**目录入口**，
   是最多 import 指向的地方。
3. **内容完全不可检索。** `PublicSetting/ExportData/Main.vue` 的全部内容是
   `<div>高级设置</div>`。搜「高级设置」—— 一个再正常不过的诉求 ——
   在任何检索模式下都返回不了它，因为它**根本不在库里**。

### 3.2 修复：不是「登记一行」，而是「给每个文件一个可检索的块」

最省事的修法是「0 chunk 也写 `files` 行」。但那只解决第 1 层，
第 2、3 层照样是坏的：文件在库里，但内容仍然进不了向量库。

真正的修法是在**语言适配层**加「整文件兜底块」：

```ts
// languages/typescript/index.ts
const MAX_MODULE_FALLBACK_BYTES = 8_000;   // 注意是字节，不是字符

const parseWithFallback = (filePath, code, language, parse) => {
  const result = parse(filePath, code);
  const chunks = result.chunks.length > 0
    ? result.chunks
    : [makeModuleFallbackChunk(filePath, code)];   // 兜底
  return { ...result, chunks: chunks.map((c) => ({ ...c, language })) };
};
```

三条设计决定，每条都有理由：

1. **兜底块 `symbolType: 'module'`，不伪装成函数。** 下标侧一眼能分辨
   「这条不是符号命中，是整文件命中」，检索层不会被污染的符号类型骗到。
2. **必须按字节判上限，不能按字符。** 本仓中文注释 3 字节/字符，
   「8000 字符」在中文语料下是 24000 字节。这类「字符 vs 字节」的坑
   在这个项目里出现过两次（另一次见 §五）。
3. **兜底放在适配层、两个解析器共用同一个包装函数。** 分散写就一定会漏一个 ——
   而这个项目的历史恰好证明了这一点：`.vue` 的「必须解包 SFC」这条规则，
   第一遍和第二遍都做了，**第三遍（跨文件符号表）被漏了整整一轮**（见文档 13）。

同时把 `indexer.ts` 里那个 `continue` 改成**防御性告警**（兜底生效后它不该再触发）：

```ts
if (parseResult.chunks.length === 0) {
  console.warn(
    `[indexer] ${filePath}：适配层未能抽出任何代码块，也没有提供整文件兜底块 → 该文件不会入库。` +
      `请检查 languages/${parser.id}/ 的 parseChunks 是否走了「空结果兜底」。`
  );
  zeroChunkFiles++;
  ...
}
```

这才是正确的分工：**组件只报告「我这层没产出」，由上层决定这是不是问题。**

## 四、缺陷三 & 四：实体层的两次「整文件回滚」

这两个问题的表现形式和 §二/§三 完全不同 —— 它们**发生在第二遍（实体层）**，
而第一遍（`code_chunks`）是正常的。于是出现一种很怪的状态：

> 文件在库里、能搜到、有向量，但 `functions` / `classes` / `string_constants` 里一条都没有。

### 4.1 根因 A：`functions.return_type` 是 `VARCHAR(255)`

第二遍存的是 **ts-morph 推断出来的**返回类型，而 Vue 组合式函数的返回值是结构化类型：

```
{ name: string; props: string[]; setup: ({ context }: { context: import("...") }) => ... }
```

实测全库最长 241 字符，**失败的那批超过了 255**：

```
✗ Error indexing src/components/Api/ApiGroup/Component/ApiTable/useContext.ts:
  error: value too long for type character varying(255)
```

⚠️ **真正的伤害不在「这一列写不进去」，而在它所在的写入是事务**：

```ts
// indexing/enhanced-indexer.ts  storeEntities()
await this.db.query('BEGIN');
try {
  for (const constant of astResult.stringConstants) { await insert... }
  for (const func of astResult.functions)        { await insert... }   // ← 这里抛
  for (const cls of astResult.classes)           { await insert... }
  await this.db.query('COMMIT');
} catch (error) {
  await this.db.query('ROLLBACK');   // ← 一个字段超长，三张表的写入全部作废
  throw error;
}
```

结果：**该文件在实体层整体消失**，日志只留一行。

影响面高度雷同 —— 24 个文件全部是 **Vue 组合式函数**（返回一个大对象字面量）
或**类型定义密集的文件**：`useContext.ts` / `useTabsContext.ts` / `useTree.ts` /
`useDrag.ts` / `useApiRun.ts` / `model/Interface/BaseForm.ts` …

**修复：`VARCHAR(255)` → `TEXT`**（`migrations/005_widen_function_return_type.sql`）。

为什么不是「截断到 255」：截断后得到的是**语法非法的半截类型表达式**
（`{ name: string; props: stri`），比没有更误导。而这一列不参与任何唯一键或等值比较
（索引建在 `name` / `full_name` 上），放宽为 `TEXT` 零成本。

### 4.2 根因 B：超长字符串常量撑爆 btree 唯一索引

同一张事务里还有另一颗雷：

```
✗ Error indexing web/open/index.js:
  error: index row requires 8520 bytes, maximum size is 8191
```

这条报错的措辞和上一条完全不同，值得单独解释：**它不是列宽问题，是索引问题。**

`idx_string_constants_unique` 建在 `(repo_id, file_id, string_value, line_start)` 上，
是 **btree** 索引；而 PostgreSQL 的 btree **单条索引项上限约 2704 字节**
（8 KB 页扣掉页头与行指针后每页可用空间的 1/3），多列合计的报错阈值是 8191 字节。

一个 8 KB 的字符串字面量（打包产物里的内联数据 blob / base64）就能让它整条 INSERT 失败
⇒ 又回到 §4.1 的事务回滚 ⇒ **整份文件从实体层消失**。

**修复：入库前按字节设上限，超限的跳过并记账**（`entities.ts`）：

```ts
const MAX_STRING_CONSTANT_BYTES = 2_000;   // 留足余量（btree 约 2704）

export function isIndexableStringConstant(value: string): boolean {
  return Buffer.byteLength(value, 'utf8') <= MAX_STRING_CONSTANT_BYTES;
}
```

同样是**跳过而不是截断**，理由和 §4.1 一样 —— 截断会留下一个**看起来合法的假常量值**。
而这些超长值本来也不是「字符串常量」（它们是数据），真正的 API 路径 / 错误码 /
事件名都在几十字节量级。

⚠️ 这三个抽取点（变量声明 / 对象属性 / 枚举成员）用的是同一个判据函数，
**不是复制三份 if** —— 复制三份就必然有一天只改了其中两份。

### 4.3 这两个问题暴露的通用教训

> **VARCHAR(n) 在事务里等于「整行数据的单点故障」。**
> 任何「描述性元数据」列都不该用窄 `VARCHAR` —— 它不参与约束，
> 却能在溢出时把**同一事务里其他无关的写入**一起带走。

同一类风险仍在别处（`functions.name` / `classes.name` / `classes.extends_class` /
`string_constants.symbol_name` / `parent_object` 仍是 `VARCHAR(255)`）——
但判断依据必须是**实测**：全库这几列当前最大 48 字符，所以本次不动。
**「实测过」和「不可能」是两句话。**

## 五、缺陷五：`git clone` 到已存在的目录 → 状态被误写成 `failed`

### 5.1 现象：数据是好的，状态是错的

```
=== repos ===
33 | testwire-frontend | failed | 1051 files
=== repo33 layers ===
1051 | 14084 | 4468 | 383 | 629      ← 各层数据齐全
```

但错误日志里躺着：

```
Index job 64 failed: Error: Command failed:
  git clone https://leon.sun%40...:****@gitlab.logwire.cn/coopwire/testwire-frontend.git /tmp/codelens-repos/33
```

根因：`/tmp/codelens-repos/33` 已存在（上一个 job 刚用过），
`git clone` 到**非空目录**会直接失败。而这个失败发生在**索引本身已经成功之后**，
它把一个 `ready` 的仓库覆写成了 `failed`。

**「状态是错的、数据是好的」比明确失败更难判断** —— 它会让人去重建一个本来完好的索引。

### 5.2 修复与顺带发现的安全问题

```ts
// ① clone 前先清目标目录
await rm(targetDir, { recursive: true, force: true });

// ② 失败信息必须脱敏
try {
  await execFileAsync('git', ['clone', cloneUrl, targetDir], { maxBuffer: 16 * 1024 * 1024 });
} catch (error) {
  const raw = error instanceof Error ? error.message : String(error);
  const redactedUrl = cloneUrl === url ? url : cloneUrl.replace('//', '//***:***@');
  throw new Error(`git clone 失败（凭据已脱敏）：${raw.split(cloneUrl).join(redactedUrl)}`);
}
```

第 ② 条是排查中发现的**独立安全问题**：`git` 的失败信息会把命令原文回显，
而 `cloneUrl` 里嵌着 `用户名:密码`（凭据由用户在仓库配置里以 `用户名:密码` 形态提供）——
**明文密码进了 `codelens-api-error.log`**。日志是要给人看、还经常被贴出来的东西，
凭据不能躺在里面。

## 六、验证：A/B 对照，并且证明「不是靠塞东西换来的」

### 6.1 为什么必须有 A/B

改解析器最忌讳的验证方式是「新版本 chunk 更多 ⇒ 改对了」。
**chunk 变多什么都证明不了**：往任何地方多塞点块都能让数字变大。
真正要回答的是两个**可能让改动作废**的问题：

- **A. 有没有文件在旧版本有 chunk、新版本反而没了？**（回归）
- **B. 有没有文件两版都是 0 chunk？**（兜底失效）

### 6.2 探针

只读、不连数据库，把新旧两版 dist 同时 import 进来，在同一份语料上逐文件比对：

```js
const oldMod = await import('/root/CodeLens/apps/api/dist.ab-before/indexing/languages/typescript/index.js');
const newMod = await import('/root/CodeLens/apps/api/dist/indexing/languages/typescript/index.js');
// 逐文件跑两版 parseChunks，按 symbolType:symbolName:lineStart-lineEnd 做签名比对
```

### 6.3 结果（repo 33，1308 个文件）

| 指标 | 结果 |
|---|---|
| chunk 总数 | 14084 → **14395**（+311） |
| 逐文件产出完全相同 | 1018 |
| **从 0 chunk 变为非 0** | **257**（整文件兜底 237 + enum 20） |
| **原有 chunk 上新增** | **33**（全部来自新增的 enum 块） |
| 两版都为 0 chunk | **0** ✓ 兜底覆盖全部 |
| 旧有条目被替换/丢失 | **0** ✓ 无回归 |
| 自洽校验 | 1018 + 257 + 33 + 0 + 0 = **1308** ✓ |

> 另外做了一次交叉验证：把「旧解析器产出 0 chunk 的文件清单」与
> 「`files` 表缺失的文件清单」做双向 `comm`，**两侧差集都是空**。
> 这证明「文件数少了 257」与「解析器产出 0 chunk 的 257 个文件」是**同一个集合** ——
> 排除了「还有第二个原因也在丢文件」的可能。

## 七、五处缺陷的共同结构（这是真正的面试答案）

| # | 缺陷 | 失效方式 | 谁该发现它 |
|---|---|---|---|
| 1 | `enum` 无 visitor | 整份文件 0 chunk | 解析器自己（能力边界） |
| 2 | `0 chunk ⇒ continue` | 不落库、不报警 | **调用方**（不该由被限制的组件下结论） |
| 3 | `return_type` 窄列 | 事务回滚、实体层整份消失 | schema 与写入方 |
| 4 | 超长常量 vs btree 上限 | 同上（同一个事务） | 写入方 |
| 5 | clone 到非空目录 | **状态**被写错（数据没错） | 任务编排层 |

**共同结构只有一句话：当前提失效时，它只是安静地少做一点事。**

三个我认为可以写进任何项目的原则：

1. **能力边界与业务结论必须分开。** 解析器只能报告「我这层没抽出东西」，
   不能替上层决定「那这个文件就不用入库了」。
2. **「预期的跳过」也要计数并汇总。** 237 个 barrel/纯模板文件走兜底是**正常行为**，
   但不汇总就没人知道差额去哪了 —— 于是排查方向被引到扫描器上去。
3. **一个字段的宽度不该能带走一整个文件的实体层。** `VARCHAR(n)` 在事务里
   就是「整行数据的单点故障」；描述性元数据一律用 `TEXT`。

## 八、面试怎么讲

### 8.1 90 秒口述稿

> 有一次我发现仓库页显示 1051 个文件，但扫描器认为该索引 1308 个 —— 差 257，而日志里一行报错都没有。
>
> 我没有直接去改，先把 257 个文件按形态分类：218 个 barrel 文件、7 个 `.d.ts`、
> 25 个纯枚举文件，还有一些真源码。分类之后我写了个只读探针，直接打印每个文件解析出几个代码块。
> 结果里有一个 **216 行的文件产出 0 个代码块** —— 这不可能是正常行为。
>
> 顺着查下去是两组问题。第一组在解析器：`enum` 声明**根本没有对应的 visitor**，
> 所以纯枚举文件整份消失；同时 `0 chunk` 的处理是**静默 continue**，
> 文件既不落库也不报警。第二组在实体层：`functions.return_type` 是 `VARCHAR(255)`，
> 而 Vue 组合式函数的推断返回类型有好几百字符，超长让 `storeEntities` 的整个事务回滚 ⇒
> 那个文件在 `functions`/`classes`/`string_constants` 三张表里一条都没有；
> 同一个事务里还有一颗雷是超长字符串常量撑爆了 btree 唯一索引。
>
> 修法是：补 `enum` visitor；在语言适配层加「整文件兜底块」保证每个入库文件至少有一条可检索的 chunk；
> 把 `return_type` 放宽成 `TEXT`；超长常量按字节设上限跳过并记账。
>
> 验证时我特意没有用「chunk 变多了」当证据 —— 那什么都证明不了。我做了 A/B 对照，
> 只回答两个问题：有没有旧有条目被替换掉、有没有文件两版都是空的。结果是
> 257 个文件从 0 恢复、33 个文件补上了枚举块、**0 回归、0 漏网**，
> 分类计数加起来正好回到 1308，能自洽。

### 8.2 高频追问与应答要点

| 追问 | 应答要点 |
|---|---|
| 「为什么 barrel 文件 0 chunk 是合理的，enum 不是？」 | 判据不是「文件大小」而是「**这份内容里有没有该被检索到的代码结构**」。barrel 只有转出语句，没有独立语义；`enum` 是值域定义，是读代码的第一落点。 |
| 「整文件兜底会不会污染检索？」 | 会，所以它 `symbolType: 'module'` 单独标记，不伪装成函数；并且有 8 KB 字节上限，不会把整个文件灌进向量。 |
| 「为什么不截断超长字符串，偏要丢掉？」 | 截断会留下**看起来合法的假值**，之后回答问题会答出一段截断的乱码 —— 比查不到更危险。这类值本来也不是字符串常量，是打包数据。 |
| 「怎么保证兜底块不引入退化？」 | A/B 对照，判据是「有没有条目被替换」而不是「总数变多」。 |
| 「`VARCHAR` 改 `TEXT` 有性能影响吗？」 | 该列无索引、无唯一约束、无等值比较；PostgreSQL 里 `VARCHAR(n)` 与 `TEXT` 的存储完全一样，长度约束只是检查。 |
| 「怎么确认没有第二处也在丢文件？」 | 交叉验证：`comm` 双向差集都是空 —— 「0 chunk 的文件集」与「`files` 缺失的文件集」完全重合。 |

### 8.3 ⚠️ 口径红线（说了会被抓）

- **不要**把这次修复说成「检索准确率提升了多少」。本次**没有**重跑评测集，
  能说的只有：**257 个文件从「不在库里」变成「可检索」、代码块 +311（+2.2%）、
  0 回归**。「文件可检索」是**结构性事实**，「答得更准」是**需要评测才能下的结论**。
- **不要**说「所有文件的实体层都完整了」。修的是**已知的两类**溢出原因
  （窄列 + btree 上限）；`functions.name` 等列仍是 `VARCHAR(255)`，
  判断依据是「实测最大 48 字符」，不是「不可能溢出」。
- **不要**把探针数字说成线上测量。A/B 是**离线只读**探针在同一份语料上的对照，
  这与「线上检索日志统计」是两回事。
