## 一、pgvector 删除性能陷阱（最大优化亮点）

### 1.1 问题发现

**场景**：用户点击"重新索引"按钮，需要先删除旧数据再重新索引

**现象**：删除 96K 条 `code_chunks` 记录耗时 **16-19 分钟**，用户体验极差

**初始代码**：
```typescript
// 直接删除（简单粗暴）
await pool.query('DELETE FROM code_chunks WHERE repo_id = $1', [repoId]);
```

**性能测试数据**：
```
测试 1: 96,234 条记录 → 16 分 23 秒
测试 2: 96,234 条记录 → 18 分 47 秒
测试 3: 96,234 条记录 → 17 分 12 秒
平均: 17 分 27 秒
```

### 1.2 性能瓶颈分析

**使用 PostgreSQL 的 EXPLAIN ANALYZE 分析**：

```sql
EXPLAIN ANALYZE DELETE FROM code_chunks WHERE repo_id = 1;

-- 结果：
-- Planning Time: 0.234 ms
-- Execution Time: 1,047,234.567 ms  (17 分钟！)
```

**深入分析发现 4 个瓶颈**：

#### 瓶颈 1：HNSW 向量索引维护

```sql
-- 查看索引
\d code_chunks

-- 索引列表：
-- idx_code_chunks_embedding_hnsw (HNSW 向量索引)
-- idx_code_chunks_file_id (B-tree)
-- idx_code_chunks_repo_id (B-tree)
-- idx_code_chunks_symbol_name (B-tree)
-- idx_code_chunks_line_start (B-tree)
-- ... 共 7 个索引
```

**HNSW 索引的特性**：
- HNSW (Hierarchical Navigable Small World) 是一种图结构
- 删除节点时需要重新连接邻居节点
- 每次删除都要更新图结构，非常耗时

**测试验证**：
```sql
-- 临时删除 HNSW 索引
DROP INDEX idx_code_chunks_embedding_hnsw;

-- 再次删除数据
DELETE FROM code_chunks WHERE repo_id = 1;
-- 时间：3 分 45 秒（提升 4.6 倍！）
```

#### 瓶颈 2：多个 B-tree 索引维护

每次删除一行数据，PostgreSQL 需要：
1. 在主表中标记删除
2. 更新 7 个索引（删除对应的索引项）
3. 更新统计信息

**累积效应**：96K 行 × 7 个索引 = 672K 次索引更新

#### 瓶颈 3：外键级联删除

```sql
-- 外键关系
code_chunks (id) 
  ← constant_references (chunk_id)  -- 约 20K 条
  ← call_graph (from_chunk_id)      -- 约 15K 条
  ← call_graph (to_chunk_id)        -- 约 15K 条
```

每删除一条 `code_chunks`，PostgreSQL 需要：
1. 查找所有引用它的子表记录
2. 级联删除子表记录
3. 更新子表的索引

**累积效应**：96K 行 × 平均 0.5 个引用 = 48K 次级联删除

#### 瓶颈 4：WAL 日志写入

PostgreSQL 的 WAL (Write-Ahead Logging) 机制：
- 每次删除都要写 WAL 日志
- 96K 次删除 = 96K 条 WAL 记录
- 大量的磁盘 I/O

### 1.3 优化方案设计

**核心思路**：先删除索引，再删除数据，最后重建索引

**为什么这样做？**
1. **删除索引**：避免逐行维护索引的开销
2. **批量删除**：PostgreSQL 对批量操作有优化
3. **重建索引**：一次性构建索引比逐行维护快 10+ 倍

**优化后的完整流程**：

```typescript
async function clearRepoData(repoId: number) {
  const client = await pool.connect();
  
  try {
    await client.query('BEGIN');
    
    // ============================================
    // 步骤 1: 删除所有索引和外键约束
    // ============================================
    console.log('Step 1: Dropping indexes...');
    
    // 删除 HNSW 向量索引（最耗时的）
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_embedding_hnsw');
    
    // 删除 B-tree 索引
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_file_id');
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_repo_id');
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_symbol_name');
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_line_start');
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_line_end');
    await client.query('DROP INDEX IF EXISTS idx_code_chunks_symbol_type');
    
    // 删除外键约束（避免级联删除的开销）
    await client.query(`
      ALTER TABLE constant_references 
      DROP CONSTRAINT IF EXISTS fk_constant_references_chunk
    `);
    await client.query(`
      ALTER TABLE call_graph 
      DROP CONSTRAINT IF EXISTS fk_call_graph_from_chunk
    `);
    await client.query(`
      ALTER TABLE call_graph 
      DROP CONSTRAINT IF EXISTS fk_call_graph_to_chunk
    `);
    
    // ============================================
    // 步骤 2: 删除子表数据（避免级联）
    // ============================================
    console.log('Step 2: Deleting child table data...');
    
    // 先获取要删除的 file_id 列表
    const fileResult = await client.query(
      'SELECT id FROM files WHERE repo_id = $1',
      [repoId]
    );
    const fileIds = fileResult.rows.map(r => r.id);
    
    if (fileIds.length === 0) {
      await client.query('COMMIT');
      return;
    }
    
    // 删除 constant_references（引用 code_chunks）
    await client.query(
      'DELETE FROM constant_references WHERE repo_id = $1',
      [repoId]
    );
    
    // 删除 call_graph（引用 code_chunks）
    await client.query(
      'DELETE FROM call_graph WHERE repo_id = $1',
      [repoId]
    );
    
    // 删除 string_constants
    await client.query(
      'DELETE FROM string_constants WHERE repo_id = $1',
      [repoId]
    );
    
    // ============================================
    // 步骤 3: 删除主表数据（无索引，速度极快）
    // ============================================
    console.log('Step 3: Deleting main table data...');
    
    // 使用 ANY 操作符批量删除
    await client.query(
      'DELETE FROM code_chunks WHERE file_id = ANY($1)',
      [fileIds]
    );
    
    // 删除其他表
    await client.query('DELETE FROM functions WHERE repo_id = $1', [repoId]);
    await client.query('DELETE FROM classes WHERE repo_id = $1', [repoId]);
    await client.query('DELETE FROM url_patterns WHERE repo_id = $1', [repoId]);
    await client.query('DELETE FROM files WHERE repo_id = $1', [repoId]);
    
    // ============================================
    // 步骤 4: 重建所有索引和约束
    // ============================================
    console.log('Step 4: Recreating indexes...');
    
    // 重建 B-tree 索引（并行创建）
    await Promise.all([
      client.query('CREATE INDEX idx_code_chunks_file_id ON code_chunks (file_id)'),
      client.query('CREATE INDEX idx_code_chunks_repo_id ON code_chunks (repo_id)'),
      client.query('CREATE INDEX idx_code_chunks_symbol_name ON code_chunks (symbol_name)'),
      client.query('CREATE INDEX idx_code_chunks_line_start ON code_chunks (line_start)'),
      client.query('CREATE INDEX idx_code_chunks_line_end ON code_chunks (line_end)'),
      client.query('CREATE INDEX idx_code_chunks_symbol_type ON code_chunks (symbol_type)')
    ]);
    
    // 重建 HNSW 向量索引（最耗时，单独执行）
    await client.query(`
      CREATE INDEX idx_code_chunks_embedding_hnsw
      ON code_chunks USING hnsw (embedding vector_cosine_ops)
      WITH (m = 16, ef_construction = 64)
    `);
    
    // 重建外键约束
    await client.query(`
      ALTER TABLE constant_references
      ADD CONSTRAINT fk_constant_references_chunk
      FOREIGN KEY (chunk_id) REFERENCES code_chunks(id) ON DELETE CASCADE
    `);
    await client.query(`
      ALTER TABLE call_graph
      ADD CONSTRAINT fk_call_graph_from_chunk
      FOREIGN KEY (from_chunk_id) REFERENCES code_chunks(id) ON DELETE CASCADE
    `);
    await client.query(`
      ALTER TABLE call_graph
      ADD CONSTRAINT fk_call_graph_to_chunk
      FOREIGN KEY (to_chunk_id) REFERENCES code_chunks(id) ON DELETE CASCADE
    `);
    
    await client.query('COMMIT');
    console.log('✅ Data cleared successfully');
    
  } catch (error) {
    await client.query('ROLLBACK');
    console.error('❌ Failed to clear data:', error);
    throw error;
  } finally {
    client.release();
  }
}
```

### 1.5 技术原理深度解析

#### 为什么重建索引比维护索引快？

**逐行维护索引**（优化前）：
```
对于每一行删除：
1. 在 B-tree 中查找对应的索引项 (O(log n))
2. 删除索引项
3. 重新平衡 B-tree (可能需要节点合并)
4. 对于 HNSW 索引：
   - 查找节点在图中的位置
   - 断开与邻居的连接
   - 重新连接邻居节点（保持图的连通性）
   - 更新邻居节点的边列表

总复杂度: O(n × log n) + HNSW 图重建开销
```

**批量重建索引**（优化后）：
```
1. 扫描表中的所有数据 (O(n))
2. 排序数据（对于 B-tree）(O(n log n))
3. 自底向上构建 B-tree (O(n))
4. 对于 HNSW 索引：
   - 一次性构建整个图结构
   - 使用批量插入优化
   - 避免逐个节点的图重建

总复杂度: O(n log n)
```

**关键差异**：
- 逐行维护：每次都要查找、删除、重新平衡
- 批量重建：一次性排序和构建，利用批量操作优化

#### HNSW 索引的工作原理

**HNSW (Hierarchical Navigable Small World Graph)**：

```
层级结构：
Layer 2:  A -------- B
          |          |
Layer 1:  A -- C -- B -- D
          |    |    |    |
Layer 0:  A-C-E-B-F-D-G-H

删除节点 C 时：
1. 在 Layer 0 中：A-C-E 变为 A-E，需要连接 A 和 E
2. 在 Layer 1 中：A-C-B 变为 A-B，需要连接 A 和 B
3. 更新 A、E、B 的邻居列表
4. 重新计算最短路径
```

**为什么删除慢？**
- 每次删除都要重新连接邻居
- 需要保持图的连通性
- 需要更新多个层级

**为什么重建快？**
- 一次性构建整个图
- 可以使用优化的批量插入算法
- 不需要维护中间状态

## 二、向量维度升级（1024 → 1536）

### 2.1 升级背景

**原因**：
- 阿里百炼的 text-embedding-v4 模型支持 1536 维
- 更高的维度 = 更好的语义表示能力
- 预期准确率提升 10-15%

**挑战**：
- 已有 50K+ 条向量数据（1024 维）
- 需要平滑迁移，不能中断服务
- 需要重新生成所有向量

-- 重建 HNSW 索引（1536 维）

## 三、查询缓存优化（2-5 倍提升）

### 3.1 缓存策略

**LRU 缓存实现**：

```typescript
class LRUCache<T> {
  private cache = new Map<string, { value: T; expiry: number }>();
  private maxSize: number;
  private ttl: number;
  
  constructor(maxSize: number = 100, ttl: number = 5 * 60 * 1000) {
    this.maxSize = maxSize;
    this.ttl = ttl;
  }
  
  get(key: string): T | null {
    const item = this.cache.get(key);
    if (!item) return null;
    
    // 检查是否过期
    if (Date.now() > item.expiry) {
      this.cache.delete(key);
      return null;
    }
    
    // LRU: 移到最后（最近使用）
    this.cache.delete(key);
    this.cache.set(key, item);
    
    return item.value;
  }
  
  set(key: string, value: T) {
    // 如果缓存已满，删除最旧的项
    if (this.cache.size >= this.maxSize) {
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey);
    }
    
    this.cache.set(key, {
      value,
      expiry: Date.now() + this.ttl
    });
  }
  
  clear() {
    this.cache.clear();
  }
}
```

**缓存键生成**：

```typescript
function generateCacheKey(operation: string, params: any): string {
  // 使用 JSON.stringify 生成稳定的键
  const paramsStr = JSON.stringify(params, Object.keys(params).sort());
  return `${operation}:${paramsStr}`;
}

// 使用示例
const cacheKey = generateCacheKey('search', {
  repoId: 1,
  query: 'getUserData',
  limit: 20
});
// 结果: "search:{"limit":20,"query":"getUserData","repoId":1}"
```

## 四、多语言分词优化（中文准确度提升 40-60%）

### 4.1 问题背景

**问题**：中文查询"用户登录"无法匹配 `userLogin` 函数

```typescript
// 用户查询："用户登录"
// 期望匹配：userLogin, handleLogin, loginUser

// 优化前：
// "用户登录" → ["用户登录"]  // 作为一个整体
// 无法匹配 userLogin ❌

// 优化后：
// "用户登录" → ["用户", "登录", "user", "login", "yonghu", "denglu"]
// 可以匹配 userLogin ✅
```

### 4.2 优化方案

**中文分词 + 拼音转换 + 英文翻译**：

```typescript
import Segment from 'segmentit';
import pinyin from 'pinyin';

const segment = new Segment();
segment.useDefault();

export async function extractKeywords(text: string): Promise<string[]> {
  const keywords = new Set<string>();
  
  // 1. 原始文本
  keywords.add(text.toLowerCase());
  
  // 2. 中文分词
  const segments = segment.doSegment(text, { simple: true });
  segments.forEach(seg => {
    if (seg.w.length > 1) {  // 过滤单字
      keywords.add(seg.w);
    }
  });
  
  // 3. 拼音转换
  segments.forEach(seg => {
    if (/[一-龥]/.test(seg.w)) {  // 是中文
      const pinyinArray = pinyin(seg.w, { style: pinyin.STYLE_NORMAL });
      const pinyinStr = pinyinArray.map(p => p[0]).join('');
      keywords.add(pinyinStr);
    }
  });
  
  // 4. 英文翻译（简单映射）
  const translations: Record<string, string[]> = {
    '用户': ['user', 'account'],
    '登录': ['login', 'signin'],
    '注册': ['register', 'signup'],
    '密码': ['password', 'pwd'],
    '数据库': ['database', 'db'],
    '连接': ['connection', 'connect'],
    // ... 更多映射
  };
  
  segments.forEach(seg => {
    if (translations[seg.w]) {
      translations[seg.w].forEach(t => keywords.add(t));
    }
  });
  
  return Array.from(keywords);
}
```

> "我们发现删除 96K 条记录耗时 16-19 分钟，用户体验极差。这是一个真实的性能瓶颈。"

**2. 分析（1 分钟）**
> "我使用 EXPLAIN ANALYZE 分析，发现 4 个瓶颈：
> 1. HNSW 向量索引删除时需要重新平衡图结构
> 2. 7 个 B-tree 索引需要逐行维护
> 3. 外键级联删除触发子表操作
> 4. 大量的 WAL 日志写入"

**3. 方案（1 分钟）**
> "我的优化方案是：先删除索引，再删除数据，最后重建索引。核心原理是：批量重建索引比逐行维护快 10+ 倍。"

**4. 效果（30 秒）**
> "最终从 16-19 分钟优化到 98 秒，提升了 10-12 倍。这个优化不仅提升了性能，还让我深入理解了 HNSW 索引的工作原理。"

**5. 延伸（可选）**
> "这个经验让我意识到：性能优化不是简单的调参，而是要深入理解底层原理。后来我还优化了查询缓存、中文分词等，整体性能提升了 3-10 倍。"
