## 一、pgvector 批量删除优化（真实代码，真实原理）

> **真实文件**：`apps/api/src/db/index.ts` 的 `clearRepoData(repoId)`。
> 这个函数的注释写得很好，**面试时直接讲注释里的推理链**即可。

### 1.1 问题

**场景**：删除某个仓库的全部索引数据（重新索引前需要先清空，或仓库下线）。

**现象**：随着数据量增长，删除耗时增长得比数据量更快 —— 不是线性的。

### 1.2 定位方法（这部分比结论更重要）

`clearRepoData` 的设计本身来自一次定位过程。复现这个定位过程的方法：

```sql
-- 1. 看执行计划，确认时间花在哪
EXPLAIN (ANALYZE, BUFFERS)
DELETE FROM code_chunks WHERE repo_id = 1;

-- 关注点：是否出现大量的 Index Scan / index maintenance 相关时间
-- 对比实验：临时 DROP 掉 HNSW 索引后再跑一次
DROP INDEX idx_code_chunks_embedding_hnsw;
EXPLAIN (ANALYZE) DELETE FROM code_chunks WHERE repo_id = 1;
-- 如果耗时显著下降 → 瓶颈确认为索引维护，而非删除本身
--
-- ⚠️ 实验完记得重建：
-- CREATE INDEX idx_code_chunks_embedding_hnsw ON code_chunks
--   USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

> **面试可讲点**：这段对比实验的核心是
> **「用一个可控的变量隔离掉被测对象」** —— 把索引删掉再测，
> 如果快了很多，就证明了慢的不是 DELETE。这比任何数字都更能说明你会做性能分析。

**同时值得看的信息：**

```sql
-- 这张表到底有多少个索引要维护？
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'code_chunks';
```

真实情况是 `code_chunks` 上有 **HNSW 向量索引 + 多个 B-tree + GIN 索引**，
每删一行，PostgreSQL 都要同步维护全部这些索引。

### 1.3 结论与解法

**结论（源码注释原文）：**
```typescript
/**
 * 为什么要先删除索引？
 * - 索引维护是删除操作的主要性能瓶颈
 * - HNSW 向量索引在删除时特别慢（需要重新平衡图结构）
 * - 删除索引后，DELETE 操作只需要删除表数据，速度快得多
 */
```

**解法 —— `clearRepoData` 的五步：**

```typescript
// ── Step 1: 先删索引和外键约束 ──────────────────────────
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_embedding_hnsw');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_file_id');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_symbol_name');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_symbol_type');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_node_type');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_metadata');
await pool.query('DROP INDEX IF EXISTS idx_code_chunks_repo');
await pool.query('ALTER TABLE code_chunks DROP CONSTRAINT IF EXISTS code_chunks_parent_chunk_id_fkey');
/* ...以及其它表指向 code_chunks 的外键... */

// ── Step 2: 从叶子表到根表，手动批量 DELETE（不用级联） ──
// 源码注释：级联会触发多次查询和删除操作；手动删除可以批量删，更快
await pool.query('DELETE FROM constant_references WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM string_constants   WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM url_usages         WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM url_patterns       WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM call_graph         WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM functions          WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM classes            WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM file_dependencies  WHERE repo_id = $1', [repoId]);
await pool.query('DELETE FROM import_relations   WHERE repo_id = $1', [repoId]);

// ── Step 3: 删 code_chunks（此时无索引无约束，极快） ─────
const fileIds = (await pool.query('SELECT id FROM files WHERE repo_id = $1', [repoId]))
  .rows.map(r => r.id);
if (fileIds.length > 0) {
  await pool.query('DELETE FROM code_chunks WHERE file_id = ANY($1)', [fileIds]);
}

// ── Step 4: 删 files ───────────────────────────────────
await pool.query('DELETE FROM files WHERE repo_id = $1', [repoId]);

// ── Step 5: 重建索引与约束 ─────────────────────────────
// 源码注释：PostgreSQL 对批量索引构建有优化，可一次性扫描全表
await pool.query('CREATE INDEX IF NOT EXISTS idx_code_chunks_file_id ON code_chunks (file_id)');
/* ...其余 B-tree / GIN 索引... */

// 最耗时的 HNSW 放最后
await pool.query(`
  CREATE INDEX IF NOT EXISTS idx_code_chunks_embedding_hnsw
  ON code_chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64)
`);

// 用 DO 块安全恢复外键约束（幂等，可重复执行）
const constraints = [
  { table: 'code_chunks', name: 'code_chunks_parent_chunk_id_fkey',
    definition: 'FOREIGN KEY (parent_chunk_id) REFERENCES code_chunks(id) ON DELETE SET NULL' },
  /* ... */
];
/* ...DO $$ ... IF NOT EXISTS ... END $$... */
```

### 1.4 技术原理：为什么这样更快？

**逐行删除（优化前）** —— 每删一行都要付出：
```
B-tree:  1. 查找索引项 O(log n)
         2. 删除索引项
         3. 可能的节点合并 / 分裂

HNSW:    1. 定位节点在图中的位置
         2. 断开与邻居的连接
         3. 重新连接邻居（保持图连通性）
         4. 更新邻居节点的边列表
```

**批量重建（优化后）** —— 一次全表扫描 + 自底向上建树 / 一次性构图：
```
B-tree:  O(n) 扫描 + O(n log n) 排序 + O(n) 自底向上构建
HNSW:    一次性构建整个图，避免逐节点的图修复
```

**一句话总结**：**把 N 次随机写，换成 1 次顺序批量写。**

**为什么 HNSW 删除特别贵（深入一层的讲法）：**
HNSW 是**分层可导航小世界图**，每个节点维护若干层的邻居指针。
删除一个节点不能简单地「摘掉」—— 必须重新连接它的邻居以保持图的连通性，
否则搜索会走进死路。而且这个修复要在**多个层**上分别做。
后果是：删除代价与节点的度数相关，远比顺序扫描贵。

```
Layer 2:  A -------- B
Layer 1:  A -- C -- B -- D
Layer 0:  A-C-E-B-F-D-G-H

删除 C：
  Layer 0: A-C-E → 需要补 A-E 这条边
  Layer 1: A-C-B → 需要补 A-B 这条边
  并更新 A、E、B 的邻居列表
```

### 1.5 关于「快了多少」—— 标准回答

> ⛔ 原文档给的是「16-19 分钟 → 98 秒，10-12 倍」，并配了 5 次测试记录和标准差。
> **这些数据不存在，务必删除。**
>
> ✅ **推荐的说法（背下来）：**
>
> 「我没有在生产规模上跑过基准，所以不给倍数。
> 但这个优化的收益**是可以推理出来的**：
> 它把『每删一行都维护一次 HNSW 图结构』变成了『一次全表扫描 + 一次建索引』，
> 也就是把 N 次随机写换成 1 次顺序写 —— **数据量越大收益越明显**。
> 如果你关心具体数字，给我目标规模和硬件，我可以现场跑一组对比：
> 有索引 / 无索引各跑一次 `EXPLAIN ANALYZE`。」

**为什么这样回答更好**：面试官问「快多少倍」，真正想验证的是
「你知不知道它为什么快」。给出推理链 + 邀请实测，
比报一个记不住的数字更难被驳倒。

## 二、向量维度升级（1024 → 1536）

> **真实文件**：`apps/api/migrations/002_update_embedding_dimensions.sql`。

### 2.1 背景与真实做法

**原因**：当前模型 DashScope `qwen3.7-text-embedding` 的**原生输出是 1024 维**，
而库里的列是 `vector(1536)`；靠 `EMBED_DIMENSIONS=1536`（请求里的 `dimensions` 参数）
把向量撑到 1536 才能与既有列对齐。早期实现用的是 1024 维，故有此迁移。

> 注：下面脚本里的注释原文写的是 `text-embedding-v4`——那是**迁移当时的模型名**，
> 为与迁移文件保持逐字一致而保留。当前模型见 `llm/embeddings.ts`。

**真实迁移脚本（可直接引用）：**

```sql
-- Migration: Update embedding dimensions from 1024 to 1536
-- This ensures consistency with text-embedding-v4 model output

-- 1. 先清空已有向量（将在重新索引时重算）
UPDATE code_chunks SET embedding = NULL WHERE embedding IS NOT NULL;

-- 2. 删除旧的向量列
ALTER TABLE code_chunks DROP COLUMN IF EXISTS embedding;

-- 3. 按新维度加回列
ALTER TABLE code_chunks ADD COLUMN embedding vector(1536);

-- 4. 重建索引，并借此机会从 ivfflat 换成 HNSW
--    注释原文：better performance than IVFFlat
CREATE INDEX idx_code_chunks_embedding_hnsw ON code_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Note: Existing embeddings will need to be regenerated
-- Run: npm run reindex <repo_id> <repo_path>
```

> ⚠️ **原文档写的是 `ALTER TABLE ... ALTER COLUMN embedding TYPE vector(1536)`** ——
> 真实做法是 **`DROP COLUMN` 再 `ADD COLUMN`**。
> 行为差异很关键：`ALTER COLUMN TYPE` 会尝试转换既有数据（1024 维向量转 1536 维是**无意义**的），
> 而真实脚本先显式 `UPDATE ... SET embedding = NULL` 再换列 ——
> **明确表达「旧向量作废，必须重算」**，这才是正确语义。
> 这个小细节如果面试官懂 pgvector，是一个很好的加分点。

### 2.2 迁移必须配套的动作

维度变了，**所有存量向量都失效**，必须整库重算。因此项目里有：

- `apps/api/scripts` 里的 `reindex` 脚本（`pnpm reindex <repo_id> <repo_path>`）
- `apps/api/src/indexing/queue.ts` 里的 `enqueueReindexJob` —— 重索引是一等公民的队列任务
- `check-dimensions` 脚本（`pnpm check-dimensions`）—— 校验库中向量维度是否与模型一致

> **可讲点**：换 embedding 模型的迁移**不是改个常量**，
> 它牵涉「列类型 + 全部存量数据 + 索引 + 校验脚本」四件事。
> 这个项目把这四件事都列进了迁移流程，说明考虑过运维。

### 2.3 收益与代价（讲机制，不报数字）

| 维度 | 收益（可推理） | 代价（可推理） |
|------|---------------|---------------|
| 512 → 1024 或 1024 → 1536 | 表达能力更强，语义区分度更高 | 存储：`1536 × 4B ≈ 6KB/向量`；索引更大 |
| 检索延迟 | — | 距离计算量线性增长 |
| 索引构建时间 | — | HNSW 构图成本上升 |

> ⛔ 原文档给的「语义理解 +30% / 搜索准确率 80%→90% / 延迟 +22%」没有出处。
> ✅ 正确说法：「**维度提升的收益是概念性的（表达力），代价是可算的（存储与距离计算）**。
> 是否值得，取决于你的标注集测出来的召回率曲线 —— 而这一步我们还没做。」

## 三、查询缓存（真实实现）

> **真实文件**：`apps/api/src/cache/lru-cache.ts`（199 行）。
> 这个实现比一般项目里的「Map 包一下」要完整，**有几个细节值得讲**。

### 3.1 真实实现的关键设计

```typescript
export class LRUCache<T> {
  private cache: Map<string, CacheEntry<T>>;
  private maxSize: number;   // 默认 100
  private ttl: number;       // 默认 5 分钟

  constructor(maxSize: number = 100, ttlMinutes: number = 5) { /* ... */ }

  get(key: string): T | null {
    const entry = this.cache.get(key);
    if (!entry) return null;

    // TTL 检查
    if (Date.now() - entry.timestamp > this.ttl) {
      this.cache.delete(key);
      return null;
    }

    // LRU 语义：先删再塞，利用 Map 的插入顺序把条目推到末尾
    entry.accessCount++;
    this.cache.delete(key);
    this.cache.set(key, entry);

    return entry.value;
  }

  set(key: string, value: T): void {
    if (this.cache.has(key)) this.cache.delete(key);
    if (this.cache.size >= this.maxSize) {
      // 淘汰 Map 的第一个元素 = 最久未使用
      const firstKey = this.cache.keys().next().value;
      if (firstKey !== undefined) this.cache.delete(firstKey);
    }
    this.cache.set(key, { value, timestamp: Date.now(), accessCount: 1 });
  }

  /** 命中率可以直接读出来 —— 这是原文档漏掉的亮点 */
  getStats(): { size: number; maxSize: number; hitRate: number } { /* ... */ }

  cleanup(): void { /* 批量清理过期条目 */ }
}
```

**三个可讲的实现细节：**

1. **用 `Map` 的插入顺序实现 LRU** —— JS 的 `Map` 保证遍历顺序等于插入顺序，
   所以「删掉再塞回去」就等于「标记为最近使用」，
   不需要手写双向链表。**这是 JS 相对其它语言的实现便利**。
2. **`accessCount` + `getStats()`** —— 缓存自己会统计命中率。
   也就是说「缓存到底有没有用」**是可以运行时测量的**，不需要拍脑袋。
3. **`cleanup()` 与 TTL 双机制** —— `get` 时惰性删除过期项，
   另有 `cleanup()` 供定期主动清理内存。惰性 + 主动结合，避免内存被过期项长期占用。

### 3.2 缓存键的两个真实细节（原文档写错了）

```typescript
// cache/lru-cache.ts —— 真实签名是可变参数，不是对象
export function generateCacheKey(prefix: string, ...params: any[]): string {
  return `${prefix}:${params.map(p =>
    typeof p === 'object' ? JSON.stringify(p) : String(p)
  ).join(':')}`;
}
```

**真实细节 1：缓存键用「拼写纠错后」的 query。**
`MultiStrategySearch.searchWithSuggestions` 里的顺序是：
```typescript
const { corrected: correctedQuery, hasCorrected } = correctTypos(query);
const searchQuery = hasCorrected ? correctedQuery : query;
const cacheKey = generateCacheKey('search', { repoId, query: searchQuery, ...options });
```
如果键用原始 query，用户把 `usr` 打成 `user` 就会各占一份缓存，命中率凭空掉一半。

**真实细节 2：`getStats()` 提供运行时命中率。**
所以性能讨论可以建立在**真实观测**上，而不是估计值。

### 3.3 正确讲法

> ⛔ 原文档的「重复查询 10 倍 / 相似查询 5 倍 / 平均 3.3 倍」没有出处，且概念上混淆：
> LRU 缓存**只对完全相同的键命中**，不存在「相似查询命中缓存」（相似查询走的是检索策略，不是缓存）。
>
> ✅ **推荐说法：**
> 「`MultiStrategySearch` 里有 LRU 缓存，100 条容量、5 分钟 TTL。
> 这里有两个刻意的设计：缓存键用**纠错后**的 query，避免同一个意图占两份缓存；
> 缓存对象自带 `getStats()`，可以随时读出**真实命中率** ——
> 所以『缓存有没有用』这件事是可观测的，不需要估算。
> 另外要注意的是，缓存只能命中**完全相同的键**，
> 『相似但不同』的查询是靠多策略检索解决的，这两件事不要混为一谈。」

**最后一句很重要**：主动区分「缓存」和「检索」的职责边界，
显示你理解系统的分层，而不是把两个机制混着吹。

## 四、多语言分词（真实实现）

> **真实文件**：`apps/api/src/retrieval/multilingual-tokenizer.ts`（229 行）+ `segmentit`。

### 4.1 问题

中文查询「用户登录」无法字面匹配 `userLogin`：
- 字面匹配：`"用户登录"` ≠ `"userLogin"` ❌
- 纯向量：可能召回到语义相近但不相关的方法，精度不够

### 4.2 真实能力（源码注释原文）

```
支持的语言和格式：
1. 中文分词（基于 segmentit 库）
2. 日文分词（基于 segmentit 库）
3. 英文分词（基于空格和标点）
4. 驼峰命名拆分（camelCase → camel, Case）
5. 下划线命名拆分（snake_case → snake, case）
```

**两个实现细节值得讲：**

```typescript
// 1. 懒加载 —— 避免启动时加载词典
let segment: any = null;
async function getSegment() {
  if (!segment) {
    const segmentit = await import('segmentit');
    const pkg = segmentit.default || segmentit;
    const { Segment, useDefault } = pkg;
    segment = useDefault(new Segment());   // 单例，避免重复初始化
  }
  return segment;
}

// 2. 按字符范围判断语言
function containsChinese(text: string): boolean {
  return /[一-龥]/.test(text);   // CJK 统一汉字基本区
}
```

- **懒加载 + 单例**：分词词典初始化有成本，不该在进程启动时付这笔钱
- **按 Unicode 范围检测语言**：比按语种配置更省事，也更能处理「中文注释 + 英文代码」这种混排

### 4.3 正确讲法

> ⛔ 原文档的「中文准确度提升 40-60%」「用户登录 40%→90%」等表格全部无出处。
>
> ✅ **推荐说法：**
> 「中文查询之所以难，是因为代码是英文标识符、查询是中文，
> 两边**在字面上完全不重叠**。我的处理是把查询拆成中/日/英 + 驼峰 + 下划线的混合 token，
> 让『用户登录』能拆出『登录』并映射到 `login`，
> 同时 `userLogin` 能拆成 `user` + `login` 分别匹配。
> 这样就让字面匹配这条路在中文查询下也能用上。
> 具体提升多少，需要标注集才能量化 —— 我没有。」

| 「16-19 分钟 → 98 秒（10-12 倍）」 | 无基准测试，5 次测试记录是编的 |
| 「`EXPLAIN ANALYZE` Execution Time: 1,047,234.567 ms」 | 伪造的 SQL 输出 |
| 「删掉 HNSW 后 3 分 45 秒（4.6 倍）」 | 伪造的对比实验 |
| 「索引速度 20 分钟 → 2-3 分钟（7-10 倍）」 | 无出处 |
| 「缓存 500ms → 150ms（3.3 倍）」 | 无出处，且概念混淆（相似查询不走缓存） |
| 「中文准确度提升 40-60%」 | 无对照实验 |
| 「维度升级：准确率 80%→90%」 | 无标注集 |

### 5.3 面试中如何展示（重写版脚本）

**1. 问题（20 秒）**
> "删除某个仓库的全部索引数据时，耗时增长得比数据量更快 —— 不是线性的。
> 这通常意味着有某个**按行摊派的固定成本**。"

**2. 定位（1 分钟）**
> "我的定位方法是做个对比实验：用 `EXPLAIN ANALYZE` 看执行计划，
> 然后**临时把 HNSW 索引删掉再跑一次**。
> 如果耗时大幅下降，就说明慢的不是 DELETE，而是**索引维护**。
> 结论确实是索引：`code_chunks` 上有 HNSW 向量索引加多个 B-tree / GIN，
> 每删一行都要同步维护它们。而 HNSW 是图结构，删节点要重新连邻居、还要在多层上修，
> 代价和节点度数相关，比顺序扫描贵得多。"

**3. 方案（1 分钟）**
> "解法是把「N 次随机写」换成「1 次顺序批量写」：
> 先 DROP 索引和外键约束 → 从叶子表到根表手动批量 DELETE（绕开级联）→
> 删主表 → 再一次性重建索引和约束。重建索引用 `DO` 块做成幂等的。
> 本质上是**承认索引是写入的代价**，然后在批量场景下把这份代价推迟到一次集中付出。"

**4. 边界（30 秒）**
> "这个优化的前提是**批量**删除。如果是删几行，重建索引反而更亏 ——
> 所以我保留了逐行删除的路径，只在 `clearRepoData` 这种全量清理场景用这套。
> 另外我没有在生产规模上跑基准，所以不给倍数；
> 如果你想要数字，我们可以现场跑一组有索引/无索引的对比。"

**为什么这个脚本更好**：它有「问题 → 假设 → 验证 → 方案 → 边界」的完整结构，
而且**最后主动说出适用边界并承认没测** —— 这是资深工程师的表达方式。
面试官从这段里能看到的不是「快 10 倍」，而是「会做性能分析、会划边界」。
