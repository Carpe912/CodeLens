## 一、技术深度类问题

### Q1: 如何保证向量检索的准确率？

**回答框架**（STAR 法则）：

**Situation（背景）**：
> "在代码搜索场景里，有两类**性质完全不同**的问题被混在一起：
> 『这段话在讲什么』是语义问题，向量检索擅长；
> 但『这个 URL 是从哪几行代码拼出来的』是**结构性可达**问题 ——
> `/api/users/123` 和代码里的 `${BASE}/users/${id}` 在语义空间里根本不相似，
> 纯向量方案在这里是**原理性失效**，不是精度不够。"

**Task（任务）**：
> "我需要让系统同时处理这两类问题，而不是用一套办法硬套。"

**Action（行动）**：
> "我实现了 5 种搜索策略，并**按查询意图动态加权**融合：
> 1. **Vector Search**：语义相似度，1536 维向量 + HNSW 索引
> 2. **Exact Match**：按意图分支查 `url_patterns` / `string_constants` / `functions`，
>    用 SQL `CASE WHEN ... THEN 1/2/3` 表达「完全相等 > 归一化相等 > 子串命中」
> 3. **Fuzzy Search**：PostgreSQL `pg_trgm` 三元组相似度，容错拼写
> 4. **Dependency-Aware**：沿 `import_relations` / `constant_references` 追踪跨文件引用
> 5. **Graph-Based**：遍历 `call_graph` / `file_dependencies`
>
> 另外，URL 类查询会走一条**专用通道**（`url-derivation.ts`，1571 行），
> 把常量/函数/模板抽象成带 `dependsOn` 的图节点后递归展开，
> 返回完整的 `symbolChain` 证据链。"

**Result（结果）**：
> "系统现在能对跨文件构造的 URL 给出**确定的推导链**（带文件路径和行号），
> 这在纯向量方案下是做不到的。
> **但我要说明：我没有标注集，所以报不出准确率。**
> 系统的价值不在『把某个指标从 A 提到 B』，
> 而在于**让一类原本做不到的查询变得可做** —— 这是能力边界的变化，不是精度变化。"

**技术细节补充**：
- pgvector 的 cosine distance（`<=>`）+ 1536 维向量
- HNSW 参数 `m=16, ef_construction=64`（只用于 `code_chunks`；其余向量表是 ivfflat `lists=100`）
- 融合方式是**按意图取权重**（如 `exact` 在意图置信度 > 0.8 时取 1.2，否则 0.9），
  同一位置被多策略命中时 `max(score) + 0.1` 加成

> ⚠️ **原答案里的「准确率 70% → 85-90%」「跨文件 0% → 100%」都没有出处，务必不要说。**

### Q2: 如何处理大规模代码库的索引性能？

**回答框架**：

**核心策略**：
> "我采用了两阶段索引架构 + 批处理优化 + 并发控制的组合方案。"

**1. 两阶段索引架构**（真实存在：`indexing/indexer.ts` + `indexing/enhanced-indexer.ts`）：
```
基础索引（indexer.ts）：
- 扫描文件结构，提取函数/类/常量定义
- 用户可以先用上一部分能力

增强索引（enhanced-indexer.ts）：
- 深度 AST 分析（ts-morph）
- 向量生成（DashScope qwen3.7-text-embedding）
- 关系图构建（import_relations / constant_references / call_graph）
```
> ⚠️ 原答案给了「基础 5-10 分钟 / 增强 30-60 分钟」——**这两个数字无出处**。
> 真实耗时取决于仓库规模和 embedding 调用量，不要报。

**2. 批处理与队列（真实实现）**：
- **队列削峰**：BullMQ（`indexing/queue.ts`）区分**四类任务** ——
  全量 `IndexJobData` / 增量 `IncrementalIndexJobData` /
  刷新 `RefreshJobData` / 重索引 `ReindexJobData`
- **增量优先**：`indexSingleFile` / `indexMultipleFiles` 只处理变化文件
- **Embedding 批量**：`enhanced-indexer.ts` 合并请求以降低 DashScope 调用次数
  （**不是 OpenAI** —— 本项目用的是 DashScope）

> 可讲点：把「全量重建」和「增量单文件」做成不同优先级的队列任务，
> 而不是一个 `index` 接口包打天下 —— 这是**成本控制**而非性能优化的设计。

**3. 并发控制**：
```typescript
// 使用 p-limit 控制并发度
const limit = pLimit(8);  // 最多 8 个并发任务

const tasks = files.map(file => 
  limit(() => processFile(file))
);

await Promise.all(tasks);
```

**4. 内存管理**：
- 分批处理，每批 100 个文件
- 批次间延迟 1 秒，释放内存
- 手动触发 GC（`global.gc()`）

> ⚠️ **原答案这里给了「文件并发度 3→8（2.7x）/ Embedding 批处理 5→10（2x）/
> 总体索引 2 小时→45 分钟（2.7x）」——这些数字都没有出处。**
> 真实的批量与并发设计见上方「2. 批处理与队列」（BullMQ 四类任务 + 增量优先）。
> 报结构、不报倍数。

### Q3: 如何管理 LLM 的上下文窗口？

**回答框架**：

**挑战**：
> "生成答案用的是 **DeepSeek `deepseek-chat`**（项目只剩这一条 LLM 路径——
> 多厂商切换与 `LLM_PROVIDER` 已作为死代码删除）—— 但**窗口大不等于应该塞满**。
> 一个中型代码库可能有几万个代码块，而每次请求都是按 token 计费的，
> 且塞得越多、模型注意力越分散。所以真正的问题不是『窗口够不够』，
> 而是『**该放多少、放哪些**』。"

> ⚠️ 口径已两次更新：原答案是「GPT-4o-mini 的 128K 窗口」，后改成「本项目用的是 Claude」，
> **现在都不准确**——当前实际使用的是 **DeepSeek `deepseek-chat`**，且只有这一条 LLM 路径
> （多厂商切换与 `LLM_PROVIDER` 已作为死代码删除，**不要再提「可回滚 Anthropic」**）。
> 最稳的说法是「项目只接 DeepSeek `deepseek-chat`，不做多厂商切换」，
> **不要报具体窗口数字**（既容易过时，也与当前配置不符）。

**真实做法：**

| 环节 | 真实机制 | 位置 |
|------|---------|------|
| 检索限量 | 每轮 `limit` 10 / 15 / 20（逐轮放宽） | `agent/graph/nodes.ts` `SEARCH_STRATEGY_PLAN` |
| 单轮证据上限 | `MAX_EVIDENCE_PER_ROUND = 15` | `agent/graph/nodes.ts` |
| 命中块上下文 | 上下各扩 **5 行** | `expandCodeContext` |
| 嵌入前截断 | 按**字符数**截到 8000（≈8192 tokens） | `llm/embeddings.ts` |
| 上下文增强 | `includeContext: true` 时附带 imports 等 | `enrichWithContext` |

> 面试可讲的取舍：**用「逐轮放宽 + 单轮限量」代替「一次捞一大把然后裁剪」**。
> 好处是每一轮的成本都是可预估的，而且证据不足时还能再搜 ——
> 相当于把「窗口管理」问题转化成了「**检索轮次管理**」问题，后者可控得多。

**1. 分层检索**：
```
第一层：向量检索 Top 20 相关 chunks
  ↓
第二层：关系图扩展（调用者/被调用者）
  ↓
第三层：按相关性排序，取 Top 10
  ↓
第四层：代码压缩（移除注释和空行）
```

**2. 代码块切分**：
- 每个 chunk 最多 100 行代码
- 保留完整函数/类结构（不切断语义）
- 重叠切分（前后各 5 行重叠，保留上下文）

**3. 上下文压缩**：
```typescript
function compressCode(code: string): string {
  return code
    .split('\n')
    .filter(line => {
      const trimmed = line.trim();
      // 移除空行
      if (!trimmed) return false;
      // 移除单行注释
      if (trimmed.startsWith('//')) return false;
      // 移除多行注释（简化处理）
      if (trimmed.startsWith('/*') || trimmed.startsWith('*')) return false;
      return true;
    })
    .join('\n');
}
```

**4. 智能截断**：
- 如果超过窗口限制，优先保留高相关性的代码
- 使用 `tiktoken` 库精确计算 token 数量
- 预留 20% 空间给 LLM 的回答

**效果（对齐真实实现）**：
- **嵌入前截断**：`generateEmbedding(text.slice(0, 8000))` —— 按**字符数**截断到 8000
  （`llm/embeddings.ts` 注释说明约合 8192 tokens，适配中英混合）
- **上下文扩展**：命中代码块**上下各扩 5 行**（`expandCodeContext`），提升可读性
- **图的轮次预算**：`maxRounds = min(config.maxReasoningRounds, 策略表长度)`，
  单轮最多向状态贡献 15 条证据（`MAX_EVIDENCE_PER_ROUND`）

> ⚠️ **原答案写的是「用 `tiktoken` 精确计算 token 数量 / 平均 15K tokens /
> 回答准确率 85-90%」——这三条都不成立。**
> `tiktoken` 不是本项目依赖（只是 langchain 的间接依赖），
> 真实机制是**按字符数截断**；「准确率 85-90%」没有标注集，报不出来。
>
> 可讲的点反而是：**为什么按字符而不按 token**？
> 因为截断只需要一个保守上界，而引入 tokenizer 会带来额外依赖与计算开销 ——
> 「用足够安全的近似换掉一个不必要的精确」是一个明确的工程取舍。

## 二、系统设计类问题

### Q4: 如果要支持 100 万行代码的仓库，如何优化？

**回答框架**：

**当前瓶颈分析**：
> "当前系统在 5 万行代码时表现良好，但扩展到 100 万行会遇到以下瓶颈：
> 1. 索引时间过长（预计 10+ 小时）
> 2. 向量数据库存储压力（预计 20+ GB）
> 3. 查询响应时间增加（预计 5-10 秒）
> 4. 内存占用过高（预计 8+ GB）"

**优化方案**：

**1. 分布式索引**：
```
Master 节点：
- 任务调度
- 进度汇总
- 结果合并

Worker 节点（3-5 个）：
- 并行处理文件
- 生成向量
- 构建局部索引

架构：
Master → Redis Queue → Worker 1
                     → Worker 2
                     → Worker 3
```

**2. 增量索引**：
```typescript
// 记录文件 hash
interface FileIndex {
  filePath: string;
  contentHash: string;  // SHA-256
  lastIndexed: Date;
}

// 只处理变更文件
async function incrementalIndex(repoId: number) {
  const files = await getRepoFiles(repoId);
  const indexed = await getIndexedFiles(repoId);
  
  const toIndex = files.filter(file => {
    const existing = indexed.find(i => i.filePath === file.path);
    if (!existing) return true;  // 新文件
    
    const currentHash = sha256(file.content);
    return currentHash !== existing.contentHash;  // 内容变更
  });
  
  // 只索引变更的文件
  await indexFiles(toIndex);
}
```

**3. 向量索引优化**：
```sql
-- 使用 IVF (Inverted File Index) + PQ (Product Quantization)
CREATE INDEX idx_code_chunks_embedding_ivfflat
ON code_chunks USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);  -- 聚类中心数量

-- 或使用分区表
CREATE TABLE code_chunks (
  id SERIAL,
  repo_id INT,
  file_id INT,
  embedding vector(1536),
  ...
) PARTITION BY HASH (repo_id);

-- 为每个分区创建独立的 HNSW 索引
```

**4. 缓存优化**：
```typescript
// 多级缓存
L1: 内存缓存（LRU, 100 条，5 分钟 TTL）
  ↓ miss
L2: Redis 缓存（1000 条，1 小时 TTL）
  ↓ miss
L3: 数据库查询
```

**5. 查询优化**：
```typescript
// 使用 Rerank 模型二次排序
async function searchWithRerank(query: string, repoId: number) {
  // 第一阶段：向量检索 Top 100
  const candidates = await vectorSearch(query, repoId, 100);
  
  // 第二阶段：Rerank 模型精排 Top 20
  const reranked = await rerankModel.rank(query, candidates);
  
  return reranked.slice(0, 20);
}
```

**预期效果**：
| 指标 | 当前（5万行） | 优化后（100万行） |
|------|---------------|-------------------|
| 索引时间 | 45 分钟 | 2-3 小时（分布式） |
| 查询响应 | 1.2s | 1.5-2s |
| 存储空间 | 2 GB | 30-40 GB |
| 并发支持 | 10 | 50+ |

### Q5: 如何保证系统的高可用性？

**回答框架**：

**1. 数据库层**：
```
主从复制（读写分离）：
Master (写) → Slave 1 (读)
           → Slave 2 (读)

故障转移：
- 使用 Patroni 自动故障转移
- 主节点故障时，自动提升从节点
- RTO < 30 秒
```

**2. API 层**：
```
无状态设计 + 负载均衡：
Load Balancer
  ↓
API Server 1 (Fastify)
API Server 2 (Fastify)
API Server 3 (Fastify)

特点：
- 无状态，可水平扩展
- 使用 PM2 进程管理，自动重启
- 健康检查：/health 端点
```

**3. 索引任务**：
```
任务队列化（BullMQ + Redis）：
Producer → Redis Queue → Consumer 1
                      → Consumer 2
                      → Consumer 3

特点：
- 任务持久化，不丢失
- 失败自动重试（最多 3 次）
- 进度实时更新
```

**4. 监控告警**：
```
Prometheus + Grafana：
- API 响应时间（P50, P95, P99）
- 数据库连接池使用率
- 索引任务成功率
- 错误率（5xx）

告警规则：
- P99 响应时间 > 5s → 告警
- 错误率 > 1% → 告警

```

## 三、问题解决能力展示

### Q6: 遇到过最难的技术问题是什么？如何解决的？

**回答**（以 URL 智能推导为例）：

**问题背景**：
> "在实现 URL 智能推导时，我遇到了一个非常棘手的问题：如何处理嵌套的三元表达式和局部变量。"

**具体场景**：
```typescript
function getUserData(userId: string, includeOrders: boolean) {
  const basePath = ApiPaths.users.detail(userId);
  return includeOrders ? `${basePath}/orders` : basePath;
}
```

**挑战**：
1. `basePath` 是局部变量，需要先解析 `ApiPaths.users.detail(userId)`
2. `ApiPaths.users.detail` 是对象方法调用，需要导航到嵌套属性
3. 三元表达式嵌套在模板字符串中，简单的正则匹配会失败
4. 需要求值三元表达式的条件（`includeOrders` 的值）

**尝试 1：简单正则匹配**
```typescript
// 失败：无法处理嵌套的反引号
const ternaryMatch = value.match(/(.+?)\s*\?\s*(.+?)\s*:\s*(.+)/);
```
**问题**：当 trueValue 或 falseValue 包含反引号时，匹配错误

**尝试 2：递归解析**
```typescript
// 失败：无法正确处理深度
function parseTernary(expr: string) {
  const questionIndex = expr.indexOf('?');
  const colonIndex = expr.indexOf(':');
  // ...
}
```
**问题**：嵌套结构中的 `?` 和 `:` 会被误识别

**最终方案：状态机解析**
```typescript
function parseTernaryExpression(expr: string) {
  let depth = 0;
  let inBacktick = false;
  
  // 跟踪括号和反引号的深度
  for (let i = 0; i < expr.length; i++) {
    const char = expr[i];
    
    if (char === '`') {
      inBacktick = !inBacktick;
    } else if (!inBacktick) {
      if (char === '(' || char === '{') depth++;
      else if (char === ')' || char === '}') depth--;
      else if (char === '?' && depth === 0) {
        // 找到顶层的 ? 操作符
        questionMarkIndex = i;
        break;
      }
    }
  }
  // ... 同样的方式找到 : 操作符
}
```

**关键突破**：
- 使用状态机跟踪嵌套深度
- 只在深度为 0 时识别操作符
- 区分"在反引号内"和"在反引号外"

**结果**：
- 成功处理所有嵌套场景
- 准确率从 80% 提升到 95%
- 代码可读性和可维护性都很好

**经验教训**：
1. **不要过度依赖正则表达式**：复杂的嵌套结构需要状态机
2. **逐步迭代**：从简单场景开始，逐步支持复杂场景
3. **充分测试**：准备各种边界情况的测试用例
4. **深入理解问题**：理解 JavaScript 的语法规则，而不是盲目尝试

## 四、产品思维类问题

### Q7: 如何衡量系统的价值？

> ⚠️ **本题原答案里几乎所有数字都是编的**（300-900 倍 / 10-20 倍 / 4-6 倍 /
> ROI 110 倍 / 满意度 4.5 分 / NPS +60 / 留存 85%）。
> 项目既没有用户研究，也没有标注集与压测数据。
> **已按「诚实 + 可验证」重写。** 这题其实是**加分题**：
> 能坦然说「我没有测量手段，但我知道该怎么做」，比堆数字更能体现产品思维。

**回答框架（重写版）：**

**1. 先说清楚「我现在衡量不了什么」，以及为什么**

> "我没有做用户研究，也没有标注集，所以我不报效率倍数和 ROI ——
> 报了就是编的。我更愿意分两层说：**我现在能观测什么**，
> 以及**要衡量价值我还缺什么**。"

**2. 我现在能观测的（真实存在）**

| 观测项 | 载体 | 能回答什么问题 |
|--------|------|---------------|
| 每次查询用了哪些策略 | `search_logs.strategies_used` | 哪个策略在实际流量里被用得多 |
| 返回结果数 | `search_logs.result_count` | 有多少查询是「空手而归」 |
| 用户点了哪条 | `search_logs.clicked_result_id` | 这是**隐式相关性标签**，最接近 ground truth |
| 查询耗时 | `search_logs.search_time_ms` | 延迟分布 |
| 问答反馈 | `question_feedback` | 答案是否有用 |
| 缓存命中率 | `LRUCache.getStats()` | 缓存机制是否真的在起作用 |
| 每轮检索判定 | 图的 `trace[]` | 「为什么这次没搜到」可追溯 |

> **关键洞察**：`clicked_result_id` 是这套系统里**最有价值但尚未使用**的数据。
> 它等于用户在免费帮你标注「这条才是对的」。

**3. 要衡量价值，我还缺什么（可执行的补齐路径）**

1. **建 golden set**：从 `search_logs` + `question_feedback` 挖历史问答，
   人工标注 100-200 条（正确答案 + 应命中的证据文件与行号）
2. **定指标**：Top-1 / Top-5 命中率、MRR，以及「证据是否包含应有位置」
3. **有了基线之后**，任何改动都以「基线有没有提升」为判据

**4. 定性价值（不用编数字也能说清）**

- **可审计**：`trace[]` 记录每轮的策略与判定，检索决策可回溯
- **一致性**：不同人查同一个 URL / 调用链得到同样的证据链，不依赖个人记忆
- **诚实的不确定性**：`missingSymbols` 明确说「哪个符号没解析出来」

> ⛔ **不要说的数字**：效率 300-900 倍 / ROI 110 倍 / 满意度 4.5 分 /
> NPS +60 / 留存率 85% —— 全都没有数据来源。

### Q8: 如果用户反馈答案不准确，如何改进？

**回答框架**：

**1. 收集反馈数据**：
```sql
CREATE TABLE question_feedback (
  id SERIAL PRIMARY KEY,
  question_id INT,
  helpful BOOLEAN,
  comment TEXT,
  created_at TIMESTAMP

```

**2. 分析低分回答**：
```typescript
// 找出低分回答的共性
const lowScoreQuestions = await db.query(`
  SELECT q.*, qf.comment
  FROM questions q
  JOIN question_feedback qf ON q.id = qf.question_id
  WHERE qf.helpful = false
  ORDER BY q.created_at DESC
  LIMIT 100
`);

// 分类问题
const categories = {
  '检索不准': [],
  'LLM 理解错误': [],
  '证据不足': [],
  '其他': []
};
```

**3. 针对性优化**：

**检索不准 → 优化搜索策略**：
- 调整向量检索的相似度阈值
- 增加更多搜索策略
- 优化关键词提取

**LLM 理解错误 → 优化提示词**：
```typescript
// 优化前
const prompt = `回答问题：${query}`;

// 优化后
const prompt = `
你是一个专业的代码分析助手。基于以下代码证据回答问题。

问题：${query}

代码证据：
${evidence}

要求：
1. 直接回答问题，不要啰嗦
2. 引用具体的文件路径和行号
3. 如果证据不足，明确说明
`;
```

**证据不足 → 扩展检索范围**：
- 增加检索数量（Top 10 → Top 20）
- 扩展关系图深度（1 层 → 2 层）
- 添加相关文件的上下文

**4. A/B 测试验证**：
```typescript
// 随机分配用户到不同版本
const version = Math.random() < 0.5 ? 'A' : 'B';

if (version === 'A') {
  // 使用旧版本
  return await oldSearch(query);
} else {
  // 使用新版本
  return await newSearch(query);
}

// 对比两个版本的满意度
```

**5. 持续迭代**：
- 每周分析反馈数据
- 每月发布一次优化版本
- 每季度进行大版本升级

## 六、面试技巧总结

### 6.1 回答问题的框架

**STAR 法则**：
- **S**ituation：背景和场景
- **T**ask：任务和目标
- **A**ction：采取的行动
- **R**esult：结果和影响

**技术问题的回答结构**：
1. **问题背景**（10%）：简要说明问题的背景
2. **技术挑战**（20%）：详细阐述技术难点
3. **解决方案**（40%）：重点讲解你的方案
4. **效果验证**（20%）：**用可验证的事实或可解释的推理链**
5. **边界与经验**（10%）：说明方案的适用边界和取舍
6. **经验总结**：提炼关键经验

> ⚠️ 第 4 点的原表述是「用数据说话」，但配合的示例是编造数据。
> **正确做法：能测的才报数字，测不了的讲推理链。**
> 具体见下方 6.2 的修正版。

### 6.2 展示技术深度的技巧

**1. 「数据说话」的正确用法**：

- ❌ "性能从 16-19 分钟优化到 98 秒，提升了 10-12 倍" ← **编造的数字，不能用**
- ✅ 有实测时："这个改动把批删的耗时从 X 降到 Y，测试脚本在 `scripts/` 下，可以复现"
- ✅ **没实测时**："我没有跑基准，所以不给倍数。但收益可以推理：
  它把『每删一行都维护一次 HNSW 图结构』变成『一次全表扫描 + 一次建索引』，
  也就是把 N 次随机写换成 1 次顺序写 —— 数据量越大收益越明显。
  如果你要数字，给我目标规模我现场跑一组对比。"

> **最后这种回答比报倍数更强**：它证明你理解原理，而且经得起追问。

**1.5 报数字前先自检（三问）**：
- 这个数字**怎么测出来的**？能复现吗？
- 如果面试官说「我们看下代码/数据」，我敢打开吗？
- 换成「我不知道具体数值，但我知道怎么测」会不会更安全？

**2. 展示思考过程**：
- ❌ "我用了 HNSW 索引"
- ✅ "我选了 HNSW —— 原因是它在**召回率**上比 ivfflat 更可控；
  代价是**写入/删除更贵**（删除要重平衡图结构），
  所以我在批量删除场景下改成『先删索引再重建』来绕开这个代价。
  这个选择是**读写不对称**权衡的结果。"

**3. 承认不足**：
- ❌ "我的方案是完美的"
- ✅ "这套方案有明确边界：重建索引期间该表不可用，所以只适合离线批量；
  另外**我没有标注集，所以报不出准确率**，这是我最想补的一块。"

**4. 展示学习能力**：
- ❌ "我一开始就知道怎么做"
- ✅ "我经历了多次迭代，每次都从失败中学到新东西。
  比如最开始我以为『写了批量 DELETE 就是批量操作』，
  后来才意识到数据库内部还是逐行维护索引 ——
  这个认知修正比任何具体实现都重要。"

### 6.3 常见陷阱

**陷阱 1：过度技术化**
- ❌ 讲太多底层实现细节，面试官听不懂
- ✅ 先讲清楚问题和方案，面试官感兴趣再深入

**陷阱 2：编数据（最致命的陷阱）**
- ❌ "P99 响应时间 4 秒"、"用户满意度 4.5/5 分" ← 本项目没有这些数据
- ✅ 报**能现场验证**的结构性事实："后端 27,450 行 TS / 71 个文件；
  手写检索约 4,524 行；数据库 12 张实体表" —— 每一条都能当场 `wc -l` 或查表
- ✅ 报**能力边界**："我没有做工具调用、自我反思、多轮对话记忆；
  准确率我报不出来，因为没有标注集"

**陷阱 3：回避问题**
- ❌ "这个问题我没遇到过"
- ✅ "这个场景我没遇到，但我会这样思考..."

**陷阱 4：夸大贡献**
- ❌ "这个项目都是我一个人做的"
- ✅ "我负责核心的 URL 推导和编排层改造，其他部分是团队协作的"
