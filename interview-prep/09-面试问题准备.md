## 一、技术深度类问题

### Q1: 如何保证向量检索的准确率？

**回答框架**（STAR 法则）：

**Situation（背景）**：
> "在代码搜索场景中，单一的向量检索准确率只有 70% 左右，无法满足生产需求。"

**Task（任务）**：
> "我需要设计一个多策略搜索引擎，将准确率提升到 85-90%。"

**Action（行动）**：
> "我实现了 5 种搜索策略的智能组合：
> 1. **Vector Search**：语义相似度搜索，使用 1536 维向量 + HNSW 索引
> 2. **Exact Match**：精确模式匹配，适用于已知符号名
> 3. **Fuzzy Search**：使用 trigram 相似度容错拼写错误
> 4. **Dependency-Aware**：追踪跨文件的常量引用
> 5. **Graph-Based**：遍历函数调用图
> 
> 关键创新是根据查询意图自动选择最优策略组合，并使用动态权重融合结果。"

**Result（结果）**：
> "最终准确率从 70% 提升到 85-90%，其中跨文件引用场景从 0% 提升到 100%。"

**技术细节补充**：
- 使用 pgvector 的 cosine similarity 计算向量相似度
- HNSW 索引参数：m=16, ef_construction=64
- 多策略结果融合时使用加权评分，权重根据查询意图动态调整

### Q2: 如何处理大规模代码库的索引性能？

**回答框架**：

**核心策略**：
> "我采用了两阶段索引架构 + 批处理优化 + 并发控制的组合方案。"

**1. 两阶段索引架构**：
```
基础索引（5-10 分钟）：
- 快速扫描文件结构
- 提取函数/类/变量定义
- 用户可以开始使用

增强索引（30-60 分钟，后台运行）：
- 深度 AST 分析
- 向量生成
- 关系图构建
```

**2. 批处理优化**：
- **文件批处理**：8 个文件并发处理（而非逐个处理）
- **Embedding 批处理**：10 个 chunk 一次性调用 OpenAI API（减少网络开销）
- **数据库批处理**：使用 COPY 命令批量插入（比 INSERT 快 10 倍）

**3. 并发控制**：
```typescript
// 使用 p-limit 控制并发度
const limit = pLimit(8);  // 最多 8 个并发任务

const tasks = files.map(file => 
  limit(() => processFile(file))
);

await Promise.all(tasks);
```

**4. 内存管理**：
- 分批处理，每批 100 个文件
- 批次间延迟 1 秒，释放内存
- 手动触发 GC（`global.gc()`）

**性能数据**：
| 优化项 | 优化前 | 优化后 | 提升 |
|--------|--------|--------|------|
| 文件并发度 | 3 | 8 | 2.7x |
| Embedding 批处理 | 5 | 10 | 2x |
| 总体索引速度 | ~2小时 | ~45分钟 | 2.7x |

### Q3: 如何管理 LLM 的上下文窗口？

**回答框架**：

**挑战**：
> "GPT-4o-mini 的上下文窗口是 128K tokens，但一个中型代码库可能有 50K+ 个代码块。如何在有限窗口内提供足够的代码证据？"

**解决方案**：

**1. 分层检索**：
```
第一层：向量检索 Top 20 相关 chunks
  ↓
第二层：关系图扩展（调用者/被调用者）
  ↓
第三层：按相关性排序，取 Top 10
  ↓
第四层：代码压缩（移除注释和空行）
```

**2. 代码块切分**：
- 每个 chunk 最多 100 行代码
- 保留完整函数/类结构（不切断语义）
- 重叠切分（前后各 5 行重叠，保留上下文）

**3. 上下文压缩**：
```typescript
function compressCode(code: string): string {
  return code
    .split('\n')
    .filter(line => {
      const trimmed = line.trim();
      // 移除空行
      if (!trimmed) return false;
      // 移除单行注释
      if (trimmed.startsWith('//')) return false;
      // 移除多行注释（简化处理）
      if (trimmed.startsWith('/*') || trimmed.startsWith('*')) return false;
      return true;
    })
    .join('\n');
}
```

**4. 智能截断**：
- 如果超过窗口限制，优先保留高相关性的代码
- 使用 `tiktoken` 库精确计算 token 数量
- 预留 20% 空间给 LLM 的回答

**效果**：
- 平均每次查询使用 15K tokens（约 12% 的窗口）
- 保留了 10 个高质量代码证据
- 回答准确率 85-90%

## 二、系统设计类问题

### Q4: 如果要支持 100 万行代码的仓库，如何优化？

**回答框架**：

**当前瓶颈分析**：
> "当前系统在 5 万行代码时表现良好，但扩展到 100 万行会遇到以下瓶颈：
> 1. 索引时间过长（预计 10+ 小时）
> 2. 向量数据库存储压力（预计 20+ GB）
> 3. 查询响应时间增加（预计 5-10 秒）
> 4. 内存占用过高（预计 8+ GB）"

**优化方案**：

**1. 分布式索引**：
```
Master 节点：
- 任务调度
- 进度汇总
- 结果合并

Worker 节点（3-5 个）：
- 并行处理文件
- 生成向量
- 构建局部索引

架构：
Master → Redis Queue → Worker 1
                     → Worker 2
                     → Worker 3
```

**2. 增量索引**：
```typescript
// 记录文件 hash
interface FileIndex {
  filePath: string;
  contentHash: string;  // SHA-256
  lastIndexed: Date;
}

// 只处理变更文件
async function incrementalIndex(repoId: number) {
  const files = await getRepoFiles(repoId);
  const indexed = await getIndexedFiles(repoId);
  
  const toIndex = files.filter(file => {
    const existing = indexed.find(i => i.filePath === file.path);
    if (!existing) return true;  // 新文件
    
    const currentHash = sha256(file.content);
    return currentHash !== existing.contentHash;  // 内容变更
  });
  
  // 只索引变更的文件
  await indexFiles(toIndex);
}
```

**3. 向量索引优化**：
```sql
-- 使用 IVF (Inverted File Index) + PQ (Product Quantization)
CREATE INDEX idx_code_chunks_embedding_ivfflat
ON code_chunks USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);  -- 聚类中心数量

-- 或使用分区表
CREATE TABLE code_chunks (
  id SERIAL,
  repo_id INT,
  file_id INT,
  embedding vector(1536),
  ...
) PARTITION BY HASH (repo_id);

-- 为每个分区创建独立的 HNSW 索引
```

**4. 缓存优化**：
```typescript
// 多级缓存
L1: 内存缓存（LRU, 100 条，5 分钟 TTL）
  ↓ miss
L2: Redis 缓存（1000 条，1 小时 TTL）
  ↓ miss
L3: 数据库查询
```

**5. 查询优化**：
```typescript

async function searchWithRerank(query: string, repoId: number) {
  // 第一阶段：向量检索 Top 100
  const candidates = await vectorSearch(query, repoId, 100);
  
  // 第二阶段：Rerank 模型精排 Top 20
  const reranked = await rerankModel.rank(query, candidates);
  
  return reranked.slice(0, 20);
}
```

**预期效果**：
| 指标 | 当前（5万行） | 优化后（100万行） |
|------|---------------|-------------------|
| 索引时间 | 45 分钟 | 2-3 小时（分布式） |
| 查询响应 | 1.2s | 1.5-2s |
| 存储空间 | 2 GB | 30-40 GB |
| 并发支持 | 10 | 50+ |

## 三、问题解决能力展示

### Q6: 遇到过最难的技术问题是什么？如何解决的？

**回答**（以 URL 智能推导为例）：

**问题背景**：
> "在实现 URL 智能推导时，我遇到了一个非常棘手的问题：如何处理嵌套的三元表达式和局部变量。"

**具体场景**：
```typescript
function getUserData(userId: string, includeOrders: boolean) {
  const basePath = ApiPaths.users.detail(userId);
  return includeOrders ? `${basePath}/orders` : basePath;
}
```

**挑战**：
1. `basePath` 是局部变量，需要先解析 `ApiPaths.users.detail(userId)`
2. `ApiPaths.users.detail` 是对象方法调用，需要导航到嵌套属性
3. 三元表达式嵌套在模板字符串中，简单的正则匹配会失败
4. 需要求值三元表达式的条件（`includeOrders` 的值）

**尝试 1：简单正则匹配**
```typescript
// 失败：无法处理嵌套的反引号
const ternaryMatch = value.match(/(.+?)\s*\?\s*(.+?)\s*:\s*(.+)/);
```
**问题**：当 trueValue 或 falseValue 包含反引号时，匹配错误

**尝试 2：递归解析**
```typescript
// 失败：无法正确处理深度
function parseTernary(expr: string) {
  const questionIndex = expr.indexOf('?');
  const colonIndex = expr.indexOf(':');
  // ...
}
```
**问题**：嵌套结构中的 `?` 和 `:` 会被误识别

**最终方案：状态机解析**
```typescript
function parseTernaryExpression(expr: string) {
  let depth = 0;
  let inBacktick = false;
  
  // 跟踪括号和反引号的深度
  for (let i = 0; i < expr.length; i++) {
    const char = expr[i];
    
    if (char === '`') {
      inBacktick = !inBacktick;
    } else if (!inBacktick) {
      if (char === '(' || char === '{') depth++;
      else if (char === ')' || char === '}') depth--;
      else if (char === '?' && depth === 0) {
        // 找到顶层的 ? 操作符
        questionMarkIndex = i;
        break;
      }
    }
  }
  // ... 同样的方式找到 : 操作符
}
```

**关键突破**：
- 使用状态机跟踪嵌套深度
- 只在深度为 0 时识别操作符
- 区分"在反引号内"和"在反引号外"

**结果**：
- 成功处理所有嵌套场景
- 准确率从 80% 提升到 95%
- 代码可读性和可维护性都很好

**经验教训**：
1. **不要过度依赖正则表达式**：复杂的嵌套结构需要状态机
2. **逐步迭代**：从简单场景开始，逐步支持复杂场景
3. **充分测试**：准备各种边界情况的测试用例
4. **深入理解问题**：理解 JavaScript 的语法规则，而不是盲目尝试

## 六、面试技巧总结

### 6.1 回答问题的框架

**STAR 法则**：
- **S**ituation：背景和场景
- **T**ask：任务和目标
- **A**ction：采取的行动
- **R**esult：结果和影响

**技术问题的回答结构**：
1. **问题背景**（10%）：简要说明问题的背景
2. **技术挑战**（20%）：详细阐述技术难点
3. **解决方案**（40%）：重点讲解你的方案
4. **效果验证**（20%）：用数据说话
5. **经验总结**（10%）：提炼关键经验

### 6.2 展示技术深度的技巧

**1. 用数据说话**：
- ❌ "性能提升很多"
- ✅ "性能从 16-19 分钟优化到 98 秒，提升了 10-12 倍"

**2. 展示思考过程**：
- ❌ "我用了 HNSW 索引"
- ✅ "我对比了 HNSW 和 IVF 两种索引，HNSW 在准确率和查询速度上都更优，所以选择了 HNSW"

**3. 承认不足**：
- ❌ "我的方案是完美的"
- ✅ "当前方案在 100 万行代码时会遇到性能瓶颈，下一步计划引入分布式索引"

**4. 展示学习能力**：
- ❌ "我一开始就知道怎么做"
- ✅ "我经历了 4 次迭代，每次都从失败中学到新东西，最终才达到 95% 的准确率"

### 6.3 常见陷阱

**陷阱 1：过度技术化**
- ❌ 讲太多底层实现细节，面试官听不懂
- ✅ 先讲清楚问题和方案，面试官感兴趣再深入

**陷阱 2：缺乏数据支撑**
- ❌ "性能很好"、"用户很满意"
- ✅ "P99 响应时间 4 秒"、"用户满意度 4.5/5 分"

**陷阱 3：回避问题**
- ❌ "这个问题我没遇到过"
