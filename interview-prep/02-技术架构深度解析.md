**设计理念（逐条对应真实实现）：**
- **分层解耦**：每层职责清晰，检索层不依赖编排层，因此本次引入 LangGraph 时检索代码**一行未改**
- **通信方式**：Web 前端与 API 之间是 HTTP 请求-响应；API 内部各层是**直接函数调用**（非事件驱动）
- **缓存优先**：`MultiStrategySearch` 内置 LRUCache（100 条 / 5 分钟 TTL），命中即跳过整条检索链路
- **渐进式增强**：真实的演进路径是「单策略精确匹配 → 多策略动态加权融合」；
  **多轮重检索是本次新增的能力**，通过 LangGraph 条件边实现，而非既有能力

**关键设计一：解析用 ts-morph，而不是正则。**

```typescript
export class ASTAnalyzer {
  private project: Project;

  constructor() {
    this.project = new Project({
      compilerOptions: {
        target: ts.ScriptTarget.Latest,
        module: ts.ModuleKind.CommonJS,
        allowJs: true,      // 同时支持 JS 文件
        checkJs: false,     // 不做类型检查，只要结构
        noEmit: true,
      },
      skipAddingFilesFromTsConfig: true,   // 不加载 tsconfig，避免解析被中断
    });
  }

  async analyzeFile(filePath: string, content: string): Promise<ASTAnalysisResult> {
    const sourceFile = this.project.createSourceFile(filePath, content, { overwrite: true });
    // 1. 导入关系  2. 字符串常量  3. 从常量提取 URL 模式
    // 4. 函数信息  5. 类信息      6. 清理资源（避免内存泄漏）
    /* ... */
  }
}
```

`analyzeFile` 的输出结构是 `ASTAnalysisResult`，包含
`StringConstant[]`、`URLPattern[]`、`FunctionInfo[]`、`ClassInfo[]`、`ImportInfo[]`
五类实体 —— 正好对应数据库里的五张实体表。

**关键设计二：索引入队走队列，不阻塞请求。**

```typescript
// queue.ts
export const indexQueue = new Queue('index-repo', { connection });

export type IndexJobData / IncrementalIndexJobData / RefreshJobData / ReindexJobData
export function startIndexWorker()
export function enqueueIndexJob(data: IndexJobData)
export function enqueueIncrementalIndexJob(data: IncrementalIndexJobData)
export function enqueueRefreshJob(data: RefreshJobData)
export function enqueueReindexJob(data: ReindexJobData)
```

**四种任务的区分是刻意设计的**：全量重建（贵）、增量单文件（便宜）、
刷新（GitLab 拉最新后重跑）、重索引（换模型/换维度后必须整库重算）。
这比「一个 index 接口包打天下」更容易做限流与优先级。

**工程取舍：**
- **增量优先**：`indexSingleFile` / `indexMultipleFiles` 只处理变化文件，避免全量重建
- **批量 embedding**：合并请求降低 DashScope 调用次数
- **重索引是一等公民**：`002` 迁移改向量维度后，必须能一条命令重算整库 —— 这就是
  `reindexGitLabRepo` 存在的原因

### 2.2 URL 智能推导模块 (url-derivation.ts)

> 真实文件：`apps/api/src/retrieval/url-derivation.ts`，**1571 行**，是整个项目最大的单个文件。
> 它解决的问题是：**用户给了一个具体 URL，我要找出它是哪几行代码拼出来的。**

这是「结构性可达性」问题最纯粹的形态。向量检索在这里几乎无用 ——
`/api/users/123` 和代码里的 `${BASE}/users/${id}` 在语义空间里并不相似，
但它们在**构造链**上是一回事。

**核心函数签名与返回结构：**

```typescript
export interface URLDerivationResult {
  pattern: string;              // 推导出的 URL 模式，如 "/api/users/:id"
  confidence: number;           // 置信度 (0-100)
  symbolChain: Array<{          // 符号依赖链 —— 直接给用户看「证据链」
    symbol: string; file: string; line: number; value: string;
  }>;
  derivationSteps: Array<{      // 逐步推导过程，可回放
    step: number; description: string; from: string; to: string;
  }>;
  missingSymbols: string[];     // 无法解析的变量（诚实地暴露不确定性）
}

export async function deriveURLConstruction(
  db: Pool,
  repoId: number,
  targetUrl: string
): Promise<URLDerivationResult[]>
```

**五步推导算法（源码注释原文结构）：**

```typescript
export async function deriveURLConstruction(db, repoId, targetUrl) {
  // 步骤 1: 从数据库构建符号表
  //   符号表包含所有 URL 相关的常量、函数、对象
  const symbolTable = await buildSymbolTable(db, repoId);

  if (Object.keys(symbolTable).length === 0) return [];   // 早退，避免空转

  // 步骤 2: 查找入口点（可能包含目标 URL 的符号）
  //   入口点靠「路径段匹配」识别，而不是靠语义
  const entryPoints = findEntryPoints(targetUrl, symbolTable);
  if (entryPoints.length === 0) return [];

  // 步骤 3: 从每个入口点递归推导（展开 dependsOn，构建 symbolChain）
  // 步骤 4: 计算置信度（按匹配程度评分）
  // 步骤 5: 按置信度降序排序返回
}
```

**符号的建模方式（这是能递归的前提）：**

```typescript
interface Symbol {
  id: string;                                        // "const:API_URL"
  name: string;
  value: string;
  type: 'constant' | 'function' | 'template';
  dependsOn: string[];       // ← 依赖指向其它符号 id，形成有向图
  returns?: string;          // 函数类型才有
  file: string;
  line: number;
}
```

把「常量、函数、模板」统一抽象成带 `dependsOn` 的图节点之后，
推导就退化成一个**带环检测的图遍历** —— 这也是为什么它需要 1571 行：
真实的代码里充满了循环依赖、条件分支、多层函数嵌套。

**难点（也是面试可讲的深度点）：**
- **跨文件追踪**：符号表是全局的，要能跨 module 解析 import/export 后的名字变化
- **嵌套展开**：`${BASE}${VERSION}/users` 这类嵌套模板要递归到底
- **条件表达式**：`isProd ? API_PROD : API_DEV` 要按分支分别产出候选 URL
- **动态路径参数**：`/users/123` → 反推 `/users/:id` 模式
- **环检测**：`A dependsOn B` 且 `B dependsOn A` 时必须终止（这是 1571 行里最容易被忽略的部分）
- **诚实报告缺失**：`missingSymbols` 显式列出解析不了的变量，
  而不是猜一个值糊过去 —— 这个设计选择在面试里很加分

**配套的另外两个文件：**
- `url-template-matcher.ts`（338 行）：`matchURLTemplate` / `isTemplate` /
  `extractTemplateVars` / `calculateURLSimilarity` —— 负责「模式 ↔ 具体 URL」的双向匹配与相似度
- `url-search.ts`（1,336 行）：`searchURL(db, repoId, query, limit)` —— URL 类查询的专用检索通道，
  `MultiStrategySearch` 判定 `intent.type === 'url'` 后直接走这里

### 2.3 多策略搜索引擎 (MultiStrategySearch)

> 真实文件：`apps/api/src/retrieval/multi-strategy-search.ts`（约 1,279 行）。
> 这是整个项目**最核心的技术资产**，也是本次 LangGraph 改造中刻意保持不动的部分。

**职责：**
- 融合 5 种搜索策略（vector / exact / fuzzy / dependency / graph）
- 按查询意图**动态**调整各策略权重
- 结果去重、加权合并、阈值过滤
- 拼写纠错、搜索建议、上下文增强、LRU 缓存

**策略融合算法（真实实现，节选）：**

```typescript
export class MultiStrategySearch {
  private dependencyTracker: DependencyTracker;
  private searchCache: LRUCache<SearchResult[]>;  // 100 条 / 5 分钟 TTL
  // 注：这里原有一个 `private anthropic: Anthropic` 字段 ——
  //     它只赋值、从不读取（本类从不发起 LLM 调用），
  //     切换 LLM 厂商时已删除；构造函数第二参数现为有意不用的 `_llmApiKey`。

  async search(repoId: number, query: string, options: SearchOptions = {}) {
    const response = await this.searchWithSuggestions(repoId, query, options);
    return response.results;
  }

  async searchWithSuggestions(repoId, query, options = {}) {
    const { limit = 20, threshold = 0.5,
            strategies = ['vector', 'exact', 'fuzzy'],
            includeContext = true, followDependencies = false } = options;

    // 1. 拼写纠错
    const { corrected, hasCorrected } = correctTypos(query);
    const searchQuery = hasCorrected ? corrected : query;

    // 2. 缓存命中则直接返回
    const cacheKey = generateCacheKey('search', { repoId, query: searchQuery, ...options });
    const cached = this.searchCache.get(cacheKey);
    if (cached) return { results: cached };

    // 3. 意图识别 —— 决定后面用哪些策略、怎么加权
    const intent = await this.analyzeQueryIntent(searchQuery);

    // 4. URL 类查询走专用通道（url-search.ts），不做重量级推导
    if (intent.type === 'url') {
      const urlResults = await searchURL(this.db, repoId, query, limit);
      /* ...转换为统一的 SearchResult 后直接返回... */
    }

    // 5. 按意图裁剪策略集，并行执行
    const selectedStrategies = this.selectStrategies(intent, strategies);
    const searchResults = await Promise.all(
      selectedStrategies.map(s => this.executeStrategy(repoId, query, intent, s, limit))
    );

    // 6. 加权合并且排序
    const mergedResults = this.mergeResults(searchResults, intent);

    // 7. 阈值过滤 → 上下文增强 → 去重 → 生成建议
    const filteredResults = mergedResults.filter(r => r.score >= threshold);
    if (includeContext) await this.enrichWithContext(repoId, filteredResults);
    /* ... */
  }
}
```

**关键设计点一：权重随意图变化，不是固定值。**

```typescript
private mergeResults(resultSets: SearchResult[][], intent: QueryIntent): SearchResult[] {
  const merged = new Map<string, SearchResult>();

  // 权重表本身依赖 intent —— 这是「动态加权」的真实含义
  const weights: Record<string, number> = {
    vector:     intent.type === 'general' ? 1.0 : 0.8,
    exact:      intent.confidence > 0.8 ? 1.2 : 0.9,
    fuzzy:      0.7,
    dependency: intent.type === 'url' ? 1.1 : 0.8,
    graph:      intent.type === 'function' ? 1.1 : 0.8,
  };

  resultSets.forEach(results => {
    results.forEach(result => {
      const key = `${result.filePath}:${result.lineStart}`;   // 去重键
      const weight = weights[result.metadata.strategy] || 1.0;
      const weightedScore = result.score * weight;

      if (merged.has(key)) {
        // 被多个策略同时命中 → 视为更强信号，取较大值再 +0.1 加成
        const existing = merged.get(key)!;
        existing.score = Math.max(existing.score, weightedScore) + 0.1;
      } else {
        merged.set(key, { ...result, score: weightedScore });
      }
    });
  });

  return Array.from(merged.values()).sort((a, b) => b.score - a.score);
}
```

> 面试时可直接指出这个设计的好处：**多策略交叉命中会获得额外加成**，
> 相当于用「独立性」当作隐式的置信度信号 —— 单策略高分不如多策略同时命中可信。

**关键设计点二：URL 查询走专用通道。**

意图分类一旦判定为 `url`，就不走通用多策略路径，而是直接调用 `url-search.ts`（1,336 行），
由它去查 `url_patterns` / `url_usages` 表并做路径匹配。这是「结构性可达性」与「语义相似」
两类问题被分开处理的第一个分界点。

**策略详解（权重为基准值，实际由 intent 动态覆盖）：**

| 策略 | 适用场景 | 基准权重 | 优势 | 劣势 |
|------|---------|---------|------|------|
| 向量搜索 vector | 语义相似查询 | 0.8 ~ 1.0 | 理解意图，容错性强 | 计算开销大 |
| 精确匹配 exact | 已知完整路径/名称 | 0.9 ~ 1.2 | 速度快，准确率高 | 无容错能力 |
| 模糊匹配 fuzzy | 部分路径、拼写不确定 | 0.7 | 支持容错，灵活 | 可能返回过多结果 |
| 依赖感知 dependency | 关联代码查询 | 0.8 ~ 1.1 | 发现隐藏关联 | 依赖图需预先构建 |
| 图遍历 graph | 调用链查询 | 0.8 ~ 1.1 | 深度挖掘调用关系 | 复杂度高 |

### 2.4 Agent 编排层：从单轮管道到 LangGraph 有环图

> 真实文件：`apps/api/src/agent/core.ts`（701 行）、`apps/api/src/agent/graph/*.ts`（540 行）。
> 这一节是本次改造的**主战场**，也是最容易被面试官追问的地方 —— 口径必须准确。
> 完整叙述见 `04-AgentRAG架构升级.md`。

#### 2.4.1 改造前：一个诚实的单轮管道

改造前的 `AgentCore` **没有**多轮循环、没有工具注册表、没有反思模块。
它的 `query()` 是一条直线的三步流程：

```
用户问题
   │
   ├─ 1. classifyIntent(query)        → 判定 url / function / class / general
   │
   ├─ 2. multiStrategySearch.search() → 拿一批证据（URL 类走 url-search 通道）
   │
   └─ 3. answerQuestion(query, ev)    → 拼提示词，调 LLM（默认 DeepSeek），出答案
```

同时代码库里存在 5 个**只有类声明、没有任何方法体**的占位类：
`TaskPlanner`、`ReasoningEngine`、`ContextManager`、`ReflectionEngine`、`ToolRegistry`。
它们被 `index.ts` 导出，看起来像一套完整的 Agent 架构，实际从未被任何一处调用。

同样地，`config.ts` 里 7 个配置项只有 3 个真正被读取
（`toolTimeout`、`llmModel`、`temperature`），
`maxReasoningRounds`、`confidenceThreshold`、`enableReflection`、`enableLearning`
这 4 个**没有任何代码读取它们** —— 因为它们对应的功能不存在。

**这就是改造的起点：先承认现状，再动手术。** 本次做了两件事：

1. **消除误导**：5 个空类改为 `@deprecated` 并在构造函数直接抛错；设计意图迁移到
   `docs/agent-unimplemented-design.md`；`config.ts` 逐项标注「是否被读取」。
2. **补齐真实能力**：用 LangGraph 把「证据不足 → 换策略重检索」这条**环**真正实现出来，
   顺手把 4 个死配置中的 2 个接上（`maxReasoningRounds`、`confidenceThreshold`）。

#### 2.4.2 改造后：LangGraph 状态图

拓扑只有 3 个节点和 1 条条件边：

```
                 ┌──────────────────────────────────┐
                 │   证据不足 且 轮次未用尽 → 回退     │
                 ▼                                  │
START ──→ retrieve ──→ grade ────────────────────────┘
                          │
                          └──→ generate ──→ END
```

**状态定义（`agent/graph/state.ts`）** —— 用 `Annotation.Root` 声明，全部流转信息显式化：

```typescript
export const GraphState = Annotation.Root({
  query:               Annotation<string>(),
  repoId:              Annotation<number>(),
  sessionId:           Annotation<string>(),
  evidence:            Annotation<GraphEvidence[]>({ reducer: concat, default: () => [] }),
  strategiesUsed:      Annotation<string[]>({ reducer: uniqueConcat, default: () => [] }),
  round:               Annotation<number>({ reducer: (_p, n) => n, default: () => 0 }),
  maxRounds:           Annotation<number>(),
  sufficiency:         Annotation<number>({ reducer: (_p, n) => n, default: () => 0 }),
  sufficiencyThreshold: Annotation<number>(),   // 放进状态而非闭包，checkpoint 才可复现
  confidence:          Annotation<number>({ reducer: (_p, n) => n, default: () => 0 }),
  trace:               Annotation<string[]>({ reducer: concat, default: () => [] }),
});
```

**逐轮升级的检索策略表（`agent/graph/nodes.ts`）** —— 这是「不引入 LLM 规划」的刻意取舍：

```typescript
export const SEARCH_STRATEGY_PLAN = [
  { name: 'r1_vector_exact',      // 第 1 轮：偏精准，宁缺毋滥
    options: { limit: 10, threshold: 0.3, strategies: ['vector', 'exact'],
               includeContext: true } },
  { name: 'r2_with_dependency',   // 第 2 轮：顺调用图扩大召回
    options: { limit: 15, threshold: 0.25, strategies: ['vector', 'dependency'],
               includeContext: true, followDependencies: true } },
  { name: 'r3_broad',             // 第 3 轮：全策略 + 降阈值，尽量兜住
    options: { limit: 20, threshold: 0.2, strategies: ['vector', 'exact', 'fuzzy', 'graph'],
               includeContext: true } },
];
```

为什么用有序表而不是让 LLM 规划？**行为可预测、成本可估计、失败模式清晰**。
后续若要接入 LLM 规划，只需替换这张表的查表逻辑，节点契约不变。

**条件边：收敛性的保证（`agent/graph/nodes.ts`）**

```typescript
// 纯函数 —— 只看状态，不依赖任何闭包变量
export function routeAfterGrade(state: GraphStateType): 'retrieve' | 'generate' {
  if (state.sufficiency >= state.sufficiencyThreshold) return 'generate';
  if (state.round >= state.maxRounds) return 'generate';   // ← 先查轮次上限
  return 'retrieve';
}
```

判定顺序刻意**先查轮次上限**：即使在「充分度永远不达标」的最坏情况下，流程也必然终止。
这里踩过一个真实的坑 —— 终节点最初命名为 `answer`，而状态里已有一个 `answer` 通道，
LangGraph **不允许节点名与通道名重复**：`tsc` 编译通过，但 `compile()` 时抛
`answer is already being used as a state attribute (a.k.a. a channel)`。
最终把节点改名为 `generate`，这也是为什么源码注释里专门留了一段提醒。

**轮次上限的取舍（`agent/graph/index.ts`）**

```typescript
const maxRounds = Math.max(
  1,
  Math.min(config.maxReasoningRounds, SEARCH_STRATEGY_PLAN.length)
);
```

策略表定义了**互不相同**的检索手段，用尽后再重复最后一档只是白花钱、几乎不带来新证据。
所以想跑更多轮，正确的做法是往策略表里补策略，而不是把 `maxRounds` 调大。

#### 2.4.3 可测试性：依赖注入换来的确定性

图构建函数接受可注入的 `search` 与 `generateAnswer`：

```typescript
export async function createCodeLensGraph(deps: {
  pool: Pool;
  // 变量名为历史遗留，实际是「当前 LLM 客户端」而非 Anthropic 专用
  anthropicApiKey: string;
  search?: MultiStrategySearch;      // 默认 new MultiStrategySearch(...)
  generateAnswer?: GenerateAnswerFn; // 默认走 llm/qa.answerQuestion

```

这不是为了「架构好看」，而是**为了让环能被测试**：
本地没有 PostgreSQL 时，注入一个 stub `search`（按轮次返回不同数量的证据），
就能完整验证「证据不足 → 重检索 → 证据够了 → 生成」这条路径，
以及 `maxRounds` 取 1~6 时的收敛行为。这部分断言落在
`apps/api/src/scripts/verify-graph.ts`（`pnpm verify:graph`，共 30 条断言）。

#### 2.4.4 边界：图没有替换任何现有路由

| 路由 | 实现 | 状态 |
|------|------|------|
| `POST /ask` | 原单轮管道 | 行为不变 |

### 3.2 索引策略

**HNSW 参数含义（`code_chunks`）：**
- `m = 16`：每个节点的最大连接数，越大精度越高、内存越高
- `ef_construction = 64`：构建期搜索深度，越大索引越准、构建越慢
- 查询期可用 `SET hnsw.ef_search` 调整召回与延迟的平衡

**ivfflat 参数含义（其他向量表）：**
- `lists = 100`：聚类中心数量。经验值约 `rows / 1000`，当前规模是合理起点
- 查询期 `ivfflat.probes` 控制扫描的簇数量，是召回/延迟的旋钮

**索引维护策略：**
- **批量删除走「先删索引 → 删数据 → 重建」**：因为 HNSW 删除需要重平衡图结构，逐行删极慢
- **增量更新**：小批量直接 upsert（靠 `003` 迁移补的 UNIQUE 索引支持 `ON CONFLICT`）
- **定期重建**：碎片化后重建索引恢复查询性能

## 四、技术栈选型理由

### 4.1 为什么选择 PostgreSQL + pgvector？

**对比其他方案：**

| 方案 | 优势 | 劣势 | 为何不选 |
|------|------|------|----------|
| **PostgreSQL + pgvector** | 关系数据 + 向量搜索一体化，ACID保证，成熟生态 | 向量搜索性能略逊专用库 | ✅ **已选择** |
| Pinecone | 向量搜索性能极佳，全托管 | 纯向量库，无关系查询，成本高 | 需要关系查询能力 |
| Milvus | 开源，性能好 | 部署复杂，需要额外维护 | 增加运维负担 |
| Elasticsearch | 全文搜索强大 | 向量搜索支持较弱 | 向量搜索是核心需求 |
| Qdrant | 向量搜索优秀 | 生态不成熟，社区小 | 风险较高 |

**选择理由：**
1. **一体化存储**：关系数据（路由、依赖）+ 向量数据在同一数据库，避免数据同步问题
2. **ACID保证**：事务支持确保数据一致性
3. **成本低**：开源免费，无需额外付费服务
4. **生态成熟**：丰富的工具和库支持

### 4.2 LLM 选型：当前为 DeepSeek（原选型 Claude Sonnet 4.6）

> ⚠️ **口径更新（重要）**：本项目**当前实际使用的是 DeepSeek `deepseek-chat`**，
> 经 `apps/api/src/llm/client.ts` 适配层接入（OpenAI 兼容协议，复用已装的 `openai` 包，零新增依赖）。
> Anthropic Claude 作为**回滚路径**保留（`LLM_PROVIDER=anthropic` 即切回）。

**对比（Claude 现为候选/回滚项）：**

| 模型 | 上下文长度 | 推理能力 | 工具调用 | 成本 | 备注 |
|------|-----------|---------|---------|------|---------|
| **DeepSeek `deepseek-chat`** | — | ⭐⭐⭐⭐ | — | 低 | ✅ **当前使用**（另有 `deepseek-v4-pro` 推理模型可选）|
| Claude Sonnet 4.6 | 200K | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 中 | 回滚路径（`ANTHROPIC_*`）|
| GPT-4 Turbo | 128K | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 高 | 成本高，上下文短 |
| GPT-3.5 Turbo | 16K | ⭐⭐⭐ | ⭐⭐⭐ | 低 | 推理能力不足 |
| Llama 3 70B | 8K | ⭐⭐⭐ | ⭐⭐ | 低 | 上下文太短 |

**真正值得讲的是「可切换」这件事（加分项）**：
换厂商只改了**一个环境变量 + 一个适配层文件**，3 处调用点
（`qa.ts`×2、`agent/core.ts`×1）与业务代码**一行都没动**。
原因是适配层对外暴露与 Anthropic Messages API **同形状**的
`client.messages.create({ model, max_tokens, system, messages })`，
并把历史上写死的 `claude-sonnet-4-6` 归一化成「当前厂商的默认模型」。

> ⚠️ **口径提醒**：不要因为「曾经用 Claude」就宣称用过 Claude 的原生能力
> （如 function calling）——**本项目当前没有使用工具调用**
> （`ToolRegistry` 是抛错的占位符）。

### 4.3 为什么选择 Alibaba DashScope Embedding？

**对比其他embedding服务：**

| 服务 | 维度 | 性能 | 成本 | 中文支持 | 为何选择 |
|------|------|------|------|---------|---------|
| **DashScope `qwen3.7-text-embedding`** | 1024（指定 **1536**） | ⭐⭐⭐⭐⭐ | 低 | ⭐⭐⭐⭐⭐ | ✅ **当前使用** |
| OpenAI text-embedding-3-large | 3072 | ⭐⭐⭐⭐⭐ | 高 | ⭐⭐⭐ | 成本高，中文一般 |
| OpenAI text-embedding-3-small | 1536 | ⭐⭐⭐⭐ | 中 | ⭐⭐⭐ | 中文支持不如DashScope |
| Cohere embed-multilingual | 1024 | ⭐⭐⭐⭐ | 中 | ⭐⭐⭐⭐ | 维度较低 |

> ⚠️ 嵌入模型**与 LLM 厂商无关**（DeepSeek 不提供嵌入模型），所以换 LLM 时
> `EMBED_*` 一个字都不用改。反过来，**真要换嵌入模型必须重刷全部向量**——
> 维度对得上不代表语义空间可比（实测过相似度 0.036 的静默失效）。

**选择理由：**
1. **中文优化**：针对中文语义理解优化，适合国内项目
2. **成本低**：比OpenAI便宜约50%
3. **性能优秀**：1536维度，语义表达能力强
4. **稳定性好**：阿里云基础设施，国内访问快

> 真实时间线以 git 为准：`Initial commit: CodeLens 代码智能问答平台` 为 2026-04-26，
> 末次提交 2026-05-13，全程 **67 次提交、约 3 周**。

### 5.1 阶段一：精确匹配（2026-04-26 起）

```
用户查询 → 精确路径/名称匹配 → 返回结果
```

**问题：** 只支持字面匹配，用户必须知道确切名称，语义相近的查询完全查不到。

### 5.2 阶段二：引入向量搜索（2026-04 末）

```
用户查询 → 1536 维向量 → pgvector 相似度检索 → 返回结果
```

**改进：** 支持语义相似查询，不再要求用户记住确切名字。

**新问题：** 向量检索对**结构性查询**（精确 URL、函数名、调用链）反而不如字面匹配准，
而且会返回一堆「语义像但不是要找的那个」的结果。

### 5.3 阶段三：多策略动态加权融合（2026-04-29）

`001_enhanced_schema.sql` 落地（2026-04-29，提交信息
`fix: resolve TypeScript compilation errors in enhanced search system`），
从「多张实体表 + 5 策略并行 + 按意图动态加权」重构整个检索层。

```
用户查询 → 意图识别 → [vector, exact, fuzzy, dependency, graph] 并行
        → 按 intent 动态加权合并（多策略交叉命中 +0.1 加成）→ 阈值过滤 → 返回
```

**改进：**
- 5 种策略按查询意图动态取权重（见 §2.3），不再是固定配比
- 引入 `url_patterns` / `url_usages` / `constant_references` 等结构性表，
  把「URL 是从哪几个常量拼出来的」这件事落了库

**新问题：** 一次查询只有**一轮**检索。如果第一轮证据不足，系统只能硬着头皮生成答案，
不会换一种策略再试 —— 这正是 Phase 4 要解决的。

### 5.4 阶段四：LangGraph 有环编排（2026-09，本次改造）

```
用户查询 → retrieve → grade ──┬─ 证据充分 ──→ generate → 返回
                              └─ 证据不足 ──→ 换策略回到 retrieve
```

**改进：**
- 引入**条件边**：证据不足时自动换下一档策略重新检索，最多 3 档
- 状态显式化（`GraphState`），全流程可落库、可审计、可续跑（可选 PostgresSaver）
- 接上原本「存在但无人读取」的两个配置：`maxReasoningRounds`、`confidenceThreshold`
- 用**可注入的检索/生成函数**换取可测试性，环的收敛行为有 30 条断言覆盖

**明确未做（别说过头）：**
- ❌ 没有 LLM 自主规划（策略表是写死的有序表）
- ❌ 没有工具调用（没有 tool-calling 循环）
- ❌ 没有自我反思（`ReflectionEngine` 仍是抛错的占位符）
- ❌ 没有多轮对话记忆（`ConversationMemory` 未接入）

| 操作 | 做法 | 原因 |
|------|------|------|
| 批量删除 | 先 DROP INDEX → 删数据 → 重建索引 | HNSW 逐行删除需重平衡图结构，极慢 |
| 增量更新 | 直接 upsert | `003` 迁移补了 UNIQUE 索引，支持 `ON CONFLICT` |
| 向量维度升级 | `002` 迁移显式清空 embedding 后重建 | 改列类型必须重算全部向量 |

> 「删除慢」这一段是真实的工程经验，比任何编造的加速倍数都更有说服力 ——
> 因为它解释了一个**具体的、非直觉的现象**。

---

## 七、架构优势总结

1. **分层解耦**：检索层不依赖编排层 —— 所以引入 LangGraph 时，4000 行检索代码一行未改
2. **多策略动态加权**：不是固定配比，权重由查询意图决定；多策略交叉命中额外加成
3. **结构性 + 语义性分离**：URL/调用链走专用通道（结构性可达性），概念查询走向量（语义相似度）
4. **编排层可测**：依赖注入让「证据不足 → 重检索」这条环在没有数据库的环境下也能被完整验证
5. **成本可控**：开源技术栈（PostgreSQL + pgvector）+ 国产 embedding，无托管向量库订阅费
6. **可演进**：策略表、节点契约、状态定义都是显式的，后续接 LLM 规划只换查表逻辑

**面试要点（对齐 `11-面试实战口径与拓展方案.md`）：**
- 强调 **4000 行手写检索** 是护城河，而不是把 LangGraph 当成卖点
- 突出 **「什么时候该手写、什么时候该用框架」的判断**，这是区分工程师层级的地方
- 讲 **真实的坑**（节点名与状态通道重名、HNSW 删除慢、没有标注集），不编量化结果
- 用 **「我没做 X，因为 Y」** 的结构结尾，比堆砌功能更显成熟
