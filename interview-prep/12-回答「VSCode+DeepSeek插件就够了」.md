# 12 - 回答「VSCode + DeepSeek 插件就够了」

> 这是 CodeLens 项目最可能被问、也最容易答砸的一道题。
> 本文给出的不是一套说辞，而是**一套判断**：哪些问题该让、哪些该争、凭什么争。
>
> 配套：`11-面试实战口径与拓展方案.md`（三幕叙事与总口径）、
> `test-repo/TEST_REPORT.md` §12（本文第九节引用的那次修复的完整记录）。

---

## 一、先看懂这道题在考什么

面试官问「我用 VSCode + DeepSeek 插件也能做」，通常不是真的在问技术可行性。
他在测三件事：

1. **你有没有想过自己的东西可以被替代**（还是说你把时间花在了一个别人一行配置就能替代的东西上）
2. **你分不分得清「能答」和「答得可信」**——这是资深与初级的分水岭
3. **你被质疑时是防守还是拆解**

所以最差的两种答法：

- **防守型**：「我的功能更多」——他会接着问「多在哪」，你列的功能他真能拼出来。
- **投降型**：「确实是，我这个主要是练手」——等于承认这个项目不值得写进简历。

**正确的起手是先把一半让出去。** 承认得越干脆，后面那段话的可信度越高。

---

## 二、把问题分三类（这是决定胜负的框架）

任何「XX 也能做」的质疑，都可以用这个框架拆：

| 类型 | 例子 | 谁更强 | 为什么 |
|---|---|---|---|
| **A. 局部上下文任务** | 解释这个文件、改这个函数、review 这段 diff | **插件**（不用争） | 编辑器里上下文就是眼前这几行，插件零成本拿到，我反而多一跳 |
| **B. 结构性可达问题** | 这个接口在后端哪定义、被谁调用、改这个函数影响谁 | **看规模分界** | 库里存着关系图就能查；只靠模型现读文件，规模一大就崩 |
| **C. 需要结论可复核的任务** | 线上事故排查、给同事解释改动范围、写进报告的结论 | **我** | 我的每一条是带 `file:line` 的证据，插件给的是「读起来对」的一段话 |

**关键的一句过渡话**：

> 「所以我不跟它争 A 类。我做的实际上是 B 和 C ——
> 而 B 和 C 的差别，越到真实规模、越到要说服别人的场合，才越明显。」

**把分界线定在「规模」和「可复核」上，而不是「谁更聪明」上** ——
后者你必输，因为用的是同一个 DeepSeek。

## 三、90 秒回答（逐句可用）

> **【让步】**
> 「这个类比其实是对的——对很多问题插件已经够了。所以我先划边界：
> 如果是『解释这个文件』『帮我改这个函数』『review 这段 diff』，
> 插件比我这套东西好用，因为它就在编辑器里，上下文就是眼前这几行。**这部分我不跟它争。**
>
> **【定位】**
> 但有一类问题，它的架构决定它答不好——不是模型不够强，是**它拿不到做这件事需要的数据**。
>
> **【举例，这一段是核心】**
> `"/api/v1/users/:id"` 这个接口在后端哪定义、被哪些前端代码调用。
> 你在 VSCode 里 grep 这个字符串，**结果是 0——因为这个字面量在任何文件里都不存在**。
> 实际代码是 `constants` 里 `const API_BASE = '/api/v1'`、`endpoints` 里
> `` `${API_BASE}/users` `` 再 re-export、`service.ts` 里
> `` fetch(`${USER_ENDPOINT}/:id`) ``，中间还跨了别名导入。
>
> 插件这时候只有两条路：让模型自己一轮一轮 grep，读到哪算哪——这在几百个文件以内还行，
> 真实仓库五万个文件它会绕进去，而且**每问一次都要重跑一遍**；或者直接编一个看起来合理的答案。
>
> **【我的做法】**
> 我的做法是**在入库的时候就把这件事算完**：AST 解析出每个字符串常量的定义点和引用点，
> 沿 import 关系把拼接链展开成带 `dependsOn` 的图，落成一张表——一个接口一行。
> 提问时我不用模型去猜，直接查表，返回的是**确定的构造链，每一步带 file 和 line**。
> 推导不出来的时候它不猜，返回 `missingSymbols` 告诉你缺哪个符号。
>
> **【收口】**
> 所以差别不是『我的模型更聪明』——**我用的是同一个 DeepSeek**。
> 差别是**结论的性质**：一边是模型生成的、读起来对的一段话；
> 另一边是可复核的、能点开看到第几行的证据。
> 平时这区别很抽象，但放到线上事故排查里，**你只能拿后者去说服别人**。」

**这段话为什么有效**：它没有反驳前提，而是**重新定义了比较的维度**；
中间那段 grep 结果 0 的例子是当场可验证的，面试官无法反驳；
收口的「同一个 DeepSeek」主动缴了械，反而让「结论性质不同」这个论点站住。

## 四、30 秒电梯版

> 「插件和我用的是同一个模型，差别不在模型，在**数据**。
> 插件每次现场读文件，我是在入库时就把跨文件的结构关系算成了图。
> 所以对『这个接口在哪定义、被谁调用』这类问题，它给我的是**推导链**，插件给的是**一段话**。
> 单文件任务我认它更强，仓库级问题我认我更强。」

---

## 五、四个可量化的支撑点（被追问时按需抛出）

**① 成本结构：索引一次 vs 每次重读**

> 「插件把命中的文件原文整段塞进上下文，一个仓库级问题很容易吃掉几万 token，
> 而且是**每问一次重复一次**。我这边索引是一次性成本，提问时只送 10 条白名单证据。
> 实测同一批查询，出网体积从 **198KB 压到 8KB**，约 24 倍。
> 顺带剔掉了 `embedding` 字段——原来 10/10 条都带着，模型根本不该看到数据库的原始行。」

> 📌 这是在 `/ask` 与 `/search` 共用的 evidence 白名单里做的（`server/evidence-mapper.ts`）。
> 修之前默认分支直接回原始 DB 行，`content` 字段是空的 —— 这同时修好了 Web 端证据面板里的
> 空白代码块（前端是按 `line_start` 去渲染代码的，`content` 为空就是一片空白）。

**② 能被回归测试，插件不能**

> 「我有一套能跑的评测集：URL 类 37 个用例、自然语言 19 个用例 + 3 个反例，
> 改完检索层必须重跑，覆盖率掉了就是回退。
> 插件没有『同一个问题应该返回同一批证据』这个概念，
> 所以**你没法判断它今天是不是变笨了**，只能靠感觉。」

**③ 结构性问题向量检索是原理性失效，不是精度不够**

> 「『这个接口在哪定义』是**结构性可达**问题。`/api/users/123` 和代码里的
> `` `${BASE}/users/${id}` `` 在语义空间里根本不相似。
> 所以纯向量在这里不是『差一点』，是原理上够不着——我才做了混合检索：
> 字面精确匹配 + 向量语义召回 + 依赖图追踪 + 调用图遍历，按查询意图加权融合。」

**④ 私有化部署 / 代码不出内网**

> 「插件把代码发到第三方。中大型团队的合规线通常不允许，
> 我整套是私有化部署的，索引和模型都可以在客户机房。」

> ⚠️ 第 ④ 点最弱（DeepSeek 也能私有化），只在对方主动提合规时用，别主动当主打。

## 六、必须主动让出去的（不说反而扣分）

**主动认输的地方，是你专业度的证据。**

| 要让的 | 怎么说 |
|---|---|
| **小仓库上插件确实够用** | 「几十个文件的库，说老实话插件够。我的东西是在**整库塞不进上下文之后**才开始赢的。」 |
| **Cursor 也在建索引** | 「所以我的差异**不在『我建了索引』**，在**结构化的关系层**：调用图、接口跨边界归属、影响面。这些是关系，不是向量。」 |
| **单文件/补全任务它更强** | 「补全、改函数这类我根本不做，也不该做。」 |
| **语言覆盖有限** | 「目前解析器支持 TS / JS / TSX / JSX 和 `.vue`，**Java / Python / Go 进不了库**。这是真实短板，接新语言要写新 parser。」 |
| **LangGraph 环路生产没开** | 「有环编排已经实现，但线上是环境开关关着的状态——**我不能说它线上在跑**。它是唯一『证据不足就重新检索』的机制，开关打开就生效。」 |

> 📌 最后两条尤其重要。**把边界说清楚，比把能力说满更有说服力**——
> 面试官一旦发现你有一处说满了，前面所有数字都会被重新怀疑。

## 七、追问连环预案

**Q1：「那你不就是个 RAG 吗？现在做 RAG 的一大把。」**

> 「是，检索增强本身不新鲜。但 RAG 的瓶颈从来不在『有没有检索』，在**检索质量能不能被量化**。
> 我举个我真实遇到的：我有一套评测集，换成真实语料后 `/ask` 的覆盖率从 100% 掉到 26%。
> 我**没有去调 prompt**，而是先把未命中拆成三类——
> 索引器没抽出来 / 抽了但没返回 / 关联层没覆盖——
> 最后一查，是**一条 SQL 的仓库范围谓词写在了 `code_chunks.repo_id` 上，而那一列全为 NULL**，
> 于是主表的向量召回**恒返回 0 行**。
> 它不报错、不告警、证据条数看起来还正常（10 条），只是答案变差了。
> 修完回到 100%。
>
> 这件事说明的是：**同一个问题在插件上你只会觉得『它今天不太行』，在我这儿它是一个能被定位、被修复、被回归的缺陷。**」

> 📌 这是全场最强的一段。详见 `test-repo/TEST_REPORT.md` §12，含三步定位法和修复前后对比。

**Q2：「五万个文件的仓库你怎么办？」**

> 「实话：我现在的实测语料是 277 个文件的真实工程，**没有在五万文件量级验证过**，
> 这一点我不能替它吹。但架构上是为这个量级设计的：
> 索引是一次性的、走队列削峰；查询侧全走数据库索引和向量索引，不随文件数线性变慢。
> 真正没解决的是**首次全量索引的时间**，那是要按小时计的。」

> ⚠️ **必须承认没验证过。** 说「没问题」会被追问细节，一次追问就崩。

**Q3：「效果怎么量化？」**

> 「我有两套口径，但**先说口径再看数字**。
> URL 类问题判『命中的 (文件, 行号) 是否落在期望符号区间内』；
> `/ask` 的证据是 chunk 加了 ±5 行上下文的区间，所以判**区间相交**。
> 数字：URL 36/37、搜索 18/19、问答覆盖 19/19 精确 16/19、三个反例 3/3 承认证据不足。
>
> **但这组数字的语料是我自己构造的**，问题基本照着代码出的，
> 所以它是**上界**，不是承诺。真实项目里我会先用一批真实工单问题重新量一遍。」

**Q4：「为什么不用 LangChain / LlamaIndex 现成的？」**

> 「检索层我用的是手写的——这一层是项目真正的壁垒，换掉是降级。
> 编排层我确实用了 LangGraph，但只换编排层，检索和分块一行没动。
> **知道什么时候不该用某个框架，和知道该用什么，同样是判断力。**」

**Q5：「那你这个项目最大的问题是什么？」**

> 「三个，按严重程度：
> 一、**只支持 TS/JS/Vue**，语言覆盖是真实项目的硬门槛；
> 二、**评测语料是我自己构造的**，有上界偏差，缺一批真实工单问题；
> 三、`/ask` 精确 16/19，剩下 3 条是**切块粒度**问题——
> 类级大块把里面的方法包住了，覆盖命中但精确定位不到那一行，要改 chunk 策略并重建索引。
> 这三个我都能说清代价和修法。」

> 📌 **主动说出三个真实问题**，是这道题的隐藏采分点：它证明你不是在背项目，是在维护项目。

## 八、口径红线（说了就被抓）

| ❌ 不能说 | ✅ 应该说 |
|---|---|
| 「我的准确率比插件高」 | 「我用的是同一个模型；差别在我给它的是可复核的证据」 |
| 「准确率 95%+」 | 「URL 36/37、搜索 18/19、问答 19/19 —— 且这是**自造语料的上界**」 |
| 「支持所有语言」 | 「TS/JS/TSX/JSX 和 `.vue`，其余要写 parser」 |
| 「有自主决策和多轮推理」 | 「多轮重检索已实现、开关控制；**自主决策和工具调用不存在**」 |
| 「线上跑了 LangGraph 环路」 | 「已实现 + 有断言验证，**生产开关未开**」 |
| 「插件做不到」 | 「插件在**单文件/小仓库**上更好；仓库级结构问题它拿不到数据」 |

> 📌 **「引用数据的一条硬规矩：只引用你能当场复现的数字。」**
> 本页所有数字都能现场重跑（评测脚本在 `test-repo/eval/`），所以都可以说。
> 凡是不能重跑的，一律不引用。

## 九、现场演示脚本（最强的一击）

如果面试官说「那你演示一下」，**别演示功能列表，演示这一个**：

```
① 在 VSCode 里对 /api/v1/users/:id 全局搜索  →  0 个结果
② 在 CodeLens 里问「/api/v1/users/:id 这个接口在哪里被调用」
   →  返回构造链 + 每个位置带 file:line
```

**为什么这个演示无懈可击**：

- 第 ① 步是他自己熟悉的工具、他自己看到 0 个结果，**前提是你和他一起确认的**
- 第 ② 步给的不是「更聪明的答案」，是**他刚才用 grep 拿不到的东西**
- 全程不需要贬低插件

**这个演示之所以成立，靠的是三件事都做了**：入库时建跨文件符号表、
索引跨过程调用点（业务方法只调自己的封装、路径模板处理器、版本循环路由这三类
「字面交集为零」的位置）、检索时把关联结果**排在直接命中之后且带标签**。

## 十、把「可回归评测」讲成壁垒（这道题真正的加分项）

大部分人答这道题会停在「我的检索更准」。**更高的位置是**：

> 「其实这道题的答案不在功能对比，在**谁来保证它没变坏**。
> 插件是个黑盒——它今天答得对不对，你只能靠感觉。
> 我这套东西有一条可回归的链路：评测集 → 覆盖率/精确率 → 未命中分类 → 定位到层 → 修复 → 重跑。
>
> 我刚才讲的那次修复就是这个链路跑通的例子：
> **一条写在恒为 NULL 列上的 SQL 谓词，让主表的向量召回静默返回 0 行**。
> 它不报错、日志正常、证据条数正常，唯一的症状是答案变差。
> 这种东西**只能在有评测集的项目里被发现**，也**只能在没有评测集的项目里长期存活**。
>
> 所以我的竞争力不是『我的模型更好』——我们用的是同一个。
> 是**我给这件事建了一套能发现和证明问题的机制**。」
