# 13 - 索引崩溃排查实录：一个文件如何让整仓索引归零

> 本文记录 2026-09-19 接入**真实前端工程**（`testwire-frontend`，1532 个可索引文件）时暴露的
> 两起事故。它们表面无关，**结构上是同一个错误**：
>
> **一条「按单个文件成立」的假设，被写进了「处理整仓」的循环里，而且失败是静默的。**
>
> 面试价值不在「我修了个 bug」，而在：
> ① 我用的**定位方法**（全量离线探针 + A/B 对照，而不是读代码猜）；
> ② 我识别出的**通用失效形状**（静默空转 / 连坐失败 / 启发式阈值单向验证）；
> ③ 修完之后我**主动做了「对已有语料是否中性」的验证**，避免了无谓的全量重建。
>
> ⚠️ **口径提醒**：本文所有数字都标注了验证方式或探针路径。
> 未实测的地方我会明确写「未测」，**请不要在面试中把它说成测过**。

---

## 一、事故 B：一个 `.vue` 文件让 1308 个文件的索引全部归零

（先讲这个 —— 它是用户实际看到「构建失败」的那次，也是最能体现排查方法的一起。）

### 1.1 现象

用户反馈：真实仓库接进来后**只显示 7 个文件** / 仓库页面显示**失败**。

查库看到的状态（这就是「看起来索引成功了，其实什么都没索引」的现场）：

| 表 | 行数 | 说明 |
|---|---|---|
| `files` | 1051 | 第一层（切块+向量）写入的 |
| `code_chunks` | 14084 | 第一层正常产出 |
| **`functions`** | **0** | ← 实体层完全没写 |
| **`url_patterns`** | **0** | ← 接口表完全没写 |
| **`url_usages`** | **0** | ← 使用点表完全没写 |
| **`call_graph`** | **0** | ← 调用图完全没写 |
| `repos.status` | `failed` | |

**关键判据：第一层有数、第二层全 0。** 这立刻把范围从「索引器整体坏了」缩小到
「增强索引（实体/关系层）在**一开始**就死了」。

### 1.2 日志里的真实死因

```
23:06:53  Full indexing completed for 1308 files      ← 第一层跑完（23 分钟）
23:06:53  Starting enhanced indexing (AST analysis)...
23:06:53  Indexing 1045 files...
23:06:56  Updated repo 33 status to 'failed'          ← 3 秒后就死了
```

错误栈（只有一行有效信息，但要会读）：

```
Job 67 failed: InvalidOperationError: Expected the module specifier to be a string literal.
    at ImportDeclaration.getModuleSpecifier (ts-morph)
    at ImportDeclaration.getModuleSpecifierValue (ts-morph)
    at URLResolver.indexFile               (indexing/languages/typescript/url-resolver.ts:286)
    at URLResolver.registerFiles           (:189)
    at ASTAnalyzer.registerRepoFiles       (languages/typescript/entities.ts:91)
    at RepoScope.begin                     (languages/typescript/index.ts:62)
    at Object.beginRepo                    (:142)
    at EnhancedIndexer.indexFiles          (indexing/enhanced-indexer.ts:166)
    at EnhancedIndexer.reindexRepository   (:828)
```

**从栈底往上看，看得出这是「第一步」**：`reindexRepository` → `indexFiles` →
**`beginRepo`**。也就是说，它死在整个增强索引的**建仓级上下文（跨文件符号表）**环节，
逐文件的实体抽取一行都还没跑。这解释了为什么实体表全是 0。

> 「3 秒就失败」本身也是线索：1308 个文件不可能在 3 秒内处理完 ——
> 说明它死在**一次性全仓扫描**里，不是死在逐文件循环里。

### 1.3 定位：不猜，写探针把它钉到「文件 + 行」

读代码能猜到「大概是某个 import 声明不规范」，但**猜不到是哪个文件**。
所以我没有去 grep `import` 语句 —— 而是写了个**离线探针**，把
`registerRepoFiles` 里对每个文件做的**同一个调用**重放一遍，逐文件 catch：

```js
// /tmp/find-bad-import.mjs（一次性探针，用仓库自带 ts-morph，只读）
for (const abs of files) {
  const sf = project.createSourceFile(abs, content, { overwrite: true });
  for (const imp of sf.getImportDeclarations()) {
    try { imp.getModuleSpecifierValue(); }        // ← 真实代码里抛的就是这一句
    catch (e) { bad.push({ file: rel, line: imp.getStartLineNumber(), text: ... }); break; }
  }
}
```

输出 —— **4 个元凶，全是 `.vue`，而且全是「模板/CSS 被当成代码」**：

| 文件 | 行 | 该行原文 | 真相 |
|---|---|---|---|
| `src/components/DataSetEditor/EditorWrapper.vue` | 32 | `@import="onImport"` | Vue **模板事件绑定** |
| `src/components/PlayWright/SelectorTree/Main.vue` | 12 | `@import="handleImport"` | 同上 |
| `src/components/PlayWright/SelectorTree/Import/Main.vue` | 60 | `.apiwire-playwright-selector-import {` | `<style>` 里的 **CSS 类选择器** |
| `src/components/PublicSetting/ImportScenario/Wrapper/Import.vue` | 69 | `.apiwire-importScenario-import {` | 同上 |

**根因**：TypeScript 的错误恢复机制会把 `@import="x"` / `import {` 这些片段
**合成一个 `ImportDeclaration` 节点**。正常情况下 import 的模块说明符必然是字符串字面量，
所以 `getModuleSpecifierValue()` 遇到这种「合成节点」就直接**抛异常**。

> 探针本身还踩了一个坑值得记：`imp.getModuleSpecifier().getKindName()`（我想打印节点类型）
> **也会抛**，因为它和 `getModuleSpecifierValue()` 是同一个判据。
> 结果探针在 catch 块里二次抛出、整个脚本挂掉 ——
> **排查工具自己崩了，会让人误以为「问题是全局的」**。教训：探针里每一个可能抛的调用都要单独兜。

### 1.4 为什么是「整仓归零」而不是「丢一个文件」

这是本起事故**最值得讲**的部分。`URLResolver.registerFiles()` 当时长这样：

```ts
registerFiles(files) {
  for (const f of files) this.files.add(f.path);
  for (const f of files) {
    const sf = this.project.createSourceFile(f.path, f.content, { overwrite: true });
    this.sources.set(f.path, sf);
    this.indexFile(sf, f.path);      // ← 这里有 4 个文件会抛
  }
  // 第二遍 / 第三遍...
}
```

**这个循环外面一层 try/catch 都没有**（调用链一路到 `EnhancedIndexer.indexFiles` 才被捕获），
于是：

```
1 个文件抛异常
  → registerFiles 中断
  → 符号表没建起来（providersByFile / indirectByFile 都是空的）
  → beginRepo 抛出
  → indexFiles 在第一步就终止
  → 1308 个文件的实体层/关系层 → 全部为空
```

**「连坐失败」：一个文件的格式问题，代价是整仓的检索能力。**

### 1.5 修复一：降级要「只降级这一个文件」，并且必须记账

第一处修复（`url-resolver.ts`）——**逐文件 try/catch，摘掉坏文件，继续跑，并逐条上报**：

```ts
const failed: Array<{ path: string; message: string }> = [];

for (const f of files) {
  try {
    const sf = this.project.createSourceFile(f.path, f.content, { overwrite: true });
    this.sources.set(f.path, sf);
    this.indexFile(sf, f.path);
  } catch (error) {
    // 从 sources 里摘掉，后面的 indexInstances 与逐文件查询会自然跳过它
    this.sources.delete(f.path);
    failed.push({ path: f.path, message: (error as Error)?.message ?? String(error) });
  }
}
// 第二遍同样处理；最后逐条打印：
// [URLResolver] 4/1310 个文件未能进入跨文件符号表（仅这些文件降级，其余照常）：
// [URLResolver]   跳过 src/components/.../Main.vue —— Expected the module specifier to be a string literal.
```

修复后探针实测（同一语料）：

```
--- A：喂 .vue 原文（旧行为）---
[URLResolver] 4/1310 个文件未能进入跨文件符号表（仅这些文件降级，其余照常）：
[URLResolver]   跳过 src/components/DataSetEditor/EditorWrapper.vue —— ...
[URLResolver]   跳过 src/components/PlayWright/SelectorTree/Import/Main.vue —— ...
[URLResolver]   跳过 src/components/PlayWright/SelectorTree/Main.vue —— ...
[URLResolver]   跳过 src/components/PublicSetting/ImportScenario/Wrapper/Import.vue —— ...
  provider 46 个 / 跨过程落点 95 个
```

**4/1310 降级，其余 1306 个照常** —— 这就是「降级不连坐」的效果。

### 1.6 修复二：把「模板/CSS 被当代码」从源头掐掉

只做修复一，那 4 个文件仍然进不了符号表（只是不再连坐）。
但**根因还在**：所有 `.vue` 的 `<template>` / `<style>` 都被当成 TS 解析了 —— 对 407 个 `.vue`
来说，这是持续的噪声来源（ts-morph 会从中抽出 `anonymous` 垃圾节点）。

项目里其实**早就有**正确答案：`sfc-host.ts` 的 `parseVueScriptBlocks()`。
而且它的注释里写着一条教义：

> ⚠️ **两遍索引都必须走这里**，理由不同但结论相同：
> 第一遍（`parseVueFile`）：Babel 需要的是纯 script 文本；
> 第二遍（实体层）：把 `.vue` 原文交给 ts-morph 会让 `<template>` 被当 TS 解析，产出大量
> `anonymous` 垃圾类；而且 ts-morph 在 `.vue` 扩展名下 `getReturnType()` 会抛异常。

**这条教义漏掉了第三处**：喂给「跨文件符号表」的这一遍。
`RepoScope.begin` 一直把 `.vue` **原文**直接递给解析器。

补上的实现（`languages/typescript/index.ts`）：

```ts
/** 把喂给跨文件符号表的源码规范成合法 TS */
export function toResolverSource(path, content) {
  if (!path.endsWith('.vue')) return { path, content };

  let blocks;
  try { blocks = parseVueScriptBlocks(path, content); }
  catch { return { path, content: blankLines(content) }; }

  // ⚠️ 关键：用**空行占位**，不是把 script 块拼起来
  const lines = content.split('\n').map(() => '');
  for (const block of blocks) {
    const blockLines = block.content.split('\n');
    for (let i = 0; i < blockLines.length; i++) {
      lines[block.offset + i] = blockLines[i];
    }
  }
  return { path, content: lines.join('\n') };
}
```

**为什么必须用「空行占位」而不是直接拼接 script 块**（这个设计点是加分项）：

符号表产出的 **provider / 间接调用点都带行号**，UI 上点一下要跳到 `.vue` 的对应行。
一个 SFC 可能有 `<script>` + `<script setup>` 两块，直接拼会让第二块的行号整体前移；
空行占位让 ts-morph 看到的文件**行号与 `.vue` 完全对齐**，后续不需要任何平移。

### 1.7 验证：A/B 对照，并且人工判读「是变干净了还是丢东西了」

改完不能只看「不崩了」，得看**产出变没变、变对没变对**。用探针做同语料 A/B：

```
--- A：喂 .vue 原文（旧行为）---  provider 46 个 / 跨过程落点 95 个
--- B：只留 script 块（新行为）---  provider 46 个 / 跨过程落点 96 个

provider 明细: 完全一致（46 条）
跨过程落点明细: 有差异 —— 仅旧行为 1 条 / 仅新行为 2 条
  − src/components/AutomatedTesting/TestScenario/Detail/Steps/Main.vue|177
  + src/components/PlayWright/SelectorTree/Main.vue|45
  + src/components/PublicSetting/ImportScenario/Wrapper/Import.vue|42
```

然后**逐条去代码里核对**（这一步不能省，否则分不清「变干净」和「丢数据」）：

| 差异 | 核对结果 | 判定 |
|---|---|---|
| **−** `AutomatedTesting/.../Main.vue:177` | 该文件 `<script setup>` 是 48–118 行，**177 行在 `<style lang="scss">` 里的 `@container` 规则中** | 旧行为**凭空编造**了一个调用点 → 删掉是对的 |
| **+** `PlayWright/SelectorTree/Main.vue:45` | `const { id, collection, getCollection, changeActive, handleImport } = context;`（`context = useContext(props)`） | 真实解构 → 之前整份文件被丢，现在**找回来了** |
| **+** `PublicSetting/.../Import.vue:42` | `const { checkPass, form, ... } = context;` | 同上 |

**结论：新行为严格更优** ——
① 新增 2 条真实落点（来自之前被整份丢弃的文件）；
② 删掉 1 条 CSS 里的幻觉落点；③ provider 46 条一字未变（无回归）。

### 1.8 顺带做的一件事：验证对「已有语料」是否中性

符号表是**增强层所有路径解析的地基**（provider / 间接落点 / import 三条线都从它出来），
数字一变，`url_patterns`、`url_usages`、间接调用点全都会跟着变。
所以改完必须回答：**已有的仓库要不要跟着重建索引？**（全量重建要 20+ 分钟 + 嵌入费用）

用同一个探针对既有语料跑 A/B：

| 仓库 | 文件 | provider 明细 | 跨过程落点明细 | 结论 |
|---|---|---|---|---|
| repo 29（`test-repo`，含 166 个 `.vue`） | 277 | 174 → 174 | 36 → 36 | **逐条完全一致** |
| repo 30（`fastify`，0 个 `.vue`） | 289 | 868 → 868 | 25 → 25 | **逐条完全一致** |

⇒ **对这两个仓库行为中性，不需要为这次改动重建它们的索引。** 只重建确实坏掉的 repo 33。

> 这就是「省时闸门」：**先用廉价探针证明 A==B，再决定要不要付重建代价。**
> 反过来，如果 A≠B，就必须重建，否则线上跑的是新代码、库里是旧代码的产物。

## 二、事故 A：压缩产物把索引「撑爆」（同一类问题的另一张脸）

这起事故是我在排查「仓库只显示 7 个文件」时先撞上的，也是它让真实工程有机会进入索引。

### 2.1 现象：45 个文件产出 52.8 MB 代码块正文

| 仓库 | 文件数 | 代码块正文合计 | 平均每个 chunk |
|---|---|---|---|
| repo 29 `test-repo` | 277 | 0.79 MB | 约 250 B（健康） |
| repo 30 `fastify` | 289 | 2.11 MB | 约 100–200 B（健康） |
| **repo 33（守卫前）** | **45** | **52.8 MB** | **约 37 KB（异常）** |

**判据不是「总量大」（45 个文件不该有 52.8 MB），而是「派生指标」：平均 chunk 正文大小。**
只看总量会被「文件少」掩盖；换成 `正文总量 / chunk 数`，异常立刻显形。
（面试点：**指标要算到二级，不要只看一级总量。**）

### 2.2 根因：AST 分块在压缩代码上会放大约 160 倍

元凶是 `public/static/monaco/` 下 vendored 的 Monaco 编辑器构建产物：

- `.../workerMain.js`：**308 KB / 23 行 / 最长行 156,899 字符**
- 解析本身不慢 —— `parseTsFile` 只要 **323 ms**
- 但 AST 分块在这类文件上会切出**跨越大段文本的 span**：
  实际产出 **878 个 chunk / 约 50.2 MB 正文**，相对原文件放大约 **160 倍**

后果是按小时计的嵌入耗时与费用，而产出**全是没人会检索的噪声**。

> 关键认知：**问题不在「文件大」，在「单行极长」。**
> 3 MB 的正常源码毫无问题；300 KB 的压缩文件能把内存和费用打爆。

### 2.3 修复：三层守卫（按代价递增，命中就逐条上报）

闸门只有一个：`indexing/file-scanner.ts`。原有的 `SKIP_DIRS` **只按目录名**判断，
抓不到「和源码混在一起」的产物（`public/static/` 里的 vendored 包、`src/assets/` 里生成的 iconfont）。

| 层 | 判据 | 代价 | 在本语料命中 |
|---|---|---|---|
| ③ | 路径特征：`public/(static\|assets\|build\|dist)/`、`*.min.{js,ts,tsx}`、`*.bundle.js`、`*.chunk.js` | 纯字符串比对 | 222 |
| ② | 单文件 > 1 MB | 用 `stat` 已拿到的 size，零成本 | 1 |
| ① | 压缩形态：**最长行 > 5000 且平均行 > 2000** | 需读文件 | 1 |

实测：**1532 个候选 → 拦下 224 个 → 索引 1308 个文件（3.60 MB 正文）**，
最大剩余文件是 229 KB 的 `src/types/PrimaryItemRawMap.d.ts`（类型声明，合理）。

### 2.4 这起事故里最值钱的判断：**「最长行」不能单独用**

第一版判据是「最长行 > 5000」。在真实语料上跑探针时发现它会**误杀一个真实源码文件**：

`src/utils/Json.ts` ——
**61 行的手写模块**（有 import、有 JSDoc、有导出函数），
只是**第 39 行内嵌了一个 65,554 字符的位图字符串常量**：

```ts
const txt = "0000000000000000000000000000000000003000000000002222222222000000033333333333333333333333333000030333..."
```

一刀切会把这个文件**整个丢掉**，连带里面几个正经函数一起消失。

所以判据改成**两个条件 AND**：`最长行 > 5000` **且** `平均行 > 2000`。
两者一下就分开了：

| 文件 | 行数 | 最长行 | 平均行 | 判定 |
|---|---|---|---|---|
| `src/utils/Json.ts` | 61 | 65,554 | **1,099** | **真源码 → 索引** |
| `.../workerMain.js` | 23 | 156,899 | ≈13,700 | 压缩产物 → 跳过 |
| `src/assets/icon/iconfont.js` | 1 | 784,438 | 784,438 | 压缩产物 → 跳过 |

**直观解释：压缩产物是「行少而总体量巨大」，所以平均行非常大；
带大字符串常量的真源码只是「某一行特别长」，整篇平均下来仍然正常。**

> ⚠️ 这里的通用教训（面试可直接讲）：
> **启发式阈值必须双向验证** —— 既要问「该拦的拦住了吗」，
> 也要问「**不该拦的有没有被误杀**」。只测前者，阈值会越调越激进。
> 而两类错误的代价不对称：**「该索引的没索引」比「多索引点噪声」危害大得多。**

### 2.5 顺带：守卫必须先验证「对老仓库是否中性」

同一个只读探针 `probe-index-guard.js` 跑既有语料：

- repo 29：**拦 0 个** ⇒ 中性 ⇒ 不必重建
- repo 30：**拦 0 个** ⇒ 中性 ⇒ 不必重建

⇒ 只有新接入的真实工程需要重建。**20 分钟的重建 × 3 个仓库，被一个探针省掉了 2/3。**

## 三、两起事故的共同结构（这是真正的面试答案）

如果面试官问「你从这个 bug 学到了什么」，**不要答具体的 `.vue` 语法**，
要答下面这个**可迁移的失效形状**：

> **一条「按单个文件成立」的假设，被写进了「处理整仓」的循环里，而且失败是静默的。**

| | 事故 A（撑爆） | 事故 B（归零） |
|---|---|---|
| 单文件假设 | 「文件大一点没关系，解析很快」 | 「文件能解析就能进符号表」 |
| 放进整仓循环后 | 压缩产物 × 878 个 chunk ⇒ 50 MB 噪声 | 1 个文件抛异常 ⇒ 1308 个文件全部归零 |
| 失败是否静默 | ✅ 状态 `ready`、退出码 0、只有一行 `Processed: 0/0` 式的日志 | ✅ 状态 `failed`，但**实体表全 0 而不是报错崩溃**，很容易被当成「索引器不支持这个仓库」 |
| 正确定位方法 | 算**派生指标**（正文/chunk），不看总量 | 看**哪一层有数、哪一层是 0**，从栈底找到「第一步」 |

### 三条我会写进任何项目的原则

1. **静默的部分成功，比明确的失败危险得多。**
   两起事故都不是「崩溃退出」，而是「跑完了、状态看起来正常、但数据是错的」。
   所以我给这个项目的铁律是：**处理数 == 0 必须显式失败或显式 SKIP**，
   绝不允许「0/0 + ready + 退出码 0」这种形状出现。
   （同类：`reindex` 只按已登记路径重解析、目录改名后会先清空 8 张表再报成功；
   `reembed` 静默把向量留成 NULL 且退出码为 0 —— 三个都是同一个形状。）

2. **降级必须「局部化 + 记账」。**
   `try/catch` 只写在最外层 = 一个文件连坐整仓；
   只做 `try/catch` 不打日志 = 换成「静默漏掉」这个更差的形状。
   正确做法：**只降级出错的那一个，并把「跳过了谁、为什么」逐条打出来**。
   现在的输出是 `[URLResolver] 4/1310 个文件未能进入跨文件符号表` + 4 条明细，
   既能继续跑，又让人事后查得到「为什么这个文件搜不到」。

3. **改完启发式/解析器，先证明「对既有语料中性」，再决定要不要付重建代价。**
   重建一次索引 = 20+ 分钟 + 真实嵌入费用。用一个只读探针做 A/B，
   就能把「要不要重建」从**拍脑袋**变成**有证据的决定**。

## 四、附：本次排查中暴露的「工程化陷阱」（都是真实踩到的）

这些不是核心亮点，但**特别能体现「在生产环境干过活」**，面试官通常会追问细节：

| 陷阱 | 现象 | 正确做法 |
|---|---|---|
| **部署了 ≠ 生效了** | 我把修好的 `dist` 传上服务器后直接触发索引，日志仍是 `Full indexing 1532 files`（**守卫完全没生效**）—— Node 在启动时就把模块载入内存了 | 改完 `indexing/**`：**先传产物 → 再 `pm2 restart codelens-api --update-env` → 核对 uptime 归零 + `/health` 200 → 才触发索引**。这次教训的代价是白跑一遍全量索引 |
| **日志分流** | 在 out 日志里 grep 守卫输出**一无所获**，一度以为守卫没打印 | pm2 把 `console.warn/error` 分流到 `codelens-api-error.log`，`console.log` 才进 out 日志。**反过来也要求**：跳过构建产物是**预期行为**，不该用 `warn` 打（否则错误日志会被正常信息淹掉，以后没人看） |
| **同步接口 + 长事务** | 调用重建接口返回**空响应**，一度以为「接口不存在」 | `clearRepoData` 要 drop/recreate 索引，实测 **~30 秒**；`curl --max-time 20` 会让**一次成功的调用表现为空响应**。要 > 35 s |
| **配置有两份** | 手工脚本跑嵌入会写出与库不兼容的向量 | 线上配置的**唯一来源**是进程管理器的 `env_production`，`.env` 只对手工脚本生效**且值不同**（进程 = 1536 维，`.env` = 1024 维，而列类型是 `vector(1536)`）⇒ **嵌入必须交给服务进程做，不要手动跑脚本** |
| **BSD grep 的 `\|` 是字面量** | `grep -c "a\|b" file` 返回 0，差点让我断言「产物里没有新代码」 | 一律 `grep -rnE`。**这个坑我一天踩了三次**，属于「知道也会犯」，最后写死成规则：任何带 `|` 的 grep 无脑加 `-E` |

## 五、面试怎么讲（90 秒稿 + 追问预案）

### 5.1 90 秒口述稿

> "我接了一个真实的前端工程进索引，1532 个可索引文件。跑完一看，仓库页显示**失败**，
> 而且只有 7 个文件。查库发现第一层（切块和向量）是好的，有 1051 个文件、
> 1.4 万个代码块；但第二层 —— 实体表、接口表、调用图 —— **全是 0**。
>
> 这个「一层有一层没有」的形状马上把范围缩小了：不是索引器整体坏了，
> 是增强索引在**一开始**就死了。看日志，从开始到失败只有 3 秒 —— 1308 个文件不可能 3 秒跑完，
> 说明它死在**一次性全仓扫描**里。顺着调用栈从底往上看，死在**建跨文件符号表**这一步。
>
> 我没有去猜哪个文件有问题，而是写了个**离线探针**，把符号表对每个文件做的那次调用重放一遍、
> 逐文件 catch，直接钉到了 **4 个 `.vue` 文件的具体行号**。
> 原因是 `<template>` 里的 `@import="x"` 和 `<style>` 里的 `.xxx-import {`
> 被 TypeScript 的错误恢复当成了 import 声明，而 import 的说明符必须是字符串字面量，
> 不满足就抛异常。
>
> **真正的问题是它为什么会连坐**：`registerFiles` 那个循环外面一层 try/catch 都没有，
> 于是一个文件的格式问题，代价是整仓的检索能力全部归零。
>
> 我做了两处修复：一是**逐文件兜异常，只降级出错的那一个文件并逐条记账**；
> 二是从源头掐掉 —— 项目里本来就有 SFC 解包函数、注释里甚至写了「两遍索引都必须走这里」，
> 但**漏了跨文件符号表这一遍**，一直把 `.vue` 原文喂给 TS 解析器。
> 我补上了解包，而且用**空行占位**而不是拼接 script 块，这样行号与 `.vue` 文件严格对齐。
>
> 最后我做了两件事收尾：一是 A/B 对照新旧的符号表产出，逐条人工核对差异，
> 确认是「删掉了一条编造在 CSS 里的落点、找回了 2 条之前被整份丢弃的真实落点」，而不是丢数据；
> 二是验证这次改动对我另外两个已有仓库**逐条中性**，所以**不需要**为它们付 20 分钟的重建代价。"

### 5.2 高频追问与应答要点

| 追问 | 应答要点（不要跑偏） |
|---|---|
| 「你怎么知道是**那个**文件？」 | 强调**探针重放**：不猜、不 grep，把线上那一次调用在本地逐文件重放并 catch。**定位方法比结论重要。** |
| 「加个 try/catch 不就行了？」 | try/catch 只解决连坐，**不解决根因**。根因是 `.vue` 原文被当 TS 解析，对 407 个 `.vue` 来说这是持续噪声源。两处都要做，而且 try/catch **必须带日志**，否则从「连坐」退化成「静默漏掉」。 |
| 「为什么不直接把 `.vue` 从索引里排除？」 | 因为 `.vue` 的 `<script>` 里是**真实的 TS 代码**，里面有 import、有路径字符串、有 `useContext` 解构。排除掉会让「跨文件符号表」看不到 SFC 内部的引用 —— 那正是这个项目要解决的核心问题。**正确答案是解包，不是排除。** |
| 「为什么要空行占位、不把 script 块拼起来？」 | 因为符号表产出的 provider / 间接落点**带行号**，UI 上要「跳到文件:行号」。SFC 可能有 `<script>` + `<script setup>` 两块，拼接会让第二块行号前移。空行占位让 ts-morph 看到的文件行号与 `.vue` 严格对齐。 |
| 「改完怎么证明没改坏别的？」 | **A/B 探针 + 逐条人工核对 + 对既有语料的中性验证**。强调「我报的差异不是数量差，是逐条明细差，并且每一条我都去代码里核对了」。 |
| 「这个 bug 有什么可迁移的教训？」 | 用第三节那句话：**「一条按单个文件成立的假设，被写进处理整仓的循环，且失败静默」**。再补「降级要局部化 + 记账」「启发式阈值要双向验证」。 |
| 「你怎么保证下次不再犯？」 | 已落地成**可回归的机制**而不是口头承诺：只读探针（`probe-index-guard.js` / `probe-resolver-sfc.js`）+ 守卫逐条上报 + 「中性才免重建」的判据。 |

### 5.3 ⚠️ 口径红线（说了会被抓）

- **不要说「索引成功率 100%」** —— 现在是 1308/1310 进符号表（4 个 `.vue` 里最早是全部降级，
  规范化后有 2 个恢复；这条以你最后一次实测为准，**别凭印象报数**）。
- **不要说「准确率提升 N%」** —— 这个项目没有标注集，参 `11-` 的口径。
- **不要报「性能提升 N 倍」** —— 守卫的效果是**可复核的结构性事实**
  （1532 → 1308 文件、正文 52.8 MB → 3.6 MB 量级），不是压测倍数。
- **不要说「我设计了三层守卫」而不提它的误杀风险** —— 提「最长行不能单独用、
  我们差点误杀了 `Json.ts`」反而加分，因为它证明你**做了双向验证**。
