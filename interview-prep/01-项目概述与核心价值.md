## 一、项目定位

### 1.1 一句话定位

**CodeLens 是一个面向大型代码库的智能代码搜索与问答平台：它把代码库索引成
「结构化实体 + 向量」的双形态数据，用手写的多策略混合检索（约 4000 行）
同时解决「语义相似」与「结构性可达」两类问题，并在其上提供代码定位、
调用链分析与根因诊断。**

### 1.2 目标用户

- **主要用户**：中大型团队的开发者（5-50 人）
- **典型场景**：
  - 新人 onboarding：快速理解陌生代码库
  - Bug 排查：追踪错误的根因和调用链
  - 代码审查：理解代码变更的影响范围
  - API 对接：查找 API 端点的定义和使用位置
  - 重构评估：分析函数修改的影响范围

### 1.3 与竞品的差异化

| 维度 | GitHub Copilot | Sourcegraph | Cursor/Windsurf | **CodeLens** |
|------|----------------|-------------|-----------------|--------------|
| **核心能力** | 代码补全 | 代码搜索 | AI 驱动 IDE | **代码理解与问答** |
| **理解范围** | 单文件上下文 | 文本匹配 | IDE 上下文 | **整个代码库** |
| **跨文件追踪** | ❌ | ❌ | ❌ | **✅ 完整支持** |
| **调用链分析** | ❌ | 部分支持 | ❌ | **✅ 自动构建** |
| **根因分析** | ❌ | ❌ | 部分支持 | **✅ 支持** |
| **URL 推导** | ❌ | ❌ | ❌ | **✅ 差异化能力** |
| **多轮重检索** | ❌ | ❌ | ❌ | **✅ LangGraph 条件边** |
| **部署方式** | 云端 | 云端/私有化 | 本地 | **私有化** |

**核心差异化（逐条对应真实能力）：**
1. **代码库级别的理解**：不是单文件补全，而是把整个库索引成 12 张实体表 + 向量
2. **跨文件追踪能力**：`url-derivation.ts`（1571 行）追踪 URL / 常量 / 函数的跨文件构造链
3. **手写混合检索**：5 种策略按查询意图**动态加权**融合，而不是只用向量检索
4. **有环编排**：本次新增 LangGraph 图，证据不足时自动换策略重检索（最多 3 档）
5. **私有化部署**：代码不出公司，满足安全合规要求

> 原文档把第 3 点写成「AgentRAG：多轮推理、自主决策、工具调用」——
> **「自主决策」和「工具调用」都不存在**，只有「多轮重检索」是真实的（且是本次新做的）。

## 二、解决的核心痛点

### 2.1 痛点 1：手动搜索代码耗时长

**传统方式**：
```
1. 打开 IDE，全局搜索关键词
2. 逐个文件查看搜索结果
3. 手动判断哪个是目标代码
4. 追踪函数调用关系
5. 理解代码逻辑
总耗时：10-30 分钟
```

**CodeLens 方式**：
```
1. 输入自然语言问题："这个 API 在哪里定义的？"
2. 1-2 秒返回精准答案 + 代码证据
总耗时：1-2 秒
```

**效率提升**：**300-900 倍**

### 2.2 痛点 2：跨文件引用无法追踪

**典型场景**：查找 API 端点 `/api/v1/users/:id`

**传统搜索**：
```typescript
// 搜索 "/api/v1/users/:id" → 0 个结果 ❌
// 因为完整 URL 不在任何单个文件中
```

**实际代码**：
```typescript
// constants.ts
export const API_BASE = '/api/v1';

// endpoints.ts
import { API_BASE } from './constants';
export const USER_ENDPOINT = `${API_BASE}/users`;

// service.ts
import { USER_ENDPOINT } from './endpoints';
fetch(`${USER_ENDPOINT}/:id`);
```

**CodeLens 解决方案**：
- 提取所有字符串常量（`string_constants` 表）
- 追踪导入和引用关系（`import_relations` / `constant_references` 表）
- 分析字符串拼接逻辑
- 推导完整 URL 模式（`url_patterns` 表），并返回 `symbolChain` 证据链
- **对可静态解析的构造链，结果确定**；含运行时分支的会返回多个候选 + 各自置信度

> ⚠️ 不要说「准确率 100%」。正确的说法是：
> **「对能静态推导的 URL，结果是确定的（不是概率匹配）；推导不出来时，
> 返回 `missingSymbols` 明确告诉用户缺哪个符号，而不是猜一个值。」**
> 这个「诚实报告不确定性」的设计比一个假装的 100% 更经得起追问。

### 2.3 痛点 3：根因分析耗时长

**传统方式**：
```
1. 看错误日志，定位出错文件和行号（5 分钟）
2. 阅读代码，理解函数逻辑（10 分钟）
3. 追踪调用链，找到上游调用者（10 分钟）
4. 分析数据流，找到根本原因（10 分钟）
5. 提出修复方案（5 分钟）
总耗时：40 分钟
```

**CodeLens 方式**：
```
1. 输入错误信息："为什么会出现 TypeError: Cannot read property 'id' of undefined？"
2. 系统（/root-cause 路由）：
   - 检索相关代码证据（多策略混合检索）
   - 追踪调用链（call_graph / file_dependencies）
   - 把证据连同上下文交给 LLM 生成根因分析与修复建议
总耗时：受 LLM 生成耗时主导（秒级到十几秒）
```

> ⚠️ 原文档写的是「Agent 自动定位 / 追踪 / 分析」并给出 13-20 倍提速。
> **真实情况是：检索与调用链是程序做的，根因推理是 LLM 做的，不是「Agent 自主」**；
> 耗时也没有基准测试。建议改成「把 40 分钟的手工取证压缩成一次提问」，
> 不要给具体倍数。

### 2.4 痛点 4：新人 onboarding 周期长

**传统方式**：
```
1. 阅读文档（1-2 天）
2. 问老员工（每天 5-10 次打断）
3. 自己摸索代码（1-2 周）
总周期：2-3 周
```

**CodeLens 方式**：
```
1. 随时提问，即时获得答案
2. 自动追踪调用链和依赖关系
3. 快速理解代码结构
总周期：3-5 天
```

**效率提升**：**4-6 倍**

## 三、技术创新点

### 3.1 创新点 1：URL 智能推导（独家能力）

**技术难点**：
- 跨文件的字符串拼接追踪
- 模板字符串的变量展开
- 函数调用的内联展开
- 三元表达式的条件求值
- 对象方法调用的解析

**实现效果**：
```typescript
// 输入：查找 "/api/v1/users/:id"
// 输出：
{
  pattern: "/api/v1/users/:id",
  confidence: 95,
  symbolChain: [
    { symbol: "API_BASE", file: "constants.ts", value: "/api/v1" },
    { symbol: "USER_ENDPOINT", file: "endpoints.ts", value: "${API_BASE}/users" },
    { symbol: "getUserData", file: "service.ts", value: "${USER_ENDPOINT}/:id" }
  ],
  derivationSteps: [
    "步骤1: 找到 API_BASE = '/api/v1'",
    "步骤2: 展开 USER_ENDPOINT = '/api/v1/users'",
    "步骤3: 展开 getUserData 返回值 = '/api/v1/users/:id'"
  ]
}
```

**业界对比**：
- GitHub Copilot：❌ 不支持
- Sourcegraph：❌ 不支持
- Cursor：❌ 不支持
- **CodeLens**：✅ **独家支持**

### 3.2 创新点 2：有环编排（从单轮管道到 LangGraph 图）

**改造前的真实形态**：
```
用户查询 → 意图分类 → 多策略检索 → LLM 生成答案 → 返回
（单轮、直线、证据不足也只能硬生成）
```

**改造后（本次新增，`/agent/v2/query`）**：
```
用户查询
  ↓
retrieve（第 1 轮：vector + exact，阈值 0.3，求精准）
  ↓
grade（计算证据充分度，与阈值比较）
  ↓ 不达标且轮次未用尽
retrieve（第 2 轮：加 dependency，followDependencies 扩大召回）
  ↓ 仍不达标
retrieve（第 3 轮：全策略 + 阈值降到 0.2，尽量兜住）
  ↓ 达标或轮次用尽
generate → 结构化答案 + 证据链 + 启发式置信度
```

**真实能力对比（请以此表为准）：**

| 能力 | 改造前 | 改造后 | 说明 |
|------|--------|--------|------|
| 检索轮数 | 固定 1 轮 | 最多 3 轮（策略表长度） | 环由 LangGraph 条件边实现 |
| 策略切换 | ❌ 无 | ✅ 逐轮放宽 | 写死的有序表，非 LLM 规划 |
| 工具调用 | ❌ | ❌ | `ToolRegistry` 仍是抛错占位符 |
| 自我反思 | ❌ | ❌ | `ReflectionEngine` 仍是抛错占位符 |
| 会话记忆 | ❌ | ❌ | 未接入 |
| 置信度评分 | ✅ 已有 | ✅ 复用同一套启发式 | `utils/scoring.ts` 单一来源 |
| 执行轨迹 | ❌ | ✅ `trace[]` 可回放每轮判定 | 新增 |
| 断点续跑 | ❌ | ⚠️ 可选（PostgresSaver，默认关） | 需显式开环境变量 |

> **原文档这里写的是「最多 5 轮 / 4+ 工具 / 会话记忆 / 自我反思 / 答案质量 +20%」——
> 除「置信度评分」外全部不实。** 上面的表格是可以逐条对照代码验证的版本。

### 3.3 创新点 3：多策略动态加权融合

**5 种搜索策略**：

1. **Vector Search（语义搜索）**
   - 1536 维向量（阿里云 DashScope `qwen3.7-text-embedding`，靠 `EMBED_DIMENSIONS=1536` 指定）
   - `code_chunks` 走 HNSW 索引，其余实体表走 ivfflat
   - 适用场景：自然语言查询

2. **Exact Match（精确匹配）**
   - 按 `intent.type` 分支查 `url_patterns` / `string_constants` / `functions`
   - 用 SQL `CASE WHEN ... THEN 1/2/3` 表达「完全相等 > 归一化相等 > 子串命中」
   - 适用场景：已知函数名、精确 URL

3. **Fuzzy Search（模糊搜索）**
   - PostgreSQL `pg_trgm` 三元组相似度（`similarity()` + `%` 操作符）
   - 适用场景：拼写错误、部分匹配

4. **Dependency-Aware（依赖感知）**
   - 沿 `import_relations` / `constant_references` 追踪跨文件引用
   - 适用场景：跨文件拼接的 URL、常量引用

5. **Graph-Based（图遍历）**
   - 遍历 `call_graph` / `file_dependencies`
   - 适用场景：调用链分析

**智能组合策略（真实的「智能」在哪里）**：
- **权重随意图变化**：`vector` 在 general 类查询取 1.0，其余 0.8；
  `exact` 在意图置信度 > 0.8 时取 1.2，否则 0.9（详见 02 文档 §2.3）
- **多策略交叉命中加成**：同一代码位置被多个策略命中时 `max(score) + 0.1` ——
  用「独立命中」当作隐式置信度信号
- **精选而非全上**：`selectStrategies(intent, requested)` 取交集，
  低置信度意图不会启用精确匹配，避免放大误判

> ⚠️ **原文档给了「自然语言 60%→85%、跨文件 0%→100%、平均 +20%」的对照表 ——
> 项目里没有任何标注集，这些数字无法测量。** 建议改说：
> 「这套设计解决的是**结构性问题**而不是刷指标：把『语义相似』和『结构性可达』
> 分开处理。跨文件 URL 这类查询在纯向量方案下是**结构性无解**的，
> 不是 0% 到 100% 的提升，而是『能不能做』的区别。」

### 3.4 创新点 4：批量删除的顺序化改造

**问题现象**：仓库数据清理（删除某仓库的全部索引）非常慢，且数据量越大越慢。

**性能瓶颈分析（为什么慢）**：
1. HNSW 向量索引删除时需要重新平衡图结构 —— 随机写
2. 多个 B-tree / GIN 索引需同步维护
3. 外键级联删除触发子表逐层操作
4. 上述操作产生大量 WAL

**优化方案（`db/index.ts` 的 `clearRepoData`）**：
```sql
-- 1. 删除所有索引和外键约束
DROP INDEX IF EXISTS idx_code_chunks_embedding_hnsw;
DROP INDEX IF EXISTS idx_code_chunks_file_id;
-- ... 删除其他索引与约束

-- 2. 从叶子表到根表，手动批量删除子表（不用级联）
DELETE FROM constant_references WHERE repo_id = $1;
DELETE FROM string_constants   WHERE repo_id = $1;
-- ... 其余 7 张子表

-- 3. 删除主表数据（此时无索引无约束，极快）
DELETE FROM code_chunks WHERE file_id = ANY($1);

-- 4. 重建所有索引和约束
CREATE INDEX idx_code_chunks_file_id ON code_chunks (file_id);
CREATE INDEX idx_code_chunks_embedding_hnsw
  ON code_chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

**技术原理（这才是可讲的部分）**：
- **把「随机写」变成「顺序批量写」**：逐行删除时每次都要更新索引结构；
  批量重建索引只需一次全表扫描
- **HNSW 的图结构特性**：删除节点要修邻居指针，代价与度数相关，远比插入贵
- **绕开级联**：`ON DELETE CASCADE` 是逐层触发查询，手动批量 DELETE 可以一次扫完

> ⚠️ **不要报「16-19 分钟 → 98 秒 / 10-12 倍」** —— 项目里没有基准测试。
> 更好的说法是：**「这个优化的收益是可以推理出来的，但我没有在生产规模上跑过基准；
> 如果你关心具体倍数，我们可以用你给的硬件和数据显示跑一遍。」**
> 能说清「为什么快」远比报一个记不住的数字安全。

## 四、可量化的业务价值

### 4.1 开发效率提升

> ⚠️ **本节原文给出的所有倍数（300-900 倍 / 13-20 倍 / 4-6 倍）都没有测量依据。**
> 下面改写成「可归因、不撒谎」的版本：描述**发生了什么变化**，
> 而不是**量化一个没测过的提升**。

**场景 1：查找 API 调用位置**
- 传统方式：全局搜索关键词 → 逐个文件确认 → 追调用关系（多轮手工取证）
- CodeLens：一次自然语言提问，返回带文件路径与行号的代码证据
- **真实变化**：把「多轮工具切换」压缩成「一次提问」；
  耗时取决于检索（毫秒级）与 LLM 生成（秒级）

**场景 2：根因分析**
- 传统方式：日志定位 → 读代码 → 追调用链 → 分析数据流
- CodeLens：`/root-cause` 把检索到的证据 + 调用链交给 LLM 生成根因假设

**场景 3：新人 onboarding**
- 传统方式：读文档 + 反复打断同事 + 自己摸索
- CodeLens：把「这个函数在哪、被谁调用、参数从哪来」变成自助提问

**建议的口径**：
> 「我不给效率倍数，因为我没有做用户研究。但我可以说清楚系统把哪些步骤自动化了：
> 手工的『搜索 → 筛选 → 追调用链』这几步现在是**一次提问触发**的。」
> —— 这个回答比任何倍数都更难被反驳。

### 4.2 成本结构（这一项是真实的、可报的）

**这套系统的成本优势来自「不用托管向量库」：**

| 项目 | 本项目 | 若换成托管向量库 |
|------|--------|----------------|
| 向量存储 | PostgreSQL + pgvector（自建） | Pinecone / Milvus 等按量订阅 |
| 关系数据 | 同一个 PostgreSQL 实例 | 需另建一套并做数据同步 |
| 任务队列 | Redis + BullMQ（自建） | 通常另购 |
| 主要变动成本 | **embedding + LLM 的 API 调用** | 订阅费 + API 调用 |

**可讲的点**：
> 「我把向量和关系数据放在**同一个 PostgreSQL 实例**里，
> 好处不只是省钱 —— 更重要的是**不会出现『关系库更新了、向量库没更新』的一致性问题**。
> 向量检索和 `repo_id` 过滤在同一个事务边界内，这是托管向量库做不到的。」

### 4.3 ⛔ 原版 ROI 估算的问题（不要再说）

> 原版写「ROI = $5,500 / $50 = **110 倍**」。这个算法的问题：
> **分母是「运维成本」，而不是「总投入」** —— 它把开发成本（1 人月）算成了 0。
> 一旦把开发成本摊进去，结论会完全不同。
>
> 更根本的问题是：$5,500/月 这个收益，来自「每人每天省 30 分钟」这个**自设假设**。
> 换一组假设，ROI 可以是 5 倍也可以是 500 倍 —— **这不是测量，是填空**。
>
> **正确应对**（背下来）：
> 「ROI 完全取决于你假设的人力成本和时间节省比例，
> 我随便填一组参数就能算出任何你想要的数字。我能给的是**可验证的成本结构**
> （开源栈、无托管订阅费）和**能力边界**（哪些步骤被自动化了）。
> 收益要等有了 golden set、量出准确率之后才能谈。」

### 4.4 团队协作价值（这些更值得讲，因为可解释）

**减少打断**（定性，不报百分比）：
- 新人可以自助查询「这个函数在哪、被谁调用、参数从哪来」
- 老员工不必反复回答重复问题

**知识沉淀**：
- 问答历史落在 `questions` 表，检索决策落在 `search_logs` 表
- 可回溯「同一个问题上次是怎么搜的」

**可审计性**：
- 图的 `trace[]` 记录每轮用了哪个策略、充分度多少、为什么继续/终止
- 「为什么这次没搜到」有据可查 —— 这是比「提升 X%」更硬的工程价值

**代码质量提升**：
- 更快发现潜在问题（跨文件影响范围一次查清）
- 更全面的影响分析（`call_graph` / `file_dependencies`）
- 更安全的重构决策（改动前先看谁在调用）

## 五、技术栈与规模

### 5.1 技术栈（对齐 `apps/api/package.json` 实际依赖）

**后端**：
- Node.js + TypeScript，ESM（`"type": "module"`）
- **Fastify 5** + `@fastify/cors` / `@fastify/multipart` / `@fastify/rate-limit`
- **PostgreSQL + pgvector**（`pg` 驱动，连接池复用）
- **Redis（ioredis）+ BullMQ** —— 索引任务队列

**AI 能力**：
- **LLM：DeepSeek `deepseek-chat`**（OpenAI 兼容协议，复用已装的 `openai` 包，零新增依赖）：
  答案生成。厂商由 `LLM_PROVIDER` 切换，适配层见 `apps/api/src/llm/client.ts`；
  `@anthropic-ai/sdk`（`claude-sonnet-4-6`）保留作**回滚路径**
- 阿里云 DashScope（`qwen3.7-text-embedding`，1536 维）：向量嵌入
- 阿里云 DashScope（`qwen3.7-text-rerank`）：**检索精排**，见 `retrieval/rerank.ts`
- **LangGraph**（`@langchain/langgraph` 1.4.x + `@langchain/core` + `@langchain/anthropic`）
  —— **本次新增**，仅用于编排层
- `zod` 用于运行时参数/结构校验

**代码分析**：
- **ts-morph 24**（`ASTAnalyzer` 的主解析器；底层仍是 TS Compiler API）
- **@babel/parser + @babel/traverse + @babel/types**（JS 解析与遍历）
- **@vue/compiler-sfc**（Vue 单文件组件解析 —— 多语言支持，容易被忽略的加分项）
- **segmentit**（中文分词，服务于中英混合查询的意图识别）

**前端（`apps/web`）**：
- React + TypeScript + Vite
- 调用图可视化 + Tailwind CSS

> ⚠️ 原文档写「TypeScript Compiler API（AST 分析）」，更准确的说法是
> **「用 ts-morph 封装 TypeScript Compiler API」**——直接说 Compiler API 会显得没用过它。
> 另外 `@vue/compiler-sfc` 说明这个项目**不止支持 TS/JS**，是个可以主动提的亮点。
>
> 这三个解析库现在**只出现在 `indexing/languages/typescript/` 一个目录里**：
> 解析层已抽成语言适配层（`LanguageParser` 契约 + 按扩展名分发），
> 下游的关系构建、检索与前端对具体语法库**零依赖**——所以「加一门语言」才只需要加一个目录。

### 5.3 数据库规模

> ⚠️ 原文档的「2 个中型仓库 / 5,000 文件 / 50,000 chunks / 2 GB / 20,000 条调用边」
> **在仓库里找不到统计来源**。这类数字很可能被追问「怎么统计的」。
>
> 建议口径：**「数据库规模取决于接入的仓库，我可以现场用 SQL 统计你关心的那一项」** ——
> 把静态数字换成可执行的动作。真要报，就现场跑：
>
> ```sql
> SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC;
> SELECT pg_size_pretty(pg_database_size(current_database()));
> ```

**已验证的结构性事实（可安全报）：**
- 实体表 **12 张**：`repos` `files` `code_chunks` `functions` `classes` `string_constants`
  `url_patterns` `url_usages` `import_relations` `constant_references`
  `call_graph` `file_dependencies`（另有 `search_logs` `questions` `question_feedback`）
- 向量维度 **1536**，与 DashScope `qwen3.7-text-embedding`（`EMBED_DIMENSIONS=1536`）对齐
- `code_chunks` 用 **HNSW**（m=16, ef_construction=64），其余向量表用 **ivfflat**（lists=100）

### 5.4 性能指标

> ⚠️ 原文档的「P50 1.2s / P95 2.5s / P99 4s / 吞吐 100 文件/分钟 / 10+ 并发」
> 同为无出处的数字。**建议删掉，改为描述耗时构成**：

一次问答的时间主要由两段构成：
1. **检索段**：`code_chunks` 走 HNSW，多策略并行，通常是**亚秒级**
2. **生成段**：LLM（默认 DeepSeek）生成答案，通常是**秒级**，也是总耗时的主要部分

> 可讲点：「所以我关注的优化点是**减少不必要的 LLM 调用** ——
> 比如空证据时不调 LLM 直接返回、检索结果走 LRU 缓存。
> 这比压缩检索延迟的收益大得多。」

## 六、项目亮点总结

### 6.1 技术深度（已按真实实现修正）

✅ **手写混合检索**：约 4000 行，5 种策略按意图动态加权，多策略交叉命中加成  
✅ **URL 跨文件推导**：1571 行，把常量/函数/模板抽象成带 `dependsOn` 的图并递归展开  
✅ **有环编排**：LangGraph 条件边实现逐轮升级重检索，收敛性有 30 条断言覆盖  
✅ **批量删除的顺序化改造**：先删索引 → 批量删数据 → 重建索引（能讲清原理）  
✅ **多语言解析**：ts-morph + @babel + @vue/compiler-sfc  

> 原文写的是「Agent RAG 架构：多轮推理、工具调用、自我反思」+「准确率提升 20%」——
> 前者不实，后者无法测量。已替换为可逐条对照代码的版本。

### 6.2 问题解决能力

✅ **URL 推导的多次迭代**：从简单拼接 → 嵌套模板 → 函数内联 → 条件分支，逐层补齐边界  
✅ **HNSW 删除性能陷阱**：定位到「索引维护」而非「删除」是瓶颈，用顺序批量写绕开  
✅ **向量维度升级**：1024 → 1536 的迁移（`002` 迁移显式清空后重算，并升级为 HNSW）  
✅ **编排层改造的边界控制**：新图与旧路由并存，用真实数据决定是否推广  

### 6.3 系统设计能力

✅ **代码实体分表 Schema**：12 张实体表，按「函数/类/常量/URL模式」分类而非一张大表  
✅ **混合检索架构**：向量（语义）+ 关系图（结构）+ 字面匹配（精确）三类信号融合  
✅ **索引与查询分层**：检索层不依赖编排层，因此换编排框架时检索代码零改动  
✅ **可测性设计**：依赖注入让「环」的收敛行为能在无数据库环境下验证  

### 6.4 产品思维

✅ **渐进式体验**：基础索引快速可用，增强索引走 BullMQ 后台队列完成  
✅ **诚实的不确定性表达**：`missingSymbols` 显式列出解析不了的符号，不猜值  
✅ **用户反馈采集**：`question_feedback` / `search_logs` 记录点击与评分  

> ⚠️ 原文写「用户反馈闭环」——**表存在，但反馈尚未反哺模型/权重**，属于「已采集未闭环」。
> 说成「反馈闭环」会被追问「闭环在哪一环」。正确说法是：
> 「反馈已经落库了，闭环是我下一步想做的事（见 11 文档的扩展方向）。」

## 七、面试中如何展示

### 7.1 开场白（1 分钟）

> "我做的项目叫 CodeLens，是一个面向大型代码库的智能搜索与问答系统。
> 它要解决的问题很具体：在一个几十万行的代码库里，一个 URL、一个常量、
> 一条调用链，往往是**跨好几个文件拼出来的** —— 你用 IDE 全局搜索搜不到，
> 用纯向量检索也搜不到，因为这不是语义问题，是**结构性可达**问题。
>
> 我的做法是：把代码库索引成 12 张实体表 + 向量，然后手写了约 4000 行的混合检索，
> 用 5 种策略按查询意图动态加权。向量负责回答『这段话在讲什么』，
> 依赖图和调用图负责回答『这个东西是从哪儿长出来的』。
>
> 最近的改造是在这个基础上加了一层编排 —— 用 LangGraph 把
> 『检索 → 判分 → 证据不够就换策略再检一次』做成一个有环的图，
> 并且刻意让新链路和旧链路并存，用真实数据来决定要不要替换。"

### 7.2 技术亮点（1 分钟）

> "三个我比较愿意展开的点：
> 1. **URL 跨文件推导**（1571 行）：把常量、函数、模板统一抽象成带依赖关系的图节点，
>    然后递归展开成具体 URL。难点是环检测、条件分支、以及**推导不出来时怎么诚实地告诉用户**。
> 2. **多策略动态加权**：权重不是一个固定配比，而是由查询意图决定的；
>    同一个位置被多个策略同时命中会额外加成 —— 用『独立命中』当隐式置信度。
> 3. **编排层的有环图**：LangGraph 的条件边，收敛性靠『先查轮次上限』保证，
>    并且用依赖注入把检索和生成替换成 stub，让这条环在没有数据库的环境下也能被完整测试。"

### 7.3 最大挑战（1 分钟）

> "最大的挑战是 URL 推导的**边界情况**。理想情况是
> `const A = '/api'; const B = \`${A}/users\`` —— 顺着依赖链展开就完了。
> 但真实代码里有：跨文件 re-export 导致符号名变化、条件表达式导致一个 URL 有多个候选、
> 循环依赖导致递归不终止、还有 `path.join()` 这种运行时才能确定的拼接。
>
> 我们迭代了好几轮，最终的设计原则是「**能推就推到底，推不动就说推不动**」——
> 结果结构里有一个 `missingSymbols` 字段，显式列出没解析出来的变量。
> 这个决定的好处是：用户拿到结果时知道**为什么**只有部分匹配，而不是被一个
> 看起来完整但其实是猜的答案误导。"
