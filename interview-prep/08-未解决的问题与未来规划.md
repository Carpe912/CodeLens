# 08 - 未解决的问题与未来规划

## 一、当前系统的局限性

### 1.1 URL 推导的固有边界（静态可推导 vs 运行时才能确定）

> ⚠️ **原标题是「95% → 100%」，并列出了「简单路径 100% / 模板 98% / 函数调用 92% /
> 复杂表达式 85%」——这些百分比都没有出处。** 已改为按「问题类别」陈述，
> 不造假精度。**这里的内容其实更好**：它讲的是「哪些问题在原理上就做不了」。
>
> **正确口径**：不说「95% 准确率」，而说
> 「URL 推导的边界是**静态可分析性** —— 能静态展开的给出确定结果；
> 依赖运行时信息的，返回候选 + `missingSymbols` 明确标注不确定性。」

**按类别划分的能力边界：**

| 类别 | 状态 | 说明 |
|------|------|------|
| 字面量路径 | ✅ 完全确定 | `router.get('/api/users')` |
| 模板字符串拼接 | ✅ 可展开 | 顺着 `dependsOn` 展开符号 |
| 简单函数内联 | ✅ 可展开 | 返回固定值的函数 |
| 条件表达式 | ⚠️ 返回多个候选 | 两个分支都给出，附各自置信度 |
| **运行时才能确定的路径** | ❌ 原理上做不到 | 见下方问题 1-3 |

**未解决的部分（这些是「静态分析的固有边界」，不是 bug）：**

**问题1：依赖运行时随机/分支的路径**
```typescript
// 无法推导
const version = Math.random() > 0.5 ? 'v1' : 'v2';
router.get(`/api/${version}/users`, handler);

// 当前输出：/api/{version}/users  + missingSymbols: ['version']
// 期望：/api/v1/users 与 /api/v2/users 两个候选
```
> 可改进：**识别三元表达式并穷举分支**（不需要运行时值就能列出两个候选）。

**问题2：从数据库/环境读取的配置**
```typescript
// 无法推导
const config = await db.getConfig();
router.get(`${config.apiPrefix}/users`, handler);

// 当前输出：{config.apiPrefix}/users  + missingSymbols: ['config.apiPrefix']
// 期望：需要运行时信息（静态分析原理上无法获得）
```
> **这是真正的边界**：值来自外部系统，静态分析无从得知。
> 合理的做法不是"猜"，而是**明确标注为需要运行时验证**。

**问题3：高阶函数生成的路由**
```typescript
// 无法推导
const createCRUDRoutes = (resource: string) => {
  router.get(`/api/${resource}`, listHandler);
  router.post(`/api/${resource}`, createHandler);
  router.get(`/api/${resource}/:id`, getHandler);
};

createCRUDRoutes('users');
createCRUDRoutes('posts');

// 当前推导结果：/api/{resource}
// 期望结果：/api/users, /api/posts（需要追踪函数调用并做常量传播）
```
> 可改进：**做一层常量传播**（把 `'users'` 代进 `resource`）+
> **模板化输出**（`/api/{resource}` → 声明为「对任意 resource 成立」的模式）。
> 这属于「渐进式提升覆盖率」，而不是「消除边界」。

**问题4：循环生成的路由**
```typescript
// 无法推导
const resources = ['users', 'posts', 'comments'];
resources.forEach(resource => {
  router.get(`/api/${resource}`, handler);
});

// 当前推导结果：/api/{resource}
// 期望结果：/api/users, /api/posts, /api/comments
```

**可能的解决方案：**

**方案1：符号执行（Symbolic Execution）**
```typescript
class SymbolicExecutor {
  /**
   * 符号执行：追踪所有可能的执行路径
   */
  async executeSymbolically(
    func: ts.FunctionDeclaration,
    context: ExecutionContext
  ): Promise<SymbolicResult[]> {
    const paths: ExecutionPath[] = [];
    
    // 1. 构建控制流图（CFG）
    const cfg = this.buildCFG(func);
    
    // 2. 遍历所有路径
    for (const path of this.enumeratePaths(cfg)) {
      const constraints: Constraint[] = [];
      const outputs: any[] = [];
      
      // 3. 沿路径执行
      for (const node of path.nodes) {
        if (this.isConditional(node)) {
          // 记录约束条件
          constraints.push(this.extractConstraint(node));
        }
        
        if (this.isRouteDefinition(node)) {
          // 记录路由定义
          const route = this.extractRoute(node, constraints);
          outputs.push(route);
        }
      }
      
      paths.push({ constraints, outputs });
    }
    
    return paths;
  }
}

// 使用示例
const executor = new SymbolicExecutor();
const results = await executor.executeSymbolically(createCRUDRoutes, {
  resource: Symbol('resource') // 符号变量
});

// 结果：
// [
//   { constraints: [resource === 'users'], outputs: ['/api/users'] },
//   { constraints: [resource === 'posts'], outputs: ['/api/posts'] }
// ]
```

**优势：**
- 可以处理条件分支
- 可以枚举所有可能的路径
- 理论上可以达到100%准确率

**劣势：**
- 实现复杂度极高
- 路径爆炸问题（指数级增长）
- 性能开销大

**方案2：运行时插桩（Runtime Instrumentation）**
```typescript
class RuntimeInstrumentor {
  /**
   * 在运行时拦截路由注册
   */
  instrument(app: Express): void {
    const originalGet = app.get.bind(app);
    const originalPost = app.post.bind(app);
    
    app.get = (path: string, ...handlers: any[]) => {
      // 记录实际注册的路径
      this.recordRoute('GET', path);
      return originalGet(path, ...handlers);
    };
    
    app.post = (path: string, ...handlers: any[]) => {
      this.recordRoute('POST', path);
      return originalPost(path, ...handlers);
    };
  }
  
  private recordRoute(method: string, path: string): void {
    // 发送到索引服务
    indexService.addRoute({
      method,
      path,
      timestamp: Date.now()
    });
  }
}

// 使用：在开发环境启动时自动插桩
if (process.env.NODE_ENV === 'development') {
  const instrumentor = new RuntimeInstrumentor();
  instrumentor.instrument(app);
}
```

**优势：**
- 100%准确（记录的是实际运行的路径）
- 可以捕获所有动态生成的路由
- 实现相对简单

**劣势：**
- 需要运行应用
- 只能在开发环境使用
- 需要覆盖所有代码路径

```typescript
class HybridURLDeriver {
  async deriveURL(node: RouteNode): Promise<DerivationResult> {
    // 1. 尝试静态分析
    const staticResult = await this.staticAnalysis(node);
    
    if (staticResult.confidence > 0.9) {
      return staticResult;
```

```typescript
class KnowledgeGraph {
  private graph: Graph;
  
  /**
   * 构建API知识图谱
   */
  async buildGraph(): Promise<void> {
    // 1. 提取实体
    const entities = await this.extractEntities();
    // 实体类型：API、中间件、服务、数据模型、业务概念
    
    // 2. 提取关系
    const relations = await this.extractRelations();
    // 关系类型：uses、calls、requires、modifies、belongs_to
    
    // 3. 构建图
    for (const entity of entities) {
      this.graph.addNode(entity);
    }
    
    for (const relation of relations) {
      this.graph.addEdge(relation.from, relation.to, relation.type);
    }
  }
  
  /**
   * 基于图的搜索
   */
  async search(query: string): Promise<SearchResult[]> {
    // 1. 解析查询意图
    const intent = await this.parseIntent(query);
    // 例如："需要登录的API" → { concept: "authentication", relation: "requires" }
    
    // 2. 图遍历
    const results = this.graph.traverse({
      startNodes: this.findNodesByIntent(intent),
      maxDepth: 3,
      relationTypes: intent.relations
    });
    
    return results;
  }
}

// 示例：查找"需要登录的API"
// 图结构：
// API_1 --[requires]--> Middleware_Auth
// API_2 --[requires]--> Middleware_Auth
// API_3 --[requires]--> Middleware_Admin --[extends]--> Middleware_Auth
//
// 查询结果：API_1, API_2, API_3（通过图遍历发现）
```

**方案1：分层索引架构**
```typescript
class HierarchicalIndex {
  /**
   * 两层索引：粗粒度 + 细粒度
   */
  async search(query: string): Promise<SearchResult[]> {
    // 第一层：粗粒度搜索（文件级别）
    const queryVector = await this.embed(query);
    const relevantFiles = await this.coarseSearch(queryVector, {
      limit: 100 // 只返回最相关的100个文件
    });
    
    // 第二层：细粒度搜索（API级别）
    const results = await this.fineSearch(queryVector, {
      fileFilter: relevantFiles.map(f => f.id)
    });
    
    return results;
  }
  
  private async coarseSearch(
    vector: number[],
    options: SearchOptions
  ): Promise<FileResult[]> {
    // 文件级别的向量（聚合文件内所有API的向量）
    return await this.db.query(`
      SELECT file_id, AVG(embedding) as file_embedding
      FROM routes
      GROUP BY file_id
      HAVING 1 - (AVG(embedding) <=> $1) > 0.6
      ORDER BY AVG(embedding) <=> $1
      LIMIT $2
    `, [vector, options.limit]);
  }
  
  private async fineSearch(
    vector: number[],
    options: SearchOptions
  ): Promise<SearchResult[]> {
    // 只在相关文件中搜索
    return await this.db.query(`
      SELECT * FROM routes
      WHERE file_id = ANY($1)
      AND 1 - (embedding <=> $2) > 0.7
      ORDER BY embedding <=> $2
      LIMIT 10
    `, [options.fileFilter, vector]);
  }
}
```

**性能提升：**
- 粗粒度搜索：500K API → 10K文件 → 100个相关文件
- 细粒度搜索：只在100个文件的~1K API中搜索
- 查询时间：2250ms → 150ms（15x提升）

**方案2：向量量化（Vector Quantization）**
```typescript
class QuantizedVectorIndex {
  /**
   * 使用Product Quantization压缩向量
   */
  async quantize(vectors: number[][]): Promise<QuantizedVector[]> {
    // 1. 将1536维向量分成8个子向量（每个192维）
    const subVectors = vectors.map(v => this.splitVector(v, 8));
    
    // 2. 对每个子空间进行K-means聚类（256个中心）
    const codebooks = await Promise.all(
      subVectors.map(sv => this.kmeans(sv, 256))
    );
    
    // 3. 用聚类中心的ID替代原始向量
    const quantized = vectors.map(v => {
      const subVecs = this.splitVector(v, 8);
      return subVecs.map((sv, i) => 
        this.findNearestCenter(sv, codebooks[i])
      );
    });
    
    return quantized;
  }
}

// 压缩效果：
// 原始：1536维 × 4字节 = 6144字节
// 量化：8个子向量 × 1字节 = 8字节
// 压缩比：768x
```

```typescript
class DistributedSearchEngine {

   * 按文件路径分片

  async search(query: string): Promise<SearchResult[]> {
    // 1. 并行查询所有分片
```

### 2.2 API变更影响分析

**需求：** 修改API时，自动分析影响范围

**实现思路：**
```typescript
class ImpactAnalyzer {
  /**
   * 分析API变更的影响
   */
  async analyzeImpact(change: APIChange): Promise<ImpactReport> {
    // 1. 查找所有调用者
    const callers = await this.findCallers(change.apiPath);
    
    // 2. 分析变更类型
    const changeType = this.classifyChange(change);
    // - Breaking: 删除参数、修改返回类型
    // - Non-breaking: 添加可选参数
    
    // 3. 评估影响
    const impact = {
      breaking: changeType === 'breaking',
      affectedFiles: callers.map(c => c.filePath),
      affectedAPIs: callers.map(c => c.apiPath),
      estimatedFixTime: this.estimateFixTime(callers.length)
    };
    
    return impact;
  }
}

// 示例：
// 修改：POST /api/users
// 变更：添加必需参数 `email`
//
// 影响报告：
// - Breaking change: Yes
// - 影响文件：15个
// - 影响API：23个
// - 预计修复时间：2-3小时
```

## 四、面试策略

### 4.1 如何讲述未解决的问题

**框架：**
1. **问题描述** - 清晰定义问题
2. **为什么重要** - 解释业务价值
3. **当前方案的局限** - 诚实说明限制
4. **可能的解决方案** - 展示思考深度
5. **权衡考虑** - 展示工程判断力

**示例：**
```
面试官：你们的URL推导准确率是95%，剩下5%为什么做不到？

回答：
剩下5%主要是动态生成的路由，比如从数据库读取配置、
循环生成路由等。这些场景需要运行时信息才能确定。

我们考虑过三种方案：
1. 符号执行 - 理论上可以达到100%，但实现复杂度高，
   而且有路径爆炸问题
2. 运行时插桩 - 准确率100%，但需要运行应用，只能
   在开发环境使用
3. 混合方案 - 静态分析 + 有限的符号执行 + 运行时验证

我们倾向于混合方案，因为它在准确率和实现成本之间
取得了平衡。预计可以将准确率提升到98%，剩余2%
标记为需要运行时验证。

这个5%的gap对业务影响不大，因为大部分项目的路由
都是静态定义的。我们会根据用户反馈决定是否投入
资源优化这部分。
```

### 4.2 如何展示技术规划能力

**要点：**
1. **分阶段规划** - 短期、中期、长期
2. **量化目标** - 具体的指标
3. **优先级排序** - 说明决策依据
4. **风险评估** - 识别潜在问题

**示例（修正版：先建测量，再谈提升）：**
```
短期（1-3个月）：
- 【前置】建立 golden set：从 search_logs / question_feedback 挖历史问答，
  人工标注 100-200 条（正确答案 + 应命中的证据）→ 拿到 Top-1 / MRR 基线
- 【前置】把 search_logs 从「只写」变成「可读」：做一个策略命中率的离线统计
- URL 推导：补齐「条件分支 / 高阶函数 / 循环生成」三类覆盖率（不承诺百分比）
- 补充单元测试：以 agent/graph/ 的注入式测试为模板，先把检索层的纯函数覆盖住

中期（3-6个月）：
- 基于基线做检索优化（换权重要有数据支撑，而不是拍脑袋）
- 索引分区：按 repo_id 分区 + 分区内独立 HNSW
- 把 4 个分散的意图分类器合并为一次结构化输出调用（降成本、减不一致）

长期（6-12个月）：
- 多轮对话记忆（BaseStore 接 conversation_memory）
- 用真实点击数据做轻量 rerank
- 完整的能力边界文档化（让「能查什么/不能查什么」对用户可见）

优先级依据：
1. 【最高】先有测量能力 —— 没有基线，后面所有优化都无法验证
2. 【高】用户痛点是「搜不到预期的东西」，但痛点要先被量化
3. 【中】纯工程收益（成本、延迟）—— 前提是不牺牲召回
```
