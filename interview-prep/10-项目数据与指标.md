## 二、性能：可解释的部分

> ⚠️ **原文档本节所有数字（15→8 分钟、16-19 分钟→98 秒、P50 1.2s…）
> 都无出处，也不存在那套「测试环境 / 5 次取平均 / 标准差」的流程。已删除。**
>
> 面试时如果被问性能，正确的策略是：**讲耗时构成 + 讲优化原理 + 邀请现场实测**。
> 报一个记不住的静态数字，收益为零，风险为一。

### 2.1 一次问答的耗时构成（定性但不含糊）

```
用户提问
 ├─ 意图分类            （纯本地计算，微秒级）
 ├─ 多策略检索          （5 个策略并行 → 亚秒级；命中 LRU 缓存则近乎为零）
 ├─ 上下文增强          （命中块上下各扩 5 行，多次小查询）
 └─ LLM 生成答案        （秒级 —— 总耗时的主要部分）
```

**关键结论（这才是可以讲的部分）：**
> 「这个系统的耗时**主要花在 LLM 生成上**，检索只是前置步骤。
> 所以我优化的方向不是『把检索从 200ms 压到 100ms』——
> 那对总耗时的贡献只有个位数百分比 —— 而是**减少不必要的 LLM 调用**：
> 比如检索为空时直接返回、不调 LLM（避免幻觉，也省钱），
> 检索结果走 LRU 缓存（100 条 / 5 分钟）。」

**这段回答的价值**：它展示的是**能定位优化杠杆**的能力，
比「我把某处优化了 3 倍」更能说明工程判断力。

### 2.2 批量删除的性能问题（真实代码，可讲原理）

**现象**：删除某仓库的全部索引数据时，耗时随数据量增长很快。

**真实原因（`db/index.ts` 源码注释原文）：**
```typescript
/**
 * 为什么要先删除索引？
 * - 索引维护是删除操作的主要性能瓶颈
 * - HNSW 向量索引在删除时特别慢（需要重新平衡图结构）
 * - 删除索引后，DELETE 操作只需要删除表数据，速度快得多
 */
```

**解法**（`clearRepoData`）：先删索引与约束 → 从叶子表批量删数据 →
删主表 → 重建索引与约束。

**可以讲的三层推理：**
1. **定位**：慢的不是 DELETE 本身，而是「每删一行都要同步维护 HNSW 图结构」
2. **原理**：HNSW 删除要修邻居指针，代价与节点度数相关，远比插入贵
3. **转换**：把「N 次随机写」变成「1 次顺序批量写」——
   代价从 O(N × 索引维护) 降到 O(表扫描 + 建索引)

**当被追问「快了多少倍」时的标准回答：**
> "我没有在你的硬件上跑过基准，所以不给倍数。但我可以给你一个可验证的预测：
> **收益来自把随机写变成顺序批量写，数据量越大收益越明显**；
> 如果你有目标规模的数据，我们可以在上面实测一次。"

### 2.3 索引性能（可讲结构，不报数字）

| 维度 | 做法 | 为什么 |
|------|------|--------|
| 增量优先 | `indexSingleFile` / `indexMultipleFiles` | 只处理变化文件，避免全量重建 |
| 队列削峰 | BullMQ 区分全量 / 增量 / 刷新 / 重索引 | 全量索引可能几十分钟，不能占请求线程 |
| 批量 embedding | `enhanced-indexer.ts` 合并请求 | 降低 DashScope 调用次数与网络往返 |
| 维度升级可重算 | `002` 迁移 + `reindexGitLabRepo` | 换 embedding 模型后必须能整库重算 |

## 三、准确率：为什么本项目「不报准确率」

> ⚠️ **原文档的「100 个测试查询 / 人工标注 / 平均 60%→89%」
> 这套测试流程从未执行过。** 这是整份材料里**最危险**的一处 ——
> 因为「准确率」是面试官最可能深挖的指标，而深挖 3 层就会发现没有标注集。

### 3.1 诚实的现状

| 事实 | 说明 |
|------|------|
| ❌ 没有人工标注的 golden set | 因此**无法计算**准确率 / 召回率 / MRR / nDCG |
| ✅ 有 `search_logs` 表 | 记录 `query` / `query_type` / `strategies_used` / `result_count` / `clicked_result_id` |
| ✅ 有 `question_feedback` 表 | 记录用户对问答的反馈 |
| ❌ 反馈尚未反哺模型或权重 | 「采了但没闭环」 |

### 3.2 面对「准确率多少」的标准回答（强烈建议背下来）

> "**我没有报准确率，因为没有标注集 —— 报了就是编的。**
>
> 目前系统里埋了两张表：`search_logs` 记录每次查询用了哪些策略、
> 返回了几条、用户最终点了哪条；`question_feedback` 记录问答反馈。
> 这两张表只写不读，所以现在是**有反馈数据、但还没闭环**。
>
> 如果要做，我的方案是：先从这两张表里挖出历史上被点击 / 好评的问答，
> 人工标注 100-200 条作为 golden set，然后才有资格谈准确率。
> 在那之前，我更愿意用**结构性的可验证指标**来说明系统在做什么，
> 比如：跨文件 URL 推导能返回带文件行号的完整符号链，
> 这在纯向量方案下是**结构性做不到**的。"

**为什么这个回答加分**：它同时展示了（1）工程诚实，（2）知道自己缺什么，
（3）有明确的补齐方案。比一个 89% 强得多。

| 替代指标 | 数值 | 验证方式 |

## 四、业务价值：把「ROI 220%」改成可说出口的版本

> ⚠️ **原文档的 ROI 计算（$5,500/月收益、220% ROI、3.7 个月回本）全部建立在
> 自设的假设上**（10 人团队、每人每天省 30 分钟、$50/小时人力成本）。
> 面试官一眼能看出这是「先定结论再编参数」，反而扣分。已替换。

### 4.1 不报 ROI，报「自动化了哪几步」

| 环节 | 传统做法 | 系统做了什么 |
|------|---------|-------------|
| 定位符号 | IDE 全局搜索 → 逐文件确认 | 多策略检索一次返回带**文件路径 + 行号**的证据 |
| 追 URL 来源 | 正则搜字符串，跨文件拼接的搜不到 | `deriveURLConstruction` 返回完整 `symbolChain` |
| 追调用链 | 手工点进点出 | `call_graph` / `file_dependencies` 直接出图 |
| 理解逻辑 | 读代码 | 把证据连同上下文交 LLM 生成解释 |
| 证据不足 | 无反馈 | `missingSymbols` / `trace[]` 明确说明缺什么、搜了几轮 |

### 4.2 如果对方坚持要 ROI（标准应对）

> "ROI 完全取决于你假设的人力成本和时间节省比例，我随便填一组参数就能算出
> 任何你想要的数字 —— 那样的 ROI 没有意义。
>
> 我能给你的是**可验证的成本项**：这套系统用的是开源栈
> （PostgreSQL + pgvector + Redis），没有托管向量库订阅费；
> 主要变动成本是 embedding 与 LLM 的 API 调用。
> 至于收益，得先用 golden set 量出准确率，才能谈节省了多少人工 ——
> 而在没有准确率的前提下谈收益，是自欺欺人。"

### 4.3 无形收益（这些反而更真实）

- **知识沉淀**：问答历史与检索日志落库，新人可以直接检索历史问答
- **一致性**：不同人查同一个 URL / 调用链，得到同样的证据链，不依赖谁记得
- **可审计**：`trace[]` 记录每轮用了哪个策略、判定结果 ——
  「为什么这次没搜到」有据可查

## 五、数据库规模：改为「现场可查」

> ⚠️ **原文档的「2 个仓库 / 5,000 文件 / 50 万行 / 103,002 条记录 /
> 65,000 个向量 / 503 MB 数据 + 397 MB 索引」全部无出处。** 已删除。
>
> 这类数字 **应该现场查**，而不是背下来：

```sql
-- 每张表的真实行数
SELECT relname AS table, n_live_tup AS rows
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC;

-- 数据库总大小
SELECT pg_size_pretty(pg_database_size(current_database()));

-- 索引总大小
SELECT pg_size_pretty(SUM(pg_relation_size(indexrelid)))
FROM pg_stat_user_indexes;

-- 向量列占用（code_chunks 为例）
SELECT pg_size_pretty(pg_column_size(embedding)) FROM code_chunks LIMIT 1;
```

**面试时的说法：**
> 「数据库规模取决于接入了哪个仓库，我不背数字 —— 但我可以现场用
> `pg_stat_user_tables` 给你看每张表多少行、`pg_database_size` 看总大小。」

> 把静态数字换成**可执行的动作**，是这次材料清理里最重要的一条原则。

### 5.1 已确证的 Schema 事实（可安全陈述）

| 项目 | 值 |
|------|-----|
| 实体表 | 12 张：`repos` `files` `code_chunks` `functions` `classes` `string_constants` `url_patterns` `url_usages` `import_relations` `constant_references` `call_graph` `file_dependencies` |
| 辅助表 | `search_logs` `questions` `question_feedback` |
| 向量维度 | 1536（`002` 迁移从 1024 升级而来） |
| HNSW 索引 | `code_chunks`（m=16, ef_construction=64） |
| ivfflat 索引 | `functions` / `classes` / `string_constants` / `url_patterns`（lists=100） |
| 扩展 | `pg_trgm`（模糊匹配）、`vector`（pgvector） |
| 迁移脚本 | 4 个（`001_enhanced_schema` / `002_update_embedding_dimensions` / `003_add_unique_constraints` / `004_fix_call_graph_and_file_dependencies`） |

### 5.2 扩展性（讲机制，不预测时间）

| 规模 | 瓶颈会先出现在哪 | 可行手段 |
|------|-----------------|---------|
| 单仓库（万级文件） | 增强索引耗时（要跑 embedding） | 队列削峰 + 增量索引 + 批量 embedding |
| 多仓库 | 表内 `repo_id` 过滤后的向量扫描量 | 按 `repo_id` 分区 + 分区内独立 HNSW |
| 超大库 | 单纯提高 `ef_search` 会拖慢查询 | 分层索引（先粗筛再精排）+ Rerank |

> 原文档用「45 分钟 → 7.5 小时 → 75 小时」做了线性外推 ——
> 索引耗时**不是线性增长**（embedding 调用数才是真正的主项）。
> 讲机制比讲外推数字安全。

## 八、面试中如何使用这些数据

### 8.1 讲技术深度（用「结构」而不是「倍数」）

**示例 1：检索架构**
> "这个项目的核心是**约 4,500 行手写检索**：`url-derivation` 1,571 行、
> `url-search` 1,336 行、`multi-strategy-search` 1,279 行、`url-template-matcher` 338 行。
> 我手写而不是套框架，是因为要解决的是**两类不同的问题**：
> 『这段话在讲什么』是语义问题，向量擅长；
> 『这个 URL 是从哪几行拼出来的』是**结构性可达**问题，向量在原理上就做不了 ——
> `/api/users/123` 和代码里的 `${BASE}/users/${id}` 在语义空间里根本不相似。
> 所以我把这两类问题分开做。"

**示例 2：编排改造**
> "我在既有检索之上加了 LangGraph 图：retrieve → grade →
> 证据不足就换策略回到 retrieve，最多三档，逐轮放宽。
> 关键设计是**收敛性**：条件边里**先判轮次上限再判充分度**，
> 这样最坏情况也必然终止。而且图接受注入的检索/生成函数，
> 所以这条环可以在没有数据库和 LLM 的环境下被 30 条断言完整验证。"

### 8.2 被问到性能时

> "我不给倍数，因为我没有基准测试。但我可以给你可验证的东西：
> 耗时主要花在 LLM 生成上，所以我的优化杠杆是**减少不必要的 LLM 调用**
> —— 比如空证据时直接返回、检索走 LRU 缓存。
> 另外批量删除那块，我把『每行删除都维护 HNSW 索引』改成了
> 『先删索引 → 批量删 → 重建索引』，原理是把随机写变成顺序批量写。
> 如果你关心具体数字，我们可以拿你的数据实测。"

### 8.3 被问到准确率时

> "**我报不出来，因为我没有标注集。**
> 系统里有 `search_logs` 和 `question_feedback` 两张表在采数据，
> 但还没用来闭环。要做的话，路径是：先从历史点击打标 100-200 条 golden set，
> 再谈准确率。在那之前我只讲能力边界，不讲指标。"

### 8.4 被问到项目规模时

> "后端约 22,000 行 TS（61 个文件），前端约 2,200 行。
> 数据库表结构是 12 张实体表 + 3 张辅助表，跑在 PostgreSQL + pgvector 上。
> 具体数据量取决于接入的仓库 —— 我可以用 SQL 现场统计。"

**总结**：**用可验证的结构性事实 + 可解释的推理链说话，
而不是用不可复现的数字说话。** 前者经得起追问，后者一戳就破。
