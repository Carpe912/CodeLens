## ⚠️ 零、先处理一个高风险问题

### 问题所在

`04-AgentRAG架构升级.md` 描述了一套**代码里从未存在过**的实现。最典型的两处：

**1. 伪造的实现代码**（04 文件第 77-129 行）

文档展示了一段完整的 `ReasoningEngine.reason()`：

```typescript
class ReasoningEngine {
  private maxRounds = 5;
  async reason(userQuery: string): Promise<AgentResponse> {
    for (let round = 0; round < this.maxRounds; round++) {
      const response = await this.llm.complete(prompt, { tools: this.getAvailableTools() });
      if (response.stopReason === 'tool_use') {
        const toolResults = await this.executeTools(response.toolCalls);
        continue;
      }
      if (response.stopReason === 'end_turn') {
        const quality = await this.assessQuality(response.content);
        if (quality.score < 0.7) { continue; }
        return { content: response.content, rounds: round + 1, ... };
      }
    }
    return this.getBestAnswer();
  }
}
```

而改造前的真实代码是：

```typescript
export class ReasoningEngine {}   // reasoning.ts，空类
```

`AgentCore` 真实流程是固定三步，没有任何循环：分类（正则）→ 检索一次 → 生成一次。`config.maxReasoningRounds = 5` **从未被任何代码读取**。

**2. 编造的性能数据**（04 文件第 743、766-773、783-794、800 行）

| 文档声称 | 实际情况 |
|---|---|
| 推理轮次 1轮 → 1-5轮（5x） | 改造前恒为 1 轮 |
| 平均每次推理 3 轮，成本 $0.0405 | 无法成立，没有轮次概念 |
| 平均推理 8-12 秒 → 4-6 秒（提升 50%） | 无可复现的测量过程 |
| "Round 1 搜索…Round 5 汇总" 案例，准确率 60%→100% | 该案例是虚构的走查 |
| 流式输出「边推理边返回」 | **全仓无任何 SSE 实现**（grep 无 `text/event-stream`） |
| 5+ 种工具、并行工具调用 | 无工具系统，检索入口硬编码为一次调用 |

### 为什么必须处理

这类内容的风险**不是"项目显得没那么强"，而是"候选人会编数据"**。区别是量级上的：

- 面试官只要问一句「这个 `assessQuality` 的 0.7 阈值是怎么定的」或「3 轮这个数怎么测的」，就无法回答
- 只要说「我们看下代码」，`export class ReasoningEngine {}` 一秒暴露
- 一旦被打上「会编造」的标签，同场面试的其他真实亮点（URL 推导那 4000 行是真的）也一起失去可信度

### 处理方式（二选一）

**方案 A：删掉这些表述。** 把项目老老实实讲成「单轮 RAG + 强检索层」。这是安全的下限，仍然是个不错的项目。

**方案 B（推荐）：把它变成真的，然后讲这个改造过程。**

方案 B 更好，有两个原因：
1. 这件事**已经做完了**（见下文第二幕），现在文档里的说法可以是真的
2. 「我自己审计出文档与代码不符，然后真正补上了它」——这个故事比背功能列表强得多，因为它证明的是**工程诚实和自我审视能力**，而这恰恰是资深岗最看重的

具体动作：
- 删掉 04 第 77-129 行的伪造代码块，换成真实实现（`src/agent/graph/nodes.ts`）
- 删掉第 743、766-773、783-794、800 行所有无法复现的数字
- 全文凡是「流式输出」「并行工具调用」「5+ 种工具」的表述，在真正实现前一律删除
- `PROJECT_OVERVIEW.md`、`AGENTRAG_UPGRADE.md` 同样处理

### 关于引用数据的一条硬规矩

**只引用你能当场复现的数字。**

具体到本项目，下面这些我无法验证，建议在你自己跑一遍之前不要引用：
- 「~5,000 个文件 / ~50,000 chunks / ~2GB 数据库」
- 「P50 1.2s / P95 2.5s / P99 4s」
- 「URL 搜索准确率 95%+」

可安全引用的只有两类：
- **代码事实**（行数、文件数、函数名）—— 可现场打开
- **你能重跑的性能对比** —— 前提是你手里有测量脚本和原始数据

## 一、把故事讲对：三幕结构

面试讲项目，最忌「功能罗列」。本项目有一个非常完整的技术叙事，建议按三幕讲：

### 第一幕：真实痛点，真实壁垒

**痛点**：微服务代码库里，前端调用的 `/api/v1/users` 到底在后端哪里定义、经过哪些中间件、被谁改写过——用 grep 只能找到字符串字面量，遇到模板拼接、常量引用、跨文件 re-export 就失效。手工追一遍要 10-30 分钟。

**做法**：没有依赖现成方案，手写了一套约 4,500 行的混合检索层：

| 文件 | 行数 | 职责 |
|---|---|---|
| `retrieval/url-derivation.ts` | 1,571 | URL 拼接链推导（模板展开、常量解析） |
| `retrieval/url-search.ts` | 1,336 | URL 精准搜索 + 优先级评分 |
| `retrieval/multi-strategy-search.ts` | 1,279 | 5 种策略编排 + 结果融合排序 + 精排接线 |
| `retrieval/url-template-matcher.ts` | 338 | 模板字符串匹配 |

> 补充口径：整个 `retrieval/` 目录是 **9 文件 / 6,039 行**（上表 4 项之外还有
> 意图解析、去重、多语言分词、搜索建议、精排 `rerank.ts`）。

**这一幕要讲清楚的技术点**：
- 为什么向量检索在这里**必然失效**——「这个接口在哪定义」是**结构性**问题，不是语义相似度问题。你说「users」和「用户列表接口」，embedding 相似，但「users」和「api」在向量空间里可能很远
- 所以设计了**混合策略**：向量（语义召回）+ 精确（字面命中）+ 依赖图（结构关系）+ 模糊（容错）+ call_graph（可验证的调用关系）
- URL 优先级评分解决误报：完全匹配 1.0 > 包含完整目标 0.95 > 被包含 0.85 > 部分段匹配 0.7

### 第二幕：我发现自己的文档在说谎 ← 这是最强的一段

**这段务必主动讲，它比任何功能都加分。**

某次准备面试、回头核对自己的架构文档时发现：
- `planner.ts` / `reasoning.ts` / `memory.ts` / `reflection.ts` / `tool-registry.ts` 五个文件共约 1600 行，其中**五个类是空的**（`export class X {}`），体积全靠 JSDoc 设计文档撑着
- `AgentCore` 返回给前端的 `confidence` 是**写死的 0.85**，`toolsCalled` 写死为 `['vector_search']`，`stepsExecuted` 写死为 `1`
- `config.ts` 里 7 个配置项有 4 个（`maxReasoningRounds`、`confidenceThreshold`、`enableReflection`、`enableLearning`）**没有任何读取点**
- 数据库里有 6 张 agent 表，其中 5 张**零代码引用**（`agent_executions`、`agent_reflections`、`tool_calls`、`conversation_memory`、`agent_lessons`）
- 同一句「为什么登录失败」在 4 个地方被 4 套正则分类器打出 4 个互不兼容的标签

**为什么这段值钱**：
- 它展示的是**主动审计自己的能力**。绝大多数候选人只会讲自己做成了什么，不会讲自己发现自己的问题
- 它天然引出「修复方案」的讨论，而修复方案的取舍正是考察点
- 它证明我不是在背文档，而是真的读过自己的每一行代码

**一个可以强调的细节**：我当时的第一反应是「删掉这些假的东西」，但更正确的判断是**先分清楚哪些是"设计超前于实现"、哪些是"纯粹的错误"**。那 6 张表其实是**按状态机 + 迭代 + 反思的语义设计的**——schema 设计是对的，只是没有代码去驱动它。这个判断直接决定了后面的改造方向。

### 第三幕：用 LangGraph 真正落地编排层

第二幕的发现指向一个结论：缺的不是检索能力（那 4000 行是真的），而是**编排能力**——状态机、多轮、循环、持久化。而这正是 LangGraph 的领域。

**改造的边界（这里体现工程判断力）**：

| 层 | 决策 | 理由 |
|---|---|---|
| 检索层（约 4000 行） | **一行不动** | 这是项目真实壁垒，换成 `PGVectorStore` 是降级 |
| 分块层 | **一行不动** | 已有 AST 级分块，`RecursiveCharacterTextSplitter` 是倒退 |
| 编排层 | **重写为图** | 原实现是空壳 + 硬编码 |
| 索引层 / DB 层 / API 层 | **不动** | 与问题无关 |

**必须讲清楚的一句**：「知道什么时候**不**用某个框架，比会用某个框架更重要。」如果当时用 LangChain 把检索层也换掉，会失去 `url-derivation.ts` 那 1571 行积累的跨文件推导能力——那是买不来的。

**具体实现**（对应 `src/agent/graph/`）：

```
START → retrieve → grade ──┐
                    │      │ 证据不足且轮次未用尽
                    │      └──→ retrieve（换策略）
                    └→ generate → END
```

- `state.ts`：`Annotation.Root` 定义状态。关键设计——**把 `sufficiencyThreshold` 放进状态而非闭包**，这样条件边判定完全由状态决定，从 checkpoint 恢复时不会因注入了不同的闭包参数而产生行为不一致
- `nodes.ts`：检索节点按轮次取用**逐轮放宽**的策略表（向量+精确 → 加依赖追踪 → 全策略+降阈值）；评分节点算「证据充分度」；生成节点复用既有 `answerQuestion`
- `index.ts`：条件边先查轮次上限，**保证最坏情况必然收敛**
- `utils/scoring.ts`：评分启发式抽成单一事实来源，`AgentCore` 与图共用，避免两套实现漂移

**验证方式（这里体现工程严谨）**：写了 36 项断言的验证脚本（`pnpm --filter @codelens/api verify:graph`），其中包含**穷举 `maxRounds` 1..6 证明最坏情况必然收敛**。

**一个真实的踩坑（面试官会喜欢）**：给图的状态通道起了 `answer`，节点也叫 `answer`，`tsc` 完全通过，但运行时抛 `answer is already being used as a state attribute, cannot also be used as a node name`。**LangGraph 的这类约束编译期发现不了，必须实际构造图才会暴露。** 结论：图编排的验证不能只跑类型检查。

## 三、真实竞争力清单

**每一条都是可以现场打开代码验证的**——这是这份清单的价值所在。

### 1. 手写混合检索层（约 4000 行）——最硬的一条

不是调库，是自己设计的。`url-derivation.ts` 1571 行的跨文件 URL 拼接链推导尤其难得：
要处理模板字符串、常量引用、函数返回、re-export 链。这是**通用 RAG 框架不提供的能力**。

### 2. 对「检索问题分类学」的理解

能清楚说明：为什么向量检索擅长「这段代码干什么」而不擅长「这个函数在哪被调用」。
前者是语义匹配，后者是**图上的可达性问题**。这个区分是很多工程师模糊的。

### 3. pgvector HNSW 的删除性能陷阱

这是个含金量很高的坑：删除带 HNSW 索引的记录时，索引需要重平衡图结构，
逐行删除会累积巨大开销。

> ⚠️ **注意**：其他文档里写的「16-19 分钟」**没有出处，不要引用**。
> 讲这个坑时不要报倍数，改用「现象 + 定位方法 + 原理」（见 `05-性能优化实战.md` §1）。

**解法**：先删索引 → 批量删数据 → 重建索引（批量构建远快于逐行维护）。

**定位方法（比结论更值钱）**：临时 `DROP` 掉 HNSW 索引再跑同一条 DELETE，
如果耗时显著下降，就证明了慢的是**索引维护**而非删除本身 —— 这是「隔离变量」的经典手法。

**为什么这条加分**：它说明理解的是**索引的物理实现**，不是「用了个向量库」。
可以延伸讨论：HNSW 的图结构、为什么删除比插入贵、什么时候该用 IVFFlat 代替
（本项目其他向量表就还在用 ivfflat）。

### 4. AST 级索引与调用图构建

`languages/typescript/entities.ts`（1,329 行，ts-morph）/ `relationship-builder.ts`（1,355 行）/
`dependency-tracker.ts`（842 行）/ `indexer.ts`（658 行）/ `enhanced-indexer.ts`（1,108 行），
`indexing/` 目录合计 **13 文件 / 8,215 行**（含解析适配层 `languages/` 7 文件 3,885 行）。
两阶段索引（基础索引快速可用 + 增强索引后台补向量和关系图）体现**渐进式体验**的产品思维。

> ⚠️ 「基础 5-10 分钟 / 增强 30-60 分钟」这两个数字**无出处**，不要引用。
> 讲结构（两类索引器 + BullMQ 四类任务）就足够了。

### 5. 数据库 schema 设计（12 张实体表 + 3 张辅助表）

`code_chunks` 存向量、`call_graph` 存调用边、`file_dependencies` 存文件依赖边、
`string_constants` + `constant_references` 支撑 URL 推导。

**一个很好的讨论素材**：项目早期设计过一套 **6 张表的 agent 状态机**
（`agent_executions(plan, steps, result, confidence)`、`agent_reflections(round, on_track, needs_replan)`、
`agent_lessons`、`conversation_memory`、`tool_calls`、`agent_conversations`），
但审计后发现**除 `agent_conversations` 外全部零代码引用**，于是连同建表 SQL 一并删掉。
可以展开讨论「数据模型先行」：我的结论是——先行 schema 是**设计意图的存档**，
但只要没有代码驱动它就会腐烂成误导（注释里那句「由 import_relations 触发器自动聚合」
正是这样让 `file_dependencies` 空转了数月）。
后来真正落地多轮编排时，用的是 LangGraph 的 checkpointer，而不是当初那套表。

### 6. 本次编排层改造（新增，可现场演示）

LangGraph 图 + 条件边收敛保证 + 36 项断言测试 + 依赖注入以便测试。

## 四、主动说出弱点（这是加分项）

面试官问「这个项目有什么不足」时，**不要答「没什么不足」**。准备以下真实的：

| 弱点 | 说法 |
|---|---|
| **4 套并存的意图分类器** | 「`qa.ts` 8 类、`agent-core` 4 类、`query-intent-parser` 5 种、`multi-strategy-search` 5 类，术语互不兼容。同一句话在 4 处得到 4 个标签。**应该统一成一次结构化输出调用**，这是我下一步要做的。」 |
| **单轮管道无法多跳推理** | 「比如『所有需要管理员权限的 API』这类问题，需要图遍历而不是向量召回。现在靠单次检索碰运气。已经加了循环，但还缺把意图编译成执行计划的能力。」 |
| **无流式** | 「LLM 生成是阻塞的，首字等待就是全量时间。这是个明确的体验缺陷，`graph.stream()` 已经具备条件，只是还没接 SSE。」 |
| **会话只写不读** | 「`/agent/query` 会存会话记录，但从不读回历史——所以所谓多轮对话其实是每轮无状态的。这是个我审计时才发现的真问题。」 |
| **只支持 TS/JS** | 「深度依赖 TypeScript Compiler API 做 AST 分析，这是选型时为了类型信息完整付出的代价。要支持多语言得换 tree-sitter，但会丢掉类型信息。」 |
| **评测集是自造的，有上界偏差** | 「评测集**已经建起来了**（URL 类 37 例、自然语言 19 例 + 3 个反例，脚本在 `test-repo/eval/`，报告在 `test-repo/TEST_REPORT.md`）。但它有个真实缺陷：**语料和问题都是我构造的，问题基本照着代码出，所以那组数字是上界，不是承诺**。更值钱的下一步是拿一批真实工单问题重新量一遍。」 |

**最后一条尤其重要**，但**注意口径已经变了**：不再是「承认没有评测集」，
而是**「承认评测集的上界偏差」**（见 `12-回答「VSCode+DeepSeek插件就够了」.md` §七 Q3）。
前者只表明你知道该做，后者表明你**真的做了，并且知道它的局限在哪** —— 后者强得多。

## 五、高频追问与应答

**Q：为什么不用 LangChain 的 PGVectorStore，要自己写检索？**
> 「因为我要的不是向量检索，是**混合检索 + 优先级评分**。`PGVectorStore` 给我的是一个向量近邻查询接口，而我的核心逻辑在融合排序：完全匹配 1.0、包含完整目标 0.95、被包含 0.85、部分段匹配 0.7。这个排序规则是解决误报的关键，换掉它等于把项目的核心价值换掉。我实际只用了 LangGraph 做编排，LangChain 那层只取了模型封装。」

**Q：多轮循环怎么保证不死循环？**
> 「两层。一是条件边判定顺序**先查轮次上限再查重试**，所以最坏情况必然终止；二是轮次上限取 `min(config.maxRounds, 策略计划长度)`——因为策略计划定义的是**互不相同**的检索手段，用尽后再重复最后一档只是白花钱、几乎不会有新证据。我还写了穷举 `maxRounds` 1..6 的测试来证明收敛。」

**Q：为什么阈值放在状态里而不是闭包？**
> 「因为要支持 checkpoint 恢复。如果判定依赖闭包变量，进程重启后注入的参数可能不同，同一份状态会得到不同的判定结果。放进状态后，条件边是**纯函数**，恢复行为完全可复现。」

**Q：这个改造有什么风险？**
> 「三个。一是 LangGraph.js 生态落后 Python 版，API 还在演进，所以要锁小版本；二是引入框架后调用栈不再线性，调试心智负担变重，LangSmith 类的可观测性几乎变成必需；三是收益边界要说清楚——如果目标只是『问答更快更准』，图的收益有限；它真正解决的是**多轮、反思、可持久化会话**这类单轮管道做不到的事。」

**Q：为什么置信度是启发式而不是模型输出？**
> 「因为不能对外声称一个没有校准过的分数是概率。我做的是一个明确的启发式：相关性均值 70% + 证据覆盖度 30%，用途是**横向比较和触发重检索**，不是准确性承诺。代码和文档里我都明确标注了这一点——这类东西一旦被当成模型置信度用，会误导下游。」

**Q：如果给你三个月，你做什么？**
> 见下一节，挑两个讲。

### 第一优先：检索质量的评测体系（最该做，最不性感）

**现状**：✅ **已建立（2026-09-19）** —— 见紧随其后的「已落地」块。

**为什么难**：代码检索的 ground truth 很难定义。「正确答案」往往是一个文件+行号集合，标注成本高且主观。

**为什么值钱**：这是从「能跑」到「可信」的分界线。**没有评测的优化都是玄学**——这句话在面试里说出来很加分。

### 第二优先：影响面分析（爆炸半径）

**现状**：只能回答「现在是什么样」，不能回答「改这里会怎样」。

**做法**：
1. 反转 `call_graph` 做反向可达性（BFS 找所有传递调用者）
2. 叠加 git blame / git log 找代码 owner → 自动推荐 reviewer
3. 结合文件依赖图算改动扩散范围

**为什么难**：
- 反向遍历在大型图上会爆炸（一个被广泛引用的 util 可能有上千传递调用者），需要**按层次截断 + 重要性剪枝**
- 动态派发、接口实现、依赖注入会让静态调用图**不完备**——必须明确告诉用户「这是静态分析的下界，运行时可能更多」

**价值**：从「问答工具」升级为「重构安全网」。这是质变，商业价值更高。

>
> 实现过程中发现：**这条链路的瓶颈不是「图分析算法不够好」，而是「图是空的」。**

> 动手前的排查结论（全部可当场指代码验证）：

> - `file_dependencies` 空表的根因是：代码注释声称「由 `import_relations` 的触发器自动聚合」，
>   但全仓 `CREATE TRIGGER` **零结果**——职责被委托给了一个不存在的东西
> - 顺带查出 `SELECT id, content FROM code_chunks`（应为 `code_text`）、
>   `SELECT DISTINCT symbol_name FROM functions`（应为 `name`）等线上查询，

### 第三优先：多跳查询引擎（把意图编译成执行计划）

**这是我最想做的一个，因为它触及了本质。**

**现状**：所有查询最后都退化成「向量召回 top-k」，然后让 LLM 从里面找答案。这解释了为什么文档里那个「所有需要管理员权限的 API」的案例做不到——**它根本不是检索问题**。

**正确路径**：把用户意图**编译**成执行计划，而不是靠检索碰运气。

```
"所有需要管理员权限的 API"
  ↓ 意图解析（LLM，结构化输出）
{
  plan: [
    { op: 'find_symbol', name: 'requireAdmin', type: 'middleware' },
    { op: 'reverse_traverse', from: '$0', edge: 'call_graph', depth: 3 },
    { op: 'filter', where: 'symbol_type == "route_handler"' }
  ]
}
  ↓ 执行（在 call_graph 上做图遍历，不走向量）
结果：确定性的完整集合
```

**为什么难**：
- 需要定义一个中间表示（IR）——这是**查询计划 DSL** 的设计问题，类似 SQL 之于关系代数
- 需要 LLM 可靠地产出结构化计划（这里 `withStructuredOutput` + zod schema 才有真正的用武之地）
- 需要为每类算子做代价估算，决定「走图遍历」还是「走向量召回」——**混合执行计划优化**，这是数据库领域的老问题在代码检索上的投影

**为什么这条最能体现技术**：它把「RAG 调参」提升成「查询引擎设计」。而且它让那个被编造过的案例**变成了真能实现的**——如果面试官问起，你可以直接给出这个方案。

### 第四优先：增量索引

**现状**：每次全量重索引，大型库要 45 分钟。

**做法**：文件内容 hash + git diff 得到变更集，只处理变更文件。

**为什么难（这才是真正的难点）**：**调用图是全局的**。
- 删掉一个函数，所有指向它的边要失效——但边可能存在于**未变更**的文件里
- 改名一个符号，跨文件的引用全部失效，而那些文件没变
- 所以「增量」不能只算文件级 diff，需要**部分失效传播**（类似 Merkle tree 的思路：文件指纹向上聚合，局部变化触发局部重建）

**这是分布式系统和编译器领域都有的经典问题**（增量编译、增量构建），讲好了非常显功力。

### 第五优先：代码专用 Embedding + 结构增强

**现状**：通用 embedding 模型对代码语义理解有限。

**做法**（两条路）：
1. 换代码专用模型（CodeBERT / GraphCodeBERT / 或对特定代码库微调）
2. **更有意思**：把 AST 结构信息编码进向量表示——不是只 embed 代码文本，而是把「它被谁调用、它调用了谁、它在哪个模块」也编码进去

**为什么难**：第 2 条需要设计**图节点的表示学习**方案（GNN 或结构化 prompt），而且要能增量更新——代码一改，结构表示就变了。

### 第六优先：语义缓存

**现状**：`searchTTLCache` 是精确 key 缓存，改一个字就 miss。

**做法**：对 query 做 embedding，按余弦相似度做近邻缓存查找（如 > 0.95 认为等价）。

**为什么难**：要处理**假命中**——「getUser 的调用位置」和「getUsers 的调用位置」向量很近但是不同问题。需要加实体验证层。另外缓存失效策略要跟索引版本绑定。

### 第七优先：多语言支持

**现状**：深度依赖 TypeScript Compiler API，只能 TS/JS。

**做法**：换 tree-sitter 做统一语法树。

**为什么是个真权衡**：TS Compiler API 给**完整类型信息**（能解析符号的真实定义、能做类型级分析），tree-sitter 只给语法树。**支持多语言的代价是失去类型信息**，这会让 URL 推导那类能力的精度下降。这是典型的「能力换覆盖面」的取舍。

### 第八优先：平台化

**方向**：把 CodeLens 做成 MCP server，让 Claude Code / Cursor 能把它当检索后端调用。

**为什么有价值**：从「一个独立工具」变成「别人工作流里的一环」。技术难度不高，但产品判断加分——说明想过**分发**问题。
