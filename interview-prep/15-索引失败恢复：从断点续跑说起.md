# 15 - 索引失败恢复：为什么「重跑一次」不该是唯一的选项

> 承接 `13`（索引崩溃）与 `14`（静默丢数据）。前两篇讲怎么**修**问题，
> 这一篇讲修完之后仍然存在的那个问题：**失败了怎么继续。**
>
> 起因是一句很直接的抱怨：「现在只要构建过程中失败，就要进行重建，
> 这个能否优化一下，从上次构建失败的位置重新构建。」

---

## 一、先看清楚：问题不在「有没有断点续传」，而在「断点续传只做了一半」

一上来就说「加个断点续传」是错的。索引是**两遍**跑的，而这两遍的续传能力**严重不对等**：

| | 第一遍（`indexCodebase`） | 第二遍（`reindexRepository`） |
|---|---|---|
| 产出 | `code_chunks` + 向量 | 实体层（functions/classes/constants）+ 关系层（import/call_graph/url） |
| 断点续传 | ✅ 有 —— `SELECT path FROM files` 之后跳过已登记路径 | ❌ **完全没有** |
| 挂掉之后 | 重跑会接着做 | `cleanupRepository` 清空 10 张表 → **从零开始** |

再加一刀：`POST /repos/:id/reindex` 在最前面还会调一次 `clearRepoData(repoId)`，
把第一遍的成果 —— **包括已经花钱调 API 生成好的向量** —— 一起清掉。

所以「第二遍跑到 1037/1051 挂掉」的完整后果是：

> 你已经付掉了 1037 个文件的解析成本 + 向量生成成本，
> 但没有任何办法从那 1037 继续；唯一的按钮会把它们全删掉，让你重付一遍。

**一次失败 = 一次完整重来。** 实测 repo 33（1308 个文件）全量一轮约 40 分钟，
其中绝大部分是 embedding API 的等待。

---

## 二、设计：两层各自记住「我做到哪了」，不引入外部进度文件

### 2.1 为什么不做一个「进度文件」

最直觉的方案是写一个 `progress.json`，记「做完到第几个文件」。
但这个方案在这个系统里是错的，原因很具体：

- **进度不是一个数，是两个。** 第一遍按文件做完，第二遍也按文件做完，
  而且是**不同粒度的事**（一个文件可以「有 chunk 但没有实体」—— 这正是文档 14 里
  `return_value` 溢出事故的状态）。一个 `progress.json` 记不下这个二维状态。
- **进度会与数据脱节。** 增量索引（`/refresh`）会中途改文件：A 文件的内容变了，
  它的实体层结论就失效了。一个独立的进度文件**没有任何机制知道这件事**，
  于是续跑会跳过一个内容已经变了的文件。
- **崩溃点恰恰是最不可信的时刻。** 进度文件在「写完进度」和「写完数据」之间
  必然有一个窗口；崩溃落在这个窗口里，进度文件就会撒谎。

所以正确的做法是：**把进度标记附在数据本身上**，让「数据在不在」和「标记在不在」
在同一个事务语义下成立。

### 2.2 第一遍的标记：`files` 行 + `code_chunks` 存在性

第一遍本来就有标记（`files` 表），但原来的判据**不够**：

```sql
-- 修前：只要 files 表里有这个路径，就认为它做完了
SELECT path FROM files WHERE repo_id = $1
```

而写入顺序是 `insertFile()` → 逐块 `insertCodeChunk()`。进程在两者之间挂掉，
会留下「有文件行、0 个 chunk」的半成品 —— 旧判据把它当已完成 ⇒ **永久跳过** ⇒
该文件只有文件行、没有任何可检索内容，而且没有任何报错。

```sql
-- 修后：必须有文件行，且至少有一个代码块
SELECT f.path FROM files f
 WHERE f.repo_id = $1
   AND EXISTS (SELECT 1 FROM code_chunks c WHERE c.file_id = f.id)
```

> 这条判据能成立，是**上一步改动的副产品**：文档 14 让「抽不出符号」的文件也会拿到
> 整文件兜底块 ⇒ 正常完成的文件必然至少有 1 个块 ⇒ 「0 个块」可靠地等价于「没做完」。
> 如果没做那个改动，「0 个块」既可能是没做完、也可能是这个文件本来就抽不出东西，
> 这条判据就会误伤。

### 2.3 第二遍的标记：新增 `files.entities_indexed_at`

```sql
ALTER TABLE files ADD COLUMN IF NOT EXISTS entities_indexed_at TIMESTAMPTZ;
```

**为什么不能用「该文件在 functions/classes/string_constants 里有没有行」来判** ——
这是设计里最容易做错的一步：

实测 repo 33 有 **237 个文件合法地产出 0 条实体**（barrel `index.ts`、
纯模板 `.vue`、i18n 字典、`*.d.ts`）。用「有没有行」判，这 237 个文件
**每次续跑都会被重新分析一遍**；用独立标记判，跑过一次就再也不碰。

**一设一清，语义才闭环：**

```ts
// 设：四步全部成功之后才盖标记（不是「开始处理了」）
await this.db.query('UPDATE files SET entities_indexed_at = now() WHERE id = $1', [fileId]);

// 清：内容变了 ⇒ 上一轮的结论失效 ⇒ 标记必须失效
await pool.query(
  'UPDATE files SET content = $1, language = $2, entities_indexed_at = NULL WHERE id = $3',
  [content, language, fileId]
);
```

「清」这一步不是顺手清理，它挡的是一个**比不续跑更坏**的坏序列：

> 更新内容 → （进程在此崩溃） → 续跑 ⇒ 因为标记还是旧的而**跳过**这个文件
> ⇒ 新内容永远拿不到实体层更新，而且没有任何报错。

### 2.4 续跑的执行：复用 `rebuildFiles`，只换「目标集合怎么选」

第二遍的逐文件重建逻辑**已经存在**（`rebuildFiles`，增量索引用的），而且它解决的
全都是踩出来的正确性问题：

- 重建前必须先 `cleanupFileEntities` + `cleanupFileRelationships` **删干净自己**
  —— 因为 `storeEntities` 的冲突键带 `line_start`（行号一挪就插新行、旧行赖着不走）、
  `buildImportRelationships` 是 `ON CONFLICT DO NOTHING`（删掉的 import 还在）；
- `url_patterns` **不能按文件删**（接口行跨文件共享，按文件删会级联打掉别人的调用点）；
- 收尾要重算 `file_dependencies`、回收孤儿 `url_patterns`。

续跑与增量重建在这几点上**要求完全相同**，差别只有「处理哪些文件」。所以：

```ts
async resumeRepository(repoId: number, options: IndexingOptions = {}) {
  const pendingIds = (await this.db.query(
    `SELECT id FROM files WHERE repo_id = $1 AND entities_indexed_at IS NULL ORDER BY path`,
    [repoId]
  )).rows.map((r) => r.id);

  console.log(`[resume] 共 ${total} 个文件，待补实体层 ${pendingIds.length} 个`);
  return this.rebuildFiles(repoId, pendingIds, options);   // ← 复用
}
```

**这是本次改动里最重要的一个决定：没有新写一份循环体。**
复制一份循环体，就等于把上面三条正确性约束再实现一遍，而它们迟早会在其中一份里被改漏
—— 这个项目里已经发生过一次同类事故：`.vue` 的「必须解包 SFC」这条规则，
第一遍和第二遍都遵守了，**第三遍（跨文件符号表）被漏了整整一轮**（见文档 13）。

### 2.5 工作区：存在就复用，缺了分两种处理

第一遍要扫目录，所以工作区不能缺。缺了之后：

- **GitLab 源** → 重新克隆即可（**不动数据库**）；
- **ZIP 源** → 原始压缩包不在服务器上，无法恢复 → 明确报错让用户重传。

⚠️ 这里刻意**不**做「用库里的 content 反向写一份工作区」。那等于拿索引内容造源码 ——
而一旦索引本身是缺损的（正是要修的场景），就会把缺损**固化成「源码」**。
宁可让人重传。

## 三、语义对比：`reindex` 与 `resume` 到底差在哪

| | `POST /repos/:id/reindex` | `POST /repos/:id/resume` |
|---|---|---|
| 数据库 | `clearRepoData` 清空 → 从零 | **完全不动** |
| 工作区 | 删掉重克隆 | 存在就复用 |
| 第一遍 | 全量处理 1308 个文件 | 跳过「已登记且有 chunk」的 |
| 第二遍 | 清空 10 张表后全量 | 只做 `entities_indexed_at IS NULL` 的 |
| 向量 | **全部重新生成（重新花钱）** | 一个都不重新生成 |
| 代价 | ∝ **仓库大小** | ∝ **剩余工作量** |
| 什么时候用 | 索引器/切分策略变了、数据被污染 | **失败后接着做**（默认动作） |

**两个按钮对应两种不同的问题**：「我改了解析器，要全部重算」和「上次没跑完，接着跑」。
以前只有一个按钮，于是第二种问题被迫用第一种的代价来解决。

### 状态怎么报（这里也有讲究）

任务失败时的状态恢复逻辑是按「**索引还在不在**」定的：

| 失败的任务 | 索引现状 | 状态 | 理由 |
|---|---|---|---|
| `refresh` | 旧索引完好 | `ready` | 报 failed 是撒谎 |
| `reindex` | 路由已 `clearRepoData` 清空 | `failed` | 报 ready 是撒谎 |
| `resume` | **没被清空，只可能更完整了** | `failed` | 整仓仍不完整，需要人再点一次 |

关键差别在于：`resume` 的 `failed` 是**可低成本恢复的** —— 再点一次续跑，
不会重做已经完成的部分。而在这次改动之前，「failed」几乎等于「准备重付 40 分钟」。

## 四、验证：用「制造局部失败」来测，而不是跑一次全量

续跑功能不能靠「跑一次全量重建看着像是对了」来验证 —— 那恰恰是它要替代的操作。
真正要验证的是**它只重做该重做的那部分**。所以测试设计成两步：

**① 零待补的路径**（接口、任务类型、标记读取是否正确）

把已完成文件的标记补齐（这些文件的第二遍确实成功跑完过），然后调 `/resume`：

```bash
curl -s -X POST http://127.0.0.1:8787/repos/33/resume
# → {"jobId":"70","status":"indexing","pendingFiles":0}
# 日志： [resume] repo 33：共 1308 个文件，待补实体层 0 个（已完成 1308 个）
#        [resume] 没有待补文件，只重算文件级依赖
```

应当在数十秒内完成（只重算 `file_dependencies`），且**不产生任何新的向量**。

**② 有待补的路径**（模拟真实的「部分失败」）

把若干文件的标记置回 NULL（等价于「这批文件上次失败了」），调 `/resume`：

```bash
psql -c "UPDATE files SET entities_indexed_at = NULL WHERE repo_id=33 AND path IN (...)"

curl -s -X POST http://127.0.0.1:8787/repos/33/resume
# → {"pendingFiles":N}
# 日志： [resume] repo 33：共 1308 个文件，待补实体层 N 个（已完成 1308-N 个）
```

验收判据（三条，都是可查的）：
1. **只重建了 N 个文件** —— 其余文件的 `functions` 行数与重建前完全一致；
2. **这 N 个文件被重新盖上了标记** —— 再次 `/resume` 应返回 `pendingFiles: 0`；
3. **`code_chunks` 与向量的行数不变** —— 证明它没有碰第一遍的成果。

判据 3 是这次验证的重点：**「没重做已经做完的事」才是这个功能的定义**，
「跑完了」什么都不能证明。

## 五、面试怎么讲

### 5.1 90 秒口述稿

> 我们索引一个仓库分两遍跑：第一遍切代码块 + 生成向量，第二遍抽实体和关系。
>
> 问题是这两遍的续传能力不对等：第一遍按 `files` 表跳过已处理的，第二遍却是
> 「先清空 10 张表再全量重来」。而失败后的唯一入口 `POST /reindex` 还会在最前面
> 再清一次库 —— 把已经花钱生成好的向量也删掉。所以第二遍跑到 1037/1051 挂掉之后，
> 那 1037 个文件的成本就白付了，只能整仓重跑（实测一轮约 40 分钟）。
>
> 我加了「续跑」：不清库、不重新克隆，第一遍跳过已处理的、第二遍只做没做完的。
> 关键设计是**把进度标记附在数据本身上**，而不是写一个进度文件 ——
> 因为进度是二维的（一个文件可能「有代码块但没有实体」），而且增量更新会让
> 已有结论失效；进度文件没有任何机制知道这件事。
>
> 具体做法是给 `files` 加一个 `entities_indexed_at`，第二遍四步全成功才盖章，
> 而 `updateFile` 在内容变化时把它清成 NULL —— 一设一清，标记才真的等价于
> 「当前内容已完成分析」。续跑的执行直接复用增量索引那套 `rebuildFiles`，
> 只换「选哪些文件」，因为逐文件重建的正确性约束（先删干净自己、不能按文件删
> 共享的接口行）两边完全一样，复制一份循环体迟早会改漏其中一份。
>
> 验证时我没有跑全量去「看看对不对」，而是制造局部失败：把 N 个文件的标记置回 NULL，
> 然后验证三件事 —— 只重建了这 N 个、它们被重新盖章、以及
> **代码块和向量行数一个都没变**。最后一条才是重点：这个功能的定义是
> 「不重做已经做完的事」，而不是「能跑完」。

### 5.2 高频追问

| 追问 | 应答要点 |
|---|---|
| 「为什么不写个进度文件？」 | 进度是二维的（chunk 层与实体层是两个进度）；进度文件无法感知增量更新导致结论失效；而且它在「写完进度」和「写完数据」之间有窗口，崩溃落进去就撒谎。附在数据本身上，两者在同一个事务语义下。 |
| 「`entities_indexed_at` 为什么用时间戳不用布尔？」 | 顺带留下「什么时候做的」，对排障有用（比如「这批文件是三天前那次失败的产物」）。布尔值省不了多少空间。 |
| 「怎么防止『续跑跳过了一个内容已变的文件』？」 | `updateFile` 把标记清成 NULL。这是必须成对实现的，只做「设」不做「清」会得到一个比不续跑更坏的结果。 |
| 「为什么不干脆每次都用 resume？」 | resume 不重建已完成的文件，所以它**不能**用于「我改了分块策略，要全部重算」。两个按钮对应两个问题：数据要重算 vs 工作没做完。 |
| 「复用 `rebuildFiles` 会不会有耦合风险？」 | 会，所以是刻意的：耦合的方向是「续跑依赖逐文件重建」，而不是「两份实现互相独立却要求一致」。后者才是这个项目吃过亏的形态。 |
| 「老仓库第一次点续跑会怎样？」 | `entities_indexed_at` 全为 NULL ⇒ 第二遍完整重做一遍（第一遍的代码块与向量保留不动）。这是刻意的取舍：不回溯填充，因为「已完成的仓库」里也有第二遍部分失败的文件（文档 14 的 24 个文件就是），回溯填充会把它们永久盖住。 |

### 5.3 ⚠️ 口径红线

- **不要**说「索引时间从 40 分钟降到 X 分钟」。续跑的耗时**取决于剩余工作量**，
  不是一个固定数字。能说的是：**「不重做已完成的部分」是结构性事实**
  （可用 `code_chunks` / 向量行数不变来证明），省下的时间是剩余工作量的函数。
- **不要**说「现在不会有失败了」。续跑只是让失败**可恢复**，不减少失败。
- **不要**把「零待补路径数十秒完成」说成「续跑很快」—— 那是「没有活干」的耗时。

> 顺带修掉的一个独立问题：`updateIndexProgress` 原来是
> `startTime: startTime || new Date()`，而调用方**每处理一个文件**就调一次 ⇒
> `startTime` 被反复覆盖成「当前时间」，前端拿它算的「已用时」恒为 0。
> 这是一个典型的「**字段一直在撒谎，但数值看起来完全合理**」的问题 ——
> 它不是通过报错暴露的，只能通过对字段含义的追问发现。
