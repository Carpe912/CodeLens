## 一、URL 智能推导算法实现

> 真实文件：`apps/api/src/retrieval/url-derivation.ts`（**1571 行**，项目最大的单文件）。
> 真实入口是 `deriveURLConstruction(db, repoId, targetUrl)`，
> 走的是「**数据库符号表 → 入口点匹配 → 图遍历推导**」，而非纯内存 Scope 链。
> 下面的示意代码保留了核心思想，但结构与真实实现有差异。

### 1.1 核心数据结构（真实定义，可直接对照）

```typescript
// apps/api/src/retrieval/url-derivation.ts

/** 推导结果 —— 这是直接返回给 API 层的结构 */
export interface URLDerivationResult {
  pattern: string;              // 推导出的 URL 模式，如 "/api/users/:id"
  confidence: number;           // 置信度 (0-100)，非模型概率
  symbolChain: Array<{          // 符号依赖链：直接作为「证据链」展示给用户
    symbol: string;
    file: string;
    line: number;
    value: string;
  }>;
  derivationSteps: Array<{      // 逐步推导过程，可回放
    step: number;
    description: string;
    from: string;               // 转换前
    to: string;                 // 转换后
  }>;
  missingSymbols: string[];     // 无法解析的变量 —— 显式暴露不确定性
}

/** 符号 —— 把常量/函数/模板统一抽象成「带依赖的图节点」 */
interface Symbol {
  id: string;                                   // "const:API_URL"
  name: string;
  value: string;
  type: 'constant' | 'function' | 'template';
  dependsOn: string[];                          // ← 指向其它符号 id，构成有向图
  returns?: string;                             // 仅函数类型
  file: string;
  line: number;
}
```

**为什么是 `dependsOn` 而不是传统的 `Scope` 链？**
因为真实场景里 URL 是**跨文件**拼出来的：`A.ts` 定义 `BASE`，
`B.ts` 定义 `VERSION`，`C.ts` 写 `${BASE}/${VERSION}/users`。
作用域链天然只能沿调用栈走，跨文件就断了；
而把符号建成**全局有向图**，任何一个节点都能反向推导到根。

**下面是单条 URL 的「展开阶段」示意代码**（对应真实实现里的递归展开步骤，做了结构简化）：

```typescript
class URLDerivationStep {
  private symbolTable: Map<string, Symbol>;
  
  /**
   * 展开单个候选：把符号表达式还原成具体 URL
   * 注：真实实现是按 dependsOn 图递归，这里用串行的 6 个阶段来示意
   */
  async deriveURL(node: RouteNode): Promise<DerivationResult> {
    try {
      let url = node.path;
      const steps: DerivationStep[] = [];
      
      // Step 1: 检查是否是字面量（最简单情况）
      if (this.isStringLiteral(url)) {
        return {
          success: true,
          url: url,
          confidence: 1.0,
          steps: [{ type: 'literal', input: url, output: url }]
        };
      }
      
      // Step 2: 展开模板字符串
      if (this.isTemplateString(url)) {
        const expanded = await this.expandTemplateString(url, node.scope);
        steps.push({ type: 'template_expansion', input: url, output: expanded });
        url = expanded;
      }
      
      // Step 3: 内联函数调用
      if (this.hasFunctionCall(url)) {
        const inlined = await this.inlineFunctionCalls(url, node.scope);
        steps.push({ type: 'function_inline', input: url, output: inlined });
        url = inlined;
      }
      
      // Step 4: 处理三元表达式
      if (this.hasTernaryExpression(url)) {
        const resolved = this.resolveTernary(url, node.scope);
        steps.push({ type: 'ternary_resolution', input: url, output: resolved });
        url = resolved;
      }
      
      // Step 5: 解析局部变量
      if (this.hasVariableReference(url)) {
        const resolved = await this.resolveVariables(url, node.scope);
        steps.push({ type: 'variable_resolution', input: url, output: resolved });
        url = resolved;
      }
      
      // Step 6: 处理字符串拼接
      if (this.hasStringConcatenation(url)) {
        const concatenated = this.evaluateConcatenation(url, node.scope);
        steps.push({ type: 'concatenation', input: url, output: concatenated });
        url = concatenated;
      }
      
      // 计算置信度
      const confidence = this.calculateConfidence(steps);
      
      return {
        success: true,
        url: url,
        confidence: confidence,
        steps: steps
      };
      
    } catch (error) {
      return {
        success: false,
        url: node.path,
        confidence: 0,
        error: error.message,
        steps: []
      };
    }
  }
  
  /**
   * 展开模板字符串
   * 例如: `${API_PREFIX}/users` → `/api/v1/users`
   */
  private async expandTemplateString(
    template: string, 
    scope: Scope
  ): Promise<string> {
    // 匹配 ${...} 模式
    const regex = /\$\{([^}]+)\}/g;
    let result = template;
    const matches = Array.from(template.matchAll(regex));
    
    for (const match of matches) {
      const [fullMatch, expression] = match;
      
      // 评估表达式
      const value = await this.evaluateExpression(expression.trim(), scope);
      
      // 替换
      result = result.replace(fullMatch, value);
    }
    
    return result;
  }
  
  /**
   * 评估表达式
   * 支持：变量引用、属性访问、函数调用、三元表达式
   */
  private async evaluateExpression(
    expr: string, 
    scope: Scope
  ): Promise<string> {
    // 1. 简单变量引用
    if (this.isSimpleIdentifier(expr)) {
      return this.resolveVariable(expr, scope);
    }
    
    // 2. 属性访问 (例如: config.apiPrefix)
    if (expr.includes('.')) {
      return this.resolvePropertyAccess(expr, scope);
    }
    
    // 3. 函数调用 (例如: getPrefix())
    if (expr.includes('(')) {
      return this.resolveFunctionCall(expr, scope);
    }
    
    // 4. 三元表达式 (例如: isDev ? '/dev' : '/prod')
    if (expr.includes('?')) {
      return this.resolveTernary(expr, scope);
    }
    
    // 5. 字符串拼接 (例如: 'api' + version)
    if (expr.includes('+')) {
      return this.evaluateConcatenation(expr, scope);
    }
    
    // 6. 字面量
    return expr.replace(/['"]/g, '');
  }
  
  /**
   * 解析变量引用
   * 支持跨文件追踪
   */
  private resolveVariable(name: string, scope: Scope): string {
    // 1. 在当前作用域查找
    let currentScope: Scope | undefined = scope;
    while (currentScope) {
      const variable = currentScope.variables.get(name);
      if (variable) {
        if (typeof variable.value === 'string') {
          return variable.value;
        } else {
          // 如果是AST节点，需要进一步解析
          return this.evaluateASTNode(variable.value, scope);
        }
      }
      currentScope = currentScope.parent;
    }
    
    // 2. 在导入中查找
    const importInfo = scope.imports.get(name);
    if (importInfo) {
      return this.resolveImportedVariable(importInfo);
    }
    
    // 3. 在全局符号表查找
    const symbol = this.symbolTable.get(name);
    if (symbol) {
      return symbol.value;
    }
    
    // 4. 未找到，返回原始名称
    return `{${name}}`;
  }
  
  /**
   * 解析导入的变量（跨文件追踪）
   */
  private async resolveImportedVariable(
    importInfo: ImportInfo
  ): Promise<string> {
    const { modulePath, exportName } = importInfo;
    
    // 1. 读取目标文件
    const sourceFile = await this.getSourceFile(modulePath);
    
    // 2. 查找导出的变量
    const exportedVar = this.findExportedVariable(sourceFile, exportName);
    
    if (!exportedVar) {
      return `{${exportName}}`;
    }
    
    // 3. 解析变量值
    return this.evaluateASTNode(exportedVar.initializer, this.buildScope(sourceFile));
  }
  
  /**
   * 内联函数调用
   * 只内联简单的纯函数
   */
  private async inlineFunctionCalls(
    expr: string, 
    scope: Scope
  ): Promise<string> {
    const callRegex = /(\w+)\(([^)]*)\)/g;
    let result = expr;
    
    for (const match of expr.matchAll(callRegex)) {
      const [fullMatch, funcName, argsStr] = match;
      
      // 1. 查找函数定义
      const funcDef = this.findFunctionDefinition(funcName, scope);
      if (!funcDef) {
        continue; // 无法找到定义，跳过
      }
      
      // 2. 检查是否可以内联（必须是纯函数）
      if (!this.canInline(funcDef)) {
        continue;
      }
      
      // 3. 解析参数
      const args = this.parseArguments(argsStr, scope);
      
      // 4. 内联函数体
      const inlinedValue = this.inlineFunction(funcDef, args);
      
      // 5. 替换
      result = result.replace(fullMatch, inlinedValue);
    }
    
    return result;
  }
  
  /**
   * 检查函数是否可以内联
   * 条件：
   * 1. 函数体只有一个return语句
   * 2. 没有副作用（不修改外部状态）
   * 3. 不包含复杂逻辑（循环、条件等）
   */
  private canInline(funcDef: FunctionInfo): boolean {
    const body = funcDef.body;
    
    // 检查是否只有一个return语句
    if (body.statements.length !== 1) {
      return false;
    }
    
    const statement = body.statements[0];
    if (!ts.isReturnStatement(statement)) {
      return false;
    }
    
    // 检查return表达式的复杂度
    const returnExpr = statement.expression;
    if (!returnExpr) {
      return false;
    }
    
    // 不允许包含：函数调用、循环、条件语句
    const hasComplexity = this.hasComplexNode(returnExpr);
    
    return !hasComplexity;
  }
  
  /**
   * 内联函数
   * 将参数替换到函数体中
   */
  private inlineFunction(
    funcDef: FunctionInfo, 
    args: string[]
  ): string {
    const returnStatement = funcDef.body.statements[0] as ts.ReturnStatement;
    const returnExpr = returnStatement.expression!;
    
    // 构建参数映射
    const paramMap = new Map<string, string>();
    funcDef.parameters.forEach((param, index) => {
      paramMap.set(param.name, args[index] || '');
    });
    
    // 替换参数
    let result = returnExpr.getText();
    for (const [paramName, argValue] of paramMap) {
      const regex = new RegExp(`\\b${paramName}\\b`, 'g');
      result = result.replace(regex, argValue);
    }
    
    return result;
  }
  
  /**
   * 处理三元表达式
   * 例如: isDev ? '/dev' : '/prod'
   * 
   * 使用状态机解析，处理嵌套情况
   */
  private resolveTernary(expr: string, scope: Scope): string {
    // 状态机状态
    enum State {
      CONDITION,
      TRUE_BRANCH,
      FALSE_BRANCH
    }
    
    let state = State.CONDITION;
    let condition = '';
    let trueBranch = '';
    let falseBranch = '';
    let depth = 0; // 括号深度
    
    for (let i = 0; i < expr.length; i++) {
      const char = expr[i];
      
      // 跟踪括号深度
      if (char === '(') depth++;
      if (char === ')') depth--;
      
      switch (state) {
        case State.CONDITION:
          if (char === '?' && depth === 0) {
            state = State.TRUE_BRANCH;
          } else {
            condition += char;
          }
          break;
          
        case State.TRUE_BRANCH:
          if (char === ':' && depth === 0) {
            state = State.FALSE_BRANCH;
          } else {
            trueBranch += char;
          }
          break;
          
        case State.FALSE_BRANCH:
          falseBranch += char;
          break;
      }
    }
    
    // 评估条件
    const conditionResult = this.evaluateCondition(condition.trim(), scope);
    
    // 返回对应分支
    const selectedBranch = conditionResult ? trueBranch : falseBranch;
    return this.evaluateExpression(selectedBranch.trim(), scope);
  }
  
  /**
   * 评估条件表达式
   */
  private evaluateCondition(condition: string, scope: Scope): boolean {
    // 1. 解析变量
    const resolved = this.resolveVariable(condition, scope);
    
    // 2. 评估布尔值
    if (resolved === 'true') return true;
    if (resolved === 'false') return false;
    
    // 3. 检查环境变量
    if (condition.includes('process.env')) {
      return this.evaluateEnvCondition(condition);
    }
    
    // 4. 默认返回false（保守策略）
    return false;
  }
  
  /**
   * 计算推导置信度
   * 基于推导步骤的复杂度
   */
  private calculateConfidence(steps: DerivationStep[]): number {
    let confidence = 1.0;
    
    for (const step of steps) {
      switch (step.type) {
        case 'literal':
          confidence *= 1.0; // 字面量，100%确定
          break;
        case 'template_expansion':
          confidence *= 0.95; // 模板展开，95%确定
          break;
        case 'variable_resolution':
          confidence *= 0.9; // 变量解析，90%确定
          break;
        case 'function_inline':
          confidence *= 0.85; // 函数内联，85%确定
          break;
        case 'ternary_resolution':
          confidence *= 0.8; // 三元表达式，80%确定
          break;
        default:
          confidence *= 0.7; // 其他情况，70%确定
      }
    }
    
    return confidence;
  }
}
```

## 二、多策略搜索引擎实现

> 真实文件：`apps/api/src/retrieval/multi-strategy-search.ts`（约 1160 行）。

> 下面的类结构为讲解做了归并简化，**逻辑与真实实现一致**。

### 2.1 搜索引擎核心：`searchWithSuggestions` 的 16 步（可直接引用）

> 真实类名 `MultiStrategySearch`。`search()` 只是一层薄封装，真正的流程在
> `searchWithSuggestions()` 里。**这段完整流程是本文件最值得背下来的部分。**

```typescript
// apps/api/src/retrieval/multi-strategy-search.ts
async search(repoId: number, query: string, options: SearchOptions = {}) {
  const response = await this.searchWithSuggestions(repoId, query, options);
  return response.results;                    // 对外只暴露 results
}

async searchWithSuggestions(repoId, query, options = {}): Promise<SearchResponse> {
  const { limit = 20, threshold = 0.5,
          strategies = ['vector', 'exact', 'fuzzy'],
          includeContext = true, followDependencies = false } = options;

  // 步骤 1: 拼写纠错
  const { corrected: correctedQuery, hasCorrected } = correctTypos(query);
  const searchQuery = hasCorrected ? correctedQuery : query;

  // 步骤 2-3: 用「纠错后」的 query 生成缓存键，命中即返回
  const cacheKey = generateCacheKey('search', { repoId, query: searchQuery, ...options });
  const cachedResults = this.searchCache.get(cacheKey);
  if (cachedResults) return { results: cachedResults };

  // 步骤 4: 分析查询意图（url / function / class / constant / general）
  const intent = await this.analyzeQueryIntent(searchQuery);

  // 步骤 5: URL 类查询走专用通道，不做重量级多策略
  if (intent.type === 'url') {
    const urlResults = await searchURL(this.db, repoId, query, limit);
    /* ...转换为统一 SearchResult，缓存后直接 return... */
  }

  // 步骤 6: 按「意图 × 调用方指定策略」求交集
  const selectedStrategies = this.selectStrategies(intent, strategies);

  // 步骤 7: 并行执行（单策略失败不影响其它策略）
  const searchResults = await Promise.all(
    selectedStrategies.map(s => this.executeStrategy(repoId, query, intent, s, limit))
  );

  // 步骤 8: 加权合并（按 intent 动态取权重）+ 内部按 score 降序
  const mergedResults = this.mergeResults(searchResults, intent);

  // 步骤 9: 阈值过滤
  const filteredResults = mergedResults.filter(r => r.score >= threshold);

  // 步骤 10: 上下文增强（命中块上下各扩 5 行）
  if (includeContext) await this.enrichWithContext(repoId, filteredResults);

  // 步骤 11: 依赖扩展（可选）
  if (followDependencies) await this.expandWithDependencies(repoId, filteredResults);

  // 步骤 12-13: 去重 → 截断到 limit
  const deduplicatedResults = this.deduplicateSearchResults(filteredResults);
  const finalResults = deduplicatedResults.slice(0, limit);

  // 步骤 14: 写缓存
  this.searchCache.set(cacheKey, finalResults);

  // 步骤 15-16: 结果少于 3 条时，生成搜索建议
  const availableTerms = await this.getAvailableTerms(repoId);
  let suggestions;
  if (finalResults.length < 3) {
    suggestions = generateSuggestions(query, availableTerms);
  }

  return { results: finalResults, suggestions,
           correctedQuery: hasCorrected ? correctedQuery : undefined };
}
```

**面试可讲的三个设计决策：**

1. **缓存键用纠错后的 query** —— 否则用户把 `usr` 敲成 `user` 会各占一份缓存，
   命中率凭空掉一半。
2. **单策略失败不熔断** —— `Promise.all` 里任一策略抛错不影响其它策略，
   检索是「尽力而为」而非「全有或全无」。
3. **结果少于 3 条主动给建议** —— 检索的失败模式有两种：给错和给空。
   给空比给错更容易补救，所以系统在「给空」时主动引导用户换关键词。

#### 真实策略选择逻辑（可直接引用）

> 注意：**不是**用 `looksLikeExactPath()` / `queryMentionsDependencies()` 这类
> 正则猜测函数逐个判断，而是**先算出 `intent`，再用 `intent` + 调用方指定的
> `requestedStrategies` 两者求交集**。

```typescript
// apps/api/src/retrieval/multi-strategy-search.ts
private selectStrategies(
  intent: QueryIntent,
  requestedStrategies: SearchStrategy[]   // 来自 options.strategies
): SearchStrategy[] {
  const strategies: SearchStrategy[] = [];

  // 向量：语义理解的基础，调用方要求就用
  if (requestedStrategies.includes('vector')) strategies.push('vector');

  // 精确：只在意图置信度高时才值得用
  if (intent.confidence > 0.8 && requestedStrategies.includes('exact')) {
    strategies.push('exact');
  }

  // 模糊：容错
  if (requestedStrategies.includes('fuzzy')) strategies.push('fuzzy');

  // 依赖感知：URL 与函数类查询才用
  if ((intent.type === 'url' || intent.type === 'function')
      && requestedStrategies.includes('dependency')) {
    strategies.push('dependency');
  }

  // 图遍历：仅函数类查询
  if (intent.type === 'function' && requestedStrategies.includes('graph')) {
    strategies.push('graph');
  }

  return strategies;
}
```

**这里有个容易被忽略的细节**：`intent.confidence > 0.8` 才启用精确匹配。
意图识别本身可能出错，低置信度时启用精确匹配会**放大误判** ——
把「不确信的意图」直接变成「硬性字面过滤」。用置信度当闸门是个廉价而有效的防御。

#### 真实结果融合逻辑（可直接引用）

> ⚠️ 原文档这里写的是**固定权重 0.4/0.3/0.15/0.1/0.05 + 位置加权 + 4 因子重排**，
> **仓库里没有这段代码**。真实实现如下：

```typescript
private mergeResults(resultSets: SearchResult[][], intent: QueryIntent): SearchResult[] {
  const merged = new Map<string, SearchResult>();

  // 权重表本身依赖 intent —— 「动态加权」的真实含义
  const weights: Record<string, number> = {
    vector:     intent.type === 'general'   ? 1.0 : 0.8,
    exact:      intent.confidence > 0.8     ? 1.2 : 0.9,
    fuzzy:      0.7,
    dependency: intent.type === 'url'       ? 1.1 : 0.8,
    graph:      intent.type === 'function'  ? 1.1 : 0.8,
  };

  resultSets.forEach(results => {
    results.forEach(result => {
      const key = `${result.filePath}:${result.lineStart}`;
      const weight = weights[result.metadata.strategy] || 1.0;
      const weightedScore = result.score * weight;

      if (merged.has(key)) {
        // 被多个策略同时命中 → 独立性本身就是置信度信号
        merged.get(key)!.score = Math.max(merged.get(key)!.score, weightedScore) + 0.1;
      } else {
        merged.set(key, { ...result, score: weightedScore });
      }
    });
  });

  return Array.from(merged.values()).sort((a, b) => b.score - a.score);
}
```

**为什么这个设计比「固定权重加权平均」好（面试可讲）：**

| 维度 | 固定权重加权平均 | 本项目的动态加权 |
|------|----------------|----------------|
| 权重来源 | 人工拍定，全局唯一 | 由 `intent` 决定，随查询变化 |
| 多策略命中 | 分数简单累加，可能**被低质策略刷高** | `max(...) + 0.1`，只奖励「额外独立命中」 |
| 去重键 | `${url}:${filePath}` | `${filePath}:${lineStart}`（更细，同一文件不同位置不糊在一起） |
| 抗噪 | 一个噪声策略持续输出会拉高所有结果 | 噪声策略只能抬高它自己命中的那几条 |

> 📌 **`mergeResults()` 之后还有一层（本次新增）**：**模型精排**。
> 开启 `RERANK_ENABLED` 时完整链路是——
> 宽召回 50 → 上面的规则融合 → 去重 → **调 `qwen3.7-text-rerank` 语义重排** → 截断到 limit。
> 两个阶段职责不同：规则融合负责「**别把明显相关的漏掉**」（召回保底），
> 模型精排负责「**把最相关的顶上来**」（排序质量）。调不通会自动降级回规则排序并冷却。
> 代码见 `apps/api/src/retrieval/rerank.ts`。

**真实去重逻辑**不在 `MultiStrategySearch` 里，而是抽在工具模块中：

```typescript
// apps/api/src/retrieval/deduplication.ts
import { deduplicateResults, DeduplicatableResult } from './deduplication.js';
```

抽出独立模块的好处：聚类/长度/相似度阈值这些**去重策略本身也是可测的**，
不需要起数据库就能验证。

### 2.2 策略分发：一个 switch，不是 5 个类

真实实现（可直接引用）：

```typescript
// apps/api/src/retrieval/multi-strategy-search.ts
private async executeStrategy(
  repoId: number,
  query: string,
  intent: QueryIntent,
  strategy: SearchStrategy,      // 'vector' | 'exact' | 'fuzzy' | 'dependency' | 'graph'
  limit: number
): Promise<SearchResult[]> {
  switch (strategy) {
    case 'vector':     return this.vectorSearch(repoId, query, intent, limit);
    case 'exact':      return this.exactSearch(repoId, query, intent, limit);
    case 'fuzzy':      return this.fuzzySearch(repoId, query, intent, limit);
    case 'dependency': return this.dependencySearch(repoId, query, intent, limit);
    case 'graph':      return this.graphSearch(repoId, query, intent, limit);
    default:           return [];
  }
}
```

> **面试可讲点**：为什么不用策略模式（5 个 `implements SearchStrategy` 的类）？
> 因为 5 个策略**不是同一层级的东西** —— `vector` 要按 `intent` 去**多张表**分别查
> （`getSearchTables(intent.type)`），`exact` 则按 `intent.type` 走完全不同的 SQL 分支。
> 它们的输入依赖、查询对象都不一样，硬套统一接口只会多一层空转发。
> 用一个 switch + 私有方法，反而让「每种策略到底怎么查」一眼可见。

### 2.3 向量策略（真实实现，可直接引用）

```typescript
private async vectorSearch(
  repoId: number, query: string, intent: QueryIntent, limit: number
): Promise<SearchResult[]> {
  // 1. 生成查询向量（DashScope qwen3.7-text-embedding，指定 1536 维）
  const queryEmbedding = await this.generateQueryEmbedding(query);
  const embeddingVector = `[${queryEmbedding.join(',')}]`;   // pgvector 的文本字面量格式

  const results: SearchResult[] = [];

  // 2. 按意图决定查哪些表 —— 不是只查一张表
  const tables = this.getSearchTables(intent.type);

  for (const table of tables) {
    const query = this.buildVectorQuery(table, repoId, embeddingVector, limit);
    const result = await this.db.query(query.sql, query.params);
    results.push(...this.mapToSearchResults(result.rows, table, 'vector'));
  }

  return results;
}
```

**关键差别**：不是 `SELECT ... FROM routes`，而是 **`getSearchTables(intent.type)` 返回多张表，
逐表查询后统一映射**。例如概念类查询会同时命中 `code_chunks` / `functions` / `classes`。
这正是「按代码实体分表」这个 schema 设计的直接收益。

### 2.4 精确策略（真实实现，可直接引用）

`exactSearch` 内部按 `intent.type` 分成**完全不同的 SQL 分支**：

### 3.2 改造后：LangGraph 有环图（`agent/graph/`）

替换方案不是「补全那个假的循环」，而是用 LangGraph 的**条件边**把

```typescript
// apps/api/src/agent/graph/index.ts
const workflow = new StateGraph(GraphState)
  .addNode('retrieve', createRetrieveNode(search))     // 复用 MultiStrategySearch
  .addNode('grade', createGradeNode())                 // 复用 utils/scoring
  .addNode('generate', createAnswerNode(deps.generateAnswer))  // 复用 llm/qa
  .addEdge(START, 'retrieve')
  .addEdge('retrieve', 'grade')
  .addConditionalEdges('grade', routeAfterGrade, {     // ← 环就在这里
    retrieve: 'retrieve',
    generate: 'generate',
  })
  .addEdge('generate', END);
```

```typescript
// apps/api/src/agent/graph/nodes.ts —— 收敛性保证
export function routeAfterGrade(state: GraphStateType): 'retrieve' | 'generate' {
  if (state.sufficiency >= state.sufficiencyThreshold) return 'generate';
  if (state.round >= state.maxRounds) return 'generate';   // 先查上限，最坏必收敛
  return 'retrieve';
}
```

**逐轮升级的策略表（`SEARCH_STRATEGY_PLAN`）：**
第 1 轮 `[vector, exact]` 阈值 0.3 求精准；
第 2 轮加 `dependency` + `followDependencies` 扩大召回；
第 3 轮 `[vector, exact, fuzzy, graph]` 阈值降到 0.2 尽量兜住。

**这个设计的三个可讲点：**
1. **检索实现一行未改** —— 图只接管「什么时候调用谁、失败后怎么办」
2. **状态显式** —— 全部流转信息在 `GraphState` 里，可落库、可审计、可选 checkpointer 续跑
3. **可测** —— `createCodeLensGraph` 接受注入的 `search` / `generateAnswer`，
   因此环的收敛行为能在**无数据库、无 LLM** 的环境下被 30 条断言完整覆盖
   （`pnpm verify:graph`）

**踩过的真实坑（很值得讲）：** 终节点最初命名为 `answer`，
而状态里已有一个 `answer` 通道 —— LangGraph 不允许节点与状态通道重名。
`tsc` 编译通过，`compile()` 时才抛
`answer is already being used as a state attribute (a.k.a. a channel)`。
改名 `generate` 后通过。这个坑直接推动了「用依赖注入写测试」的决定。

## 四、性能优化实现

### 4.1 pgvector 批量删除优化（`clearRepoData`）

> 真实文件：`apps/api/src/db/index.ts`。
> 这段代码的注释写得比大多数「优化文章」都清楚，**面试时直接讲注释里的推理链**即可。

核心反直觉结论：**删数据慢，是慢在索引维护，不是慢在删除本身。**

```typescript
export async function clearRepoData(repoId: number): Promise<void> {
  // ── Step 1: 先删索引和外键约束 ──────────────────────────
  // 为什么先删索引？
  //   - 索引维护是删除操作的主要性能瓶颈
  //   - HNSW 向量索引在删除时特别慢（需要重新平衡图结构）
  //   - 删除索引后，DELETE 只需删表数据，快得多
  await pool.query('DROP INDEX IF EXISTS idx_code_chunks_embedding_hnsw');
  await pool.query('DROP INDEX IF EXISTS idx_code_chunks_node_type');
  await pool.query('DROP INDEX IF EXISTS idx_code_chunks_metadata');
  /* ...其余索引与 code_chunks 相关外键一并 DROP... */

  // ── Step 2: 手动删子表（从叶子到根） ────────────────────
  // 为什么不用外键级联？
  //   - 级联会触发多次查询+删除，开销大
  //   - 手动删除可以批量 DELETE，更快
  await pool.query('DELETE FROM constant_references WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM string_constants    WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM url_usages          WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM url_patterns        WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM call_graph          WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM functions           WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM classes             WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM file_dependencies   WHERE repo_id = $1', [repoId]);
  await pool.query('DELETE FROM import_relations    WHERE repo_id = $1', [repoId]);

  // ── Step 3: 删 code_chunks（此时无索引无约束，极快） ─────
  const fileIds = (await pool.query('SELECT id FROM files WHERE repo_id = $1', [repoId]))
    .rows.map(r => r.id);
  if (fileIds.length > 0) {
    await pool.query('DELETE FROM code_chunks WHERE file_id = ANY($1)', [fileIds]);
  }

  // ── Step 4: 删 files ───────────────────────────────────
  await pool.query('DELETE FROM files WHERE repo_id = $1', [repoId]);

  // ── Step 5: 重建索引与约束 ─────────────────────────────
  // 为什么批量重建更快？
  //   - PostgreSQL 对批量索引构建有优化，可一次性扫描全表
  //   - 比逐行维护索引快得多
  await pool.query(`
    CREATE INDEX IF NOT EXISTS idx_code_chunks_embedding_hnsw
    ON code_chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)      -- 最耗时的索引，放最后
  `);
  /* ...重建其余索引，再用 DO 块安全恢复外键约束... */
}
```

**这段代码为什么值得讲（三个层次）：**

1. **定位瓶颈**：不是「删得慢」，而是「边删边维护索引」慢。定位方法就是看执行计划里
   索引维护占了多大比例。
2. **利用数据库特性**：HNSW 是图结构，删除需要重新平衡节点连接；
   批量构建时 PostgreSQL 可以一次扫表建完，而逐行删除做不到。
3. **安全兜底**：`DO $$ ... $$` 块保证约束「不存在才创建」，
   让整个函数可以重复执行（幂等），这是运维友好性的体现。

> ⚠️ **注意**：不要报「10-12x 提速」这类数字 —— 代码里没有基准测试。
> 正确说法是「**改造前后的差异是可以解释的**：把随机写变成顺序批量写」，
> 如果对方追问倍数，就说「需要在你给的硬件和规模上实测」。
