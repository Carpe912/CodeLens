## 一、一句话定位（最重要）

**错误定位**（现在的写法，一听就普通）：

> 基于 RAG 的代码问答系统，支持自然语言查询代码。

**推荐定位**：

> **跨 HTTP 边界的代码依赖关系重建** —— 解决静态分析做不到的那一半：接口的调用方。

为什么这么定：`grep` 和 IDE 的「Find Usages」都**跨不过 HTTP 边界**。前端代码里只有一条 URL 字符串，后端只有一条路由声明，两者在编译器眼里毫无关系。所以业界现状是 grep 字符串或去群里问人，而 grep 有两个死穴：模板拼接的路径（`${baseURL}/api/products/${id}`）会漏，且**无法回答「找全了没有」**。

从「我找到几处」到「一共 7 个调用点，实现在这一行」——这是从无到有，不是从慢到快。**这个论证比任何提效百分比都硬。**

## 二、简历条目（按篇幅选一版）

### 版本 A · 一行（适合"项目经历"里占一行）

> **CodeLens｜代码依赖关系索引与追溯系统**（TS / Node.js / PostgreSQL + pgvector，个人项目）
> 用 AST 索引 + URL 规范化把前后端的接口调用关系重建起来，解决静态分析跨不过 HTTP 边界、无法枚举接口调用方的问题。

### 版本 B · 三条（推荐，最常用）

> **CodeLens｜代码依赖关系索引与追溯系统**　*个人项目 · TS/Node.js · PostgreSQL+pgvector*
>
> - **跨边界调用关系**：静态调用图无法跨越 HTTP 边界，改用「URL 规范化 + 接口模式索引」重建调用方与实现方的对应关系。把前后端的 URL 字面量与模板统一规范化到接口模式（`/api/users/${id}` 与 `/api/users/:id` 归一到同一行），前端侧记调用点、后端侧记路由定义，从而反查接口的完整调用方清单，并接上 handler 的进程内调用链（`call_graph`）。
> - **混合检索**：向量（pgvector 1536 维）+ 精确 + 模糊 + 依赖展开 + URL 模板推导多路召回，再用 rerank 模型语义重排；rerank 不可用时自动降级回规则排序并进入冷却，检索链路不因外部服务失败而中断。
> - **索引层静默故障排查**：定位并修复唯一索引漏掉 HTTP 方法导致的静默丢数据（`(repo_id, pattern)` 缺 `method`，同一路径下 GET/PUT/DELETE 只有第一个能入库，冲突又被 `catch` 吞掉）。修复后接口模式 65→78，可用调用点 16→36，跨边界配对率 4/65→7/78。

### 版本 C · 详版（适合单独一页或大篇幅）

在版本 B 基础上补：

> - **索引与存储**：自研 TS/JS/Vue AST 解析器产出 9 类关系表（代码块、函数、类、字符串常量、URL 模式、URL 使用位置、调用图、导入关系、文件依赖），pgvector HNSW 支撑 1536 维语义检索。
> - **Agent 编排**：主链路为「意图分类 → 混合检索 → 生成」三段式；另实现 LangGraph 状态图（`retrieve → grade →` 证据不足时回到 `retrieve` → `generate`），含轮次上限收敛控制与每阶段耗时 trace。
> - **交付形态**：Fastify 5 API + React 前端（含 ReactFlow 调用图可视化、Monaco 代码查看）；线上 nginx + PM2，前端与 API 均采用原子切换发布并保留回滚点。
> - 规模：约 34,400 行 TypeScript（后端约 29,200 / 前端约 5,200）。口径：`apps/*/src` 下的 `*.ts` / `*.tsx`，用 `wc -l` 统计 —— 面试时可直接现场跑一遍验证。

### 英文版（备选）

> **CodeLens — Cross-boundary code dependency index & traceability** *(Personal project, TypeScript/Node.js, PostgreSQL + pgvector)*
> Reconstructs API call-relationship across the HTTP boundary — the half static analysis cannot reach. Normalizes front-end URL literals and back-end route patterns into a shared endpoint identity, so an API's complete set of call sites can be enumerated rather than grepped. Hybrid retrieval (vector + exact + fuzzy + dependency expansion + URL template derivation) with model reranking and graceful degradation.

## 五、面试追问预案

### Q0：随便一个 AI IDE 就能做到，为什么要用你这个系统？（最可能被问倒的一题）

**一句话回击**：AI IDE 给你的是「它找到的那几个」；索引给你的是「全部」，而且能告诉你有没有漏。

**先承认对方对在哪**（不承认会被玩具仓库反问回来）：
在单个小仓库、一次性问答、有人兜底的场景，AI IDE 确实更好 —— 零部署、支持所有语言（我们只支持 TS/JS/Vue）。
本论证只在两个条件下成立：**多仓/大仓规模**，以及**需要完备性或可回归的决策场景**。

**核心区分**：

| | AI IDE | 索引系统 |
|---|---|---|
| 回答的是 | 这个人此刻**想知道**什么 | 这件事在被改动前**是否已被确认** |
| 性质 | 搜索 | **校验** |
| 足够标准 | 「够用了」 | 「完备」 |
| 失败模式 | 漏了没人知道 | 可度量、可回归 |

搜索只需要「够用」，校验需要「完备」。LLM 按构造是**采样式**的：grep 几轮、读几个文件、判断"差不多了"就停 ——
**它不知道它没找到什么**。改接口之前"大概齐"，正是线上事故的成因。

**四条论证**：
1. **完备性** —— 索引是闭集，可枚举，且**能测召回率**；LLM 给不出"还有没有别的"。
2. **可重复/可审计/可 diff** —— 同一问题问两次、十个人问，AI IDE 答案可能不同；删接口的结论需要确定性、能进 MR、能被人 review。
3. **成本随规模爆炸** —— AI IDE 是 per-question、per-developer、按 token 计费且每次从零探索；索引是**一次构建、长期查询**。
   这是「索引 vs 全表扫描」的老区别，不会因为模型聪明就不要数据库。
4. **能进流水线** —— 可对「改了路由却没更新调用方」设 CI 门禁，可批量回答「哪些接口已没人调用可以下线」。AI IDE 是交互式的，不进门禁。

**一个具体机制（证明不是空谈）**：
```js
axios.get(`${API_PREFIX}/${RESOURCES.USERS}/${id}/profile`)
```
grep 找不到；LLM 要读 config 跟三层常量才**可能**推出来，且不稳定。
我们把两侧都规范化到同一接口标识（`api/users/:id/profile`）所以能匹配上 —— **机制差异，不是速度差异**。

**收尾（把它变成上游而不是竞品）**：
LLM 最常见的失败是「没检索到」，一个确定性的接口索引正好可以当它的检索底座，
让它拿到**完整**调用点集合而不是抽样到的几个。定位是 AI IDE 的**上游**。

**60 秒口述稿**：见上方四条论证顺序陈述，务必保留开头那句「在单个小仓库上 AI IDE 做得比我们好，我不否认」。

> ⚠️ **这一题的真正解法不是话术，是数字。** 上面整套论证目前都是修辞 ——
> 因为手上只有 14 个文件、78 个接口、配对率 7/78 的样本仓库，一句"你仓库才 14 个文件"就能打回来。
> 只要给出两个数，对方就问不下去：
> ① 真实仓库（几十万文件）上的 **recall@k**，证明"完备"不是口号；
> ② **同类问题人工平均耗时 vs 系统 P95**，证明值得部署。
> 所以补强清单第 1、2 项不是加分项，**是这道题的答案本身**。

### Q1：这个意义是什么？不就是查接口吗？

> 查接口是最容易说明的入口，底层是**在缺乏类型系统连接的代码库里重建跨模块、跨进程的依赖关系**。接口之所以是最锋利的入口，因为它有一个用户能说出口的稳定标识符（URL）。同一套索引能回答的是同一类问题：这个字段被哪些模块读、这个常量改了影响谁、这个路由下线安全吗。索引层是两层关系：进程内的 `call_graph`，和跨 HTTP 边界的 URL 边。

### Q2：IDE 或 grep 不就行了？

> 三个层面不成立。一，IDE 能找方法引用，**跨不过 HTTP 边界**；二，grep 遇到模板拼接的路径会漏（`${this.baseURL}/api/products/${id}` 这条我就漏过）；三，也是最关键的，grep 没法告诉你找全了没有。索引化之后可以枚举，输出的是调用点清单而不是一堆匹配行。

### Q3：你怎么知道找全了？

> 现在保证不了，这是已知短板，我能量化它：78 个接口里只有 7 个两侧数据齐全。剩下两类漏因——路径参数名差异（客户端 `:id` 与路由 `:userId` 规范化后是两个串）和纯变量拼接的路径还没解析。下一步是补 URL 推导链并用标注集量化召回。**（承认边界不会显得弱，编一个完整性才会。）**

### Q4：Java 项目能用吗？

> 现在不能，解析器只有 TS/JS/Vue。这也是我明确的下一个里程碑——只有把后端侧纳入，「跨边界」才是完整的故事。

### Q5：这套东西准确率怎么样？

> 分两层看。进程内的调用图存在两个已知噪声：解析失败的边（`to_chunk_id` 为空）和「声明伪影自环」，我用精确谓词过滤后者而不是一刀切掉所有自环，否则会误杀真递归。跨边界那层准确率取决于 URL 规范化质量，目前靠占位段通配兜住参数名差异。

### Q6：讲一个最有技术含量的排查

**（这段建议背下来）**

> 有次发现调用关系的覆盖率只有 6%，65 个接口里只有 4 个能查到调用方。我先查数据，发现 `url_usages` 445 行里有 344 行是重复的，去重后只剩 101 行真实记录。然后开事务做了一次插入试探 —— 插一条真实存在的路由，直接报唯一键冲突。根因是唯一索引建在 `(repo_id, pattern)` 上，**漏了 HTTP 方法**：同一个路径字符串下 GET/POST/PUT/DELETE 只有第一个能入库，后面的 INSERT 抛冲突，又被外层一个 `catch` 记一行日志就跳过了。
>
> 修法是三步：索引改成 `(repo_id, COALESCE(method,''), normalized_pattern)`，与代码里的查询键对齐（一个接口一行、两侧共用）；写入改成 UPSERT，让冲突从"错误"变成"复用"；再加一条对使用位置表的唯一约束挡重复。另外发现分类函数判定顺序反了——先判 `.get(` 就当路由定义，而客户端只认 `axios`/`fetch`，导致 `this.client.get(url)` 全被误判成路由定义。修完接口模式 65→78，可用调用点 16→36。

## 八、一句话总结

> 这个项目的价值不在于「查接口」这个功能，而在于**它做了一件静态分析结构上做不到的事**，并且你能讲清楚为什么原来的做法（grep）不成立。面试官记不住五个功能，但会记住一个能追到索引层唯一键的人。
